# React, 당신이 알던 방식이 아닐지도? 내부 동작 원리 완벽 해부!

React 코드를 작성하고 브라우저에서 결과물을 보면서 "잠깐... 왜 이렇게 동작하지?" 하고 의아해했던 경험, 혹시 있으신가요?

모든 React 개발자가 한 번쯤은 작성해봤을 법한 고전적인 코드 조각이 있습니다.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    console.log(count);
  }

  return <button onClick={handleClick}>Count: {count}</button>;
}
```

버튼을 클릭합니다. 화면의 버튼 텍스트는 0에서 1로 업데이트됩니다. 하지만 브라우저 콘솔에는 이렇게 찍힙니다.

```plaintext
0
```

1이 아니라, 0입니다.

처음에는 아주 미세한 지연이겠거니 생각할 수 있습니다. 그래서 다시 한번 클릭해보죠. 버튼은 2로 업데이트되지만, 콘솔에는 1이 찍힙니다. 언제나 한 단계 뒤처져 있죠.

대체 왜 이럴까요?

제가 처음 이 현상을 마주했을 때, 어떤 포럼에서 "아, `setState`는 비동기라서 그래요"라는 답변을 들었습니다. 그리고 몇 달 동안 그 답변을 그대로 받아들였죠. 하지만 그건 완전한 진실이 아닙니다. 사실, 상태를 "비동기적으로 업데이트되는 변수"라고 생각하는 멘탈 모델이야말로 수많은 프로덕션 앱에서 버그를 유발하는 주범입니다.

오늘은 React의 깊은 내부 동작 원리를 파헤쳐 볼 겁니다. 불필요한 미사여구는 빼고, 교과서적인 정의도 최소화할게요. 실제 데이터 구조, 파이버(Fiber) 트리, 훅(Hook) 규칙이 왜 존재하는지, 그리고 React가 여러분의 JavaScript 코드를 어떻게 화면의 픽셀로 바꾸는지 자세히 알아보겠습니다.

좋아하는 커피 한 잔 들고, 함께 파고들어 볼까요?

## 멘탈 모델 트랩: 초보자의 생각 vs 현실

대부분의 개발자들이 React를 처음 배울 때, 뇌는 다음과 같은 아주 간단한 모델을 만듭니다.

1.  `setCount(1)`을 호출한다.
2.  React가 HTML을 뒤진다.
3.  `<button>Count: 0</button>`을 `<button>Count: 1</button>`로 바꾼다.
4.  끝.

![초보 개발자들이 React가 작동한다고 생각하는 방식 vs 실제 작동 방식](https://i.imgur.com/uZ0b2ET.jpeg)

만약 React가 이런 식으로 작동한다면, 정말 형편없는 프레임워크가 될 겁니다. 상태가 업데이트될 때마다 브라우저 DOM을 직접 검색하고 조작하는 것은 느리고 비용이 많이 드는 작업입니다. 브라우저는 스타일을 다시 계산하고, 레이아웃 기하학(리플로우)을 다시 계산하고, 픽셀을 다시 그려야 하니까요.

대신 React는 근본적으로 다른 방식으로 동작합니다.

**React는 `setState`를 호출할 때 DOM을 즉시 업데이트하지 않습니다. 대신 미래에 실행될 계산을 스케줄링합니다.**

컴포넌트가 업데이트될 때마다 발생하는 세 가지 뚜렷한 단계를 자세히 살펴보겠습니다.

## 세 가지 단계: 트리거(Trigger), 렌더(Render), 커밋(Commit)

React를 고급 레스토랑 주방에 비유해 볼까요?

*   **트리거 단계 (Trigger Phase)**: 손님이 주문을 합니다.
*   **렌더 단계 (Render Phase)**: 셰프가 요리를 하고, (주방 안에서 손님에게 보이지 않게) 카운터에 접시를 놓습니다.
*   **커밋 단계 (Commit Phase)**: 웨이터가 요리를 가져가 손님 테이블에 놓습니다.

만약 손님이 요리 도중에 마음을 바꾼다면, 셰프는 손님이 보기도 전에 반쯤 조리된 접시를 버릴 수 있습니다. 하지만 접시가 테이블에 놓이는 순간, 그것이 바로 커밋이죠.

이것이 React에서는 어떻게 매핑되는지 살펴보겠습니다.

```plaintext
[사용자 인터랙션]
       |
       v
1. 트리거 단계 (dispatchSetState가 업데이트 요청을 큐에 추가)
       |
       v
2. 렌더 단계 (순수 JS 계산: 컴포넌트 호출, Fiber 트리 비교)
       |
       v
3. 커밋 단계 (동기적인 DOM 변이: document.createElement, appendChild)
       |
       v
4. 브라우저 페인트 (브라우저가 모니터에 픽셀을 다시 그림)
```

각 단계를 자세히 알아봅시다.

### 1. 트리거 단계 (The Trigger Phase)

`setCount(count + 1)`을 호출한다고 해서 컴포넌트 함수가 즉시 다시 실행되는 것은 아닙니다.

대신 React는 **업데이트 객체(Update Object)**를 생성하고, 이 객체를 해당 컴포넌트의 내부 표현(internal representation)에 연결된 업데이트 큐에 넣습니다. React는 이 컴포넌트를 "dirty(변경 필요)" 상태로 표시하고, React 스케줄러를 통해 작업을 스케줄링합니다.

만약 버튼을 빠르게 세 번 클릭하거나, 동일한 이벤트 핸들러 내에서 세 개의 다른 상태 변수를 업데이트하더라도, React는 이들을 함께 묶어서 처리합니다. 빵 스틱 세 개를 위해 주방을 세 번 돌리지 않는다는 거죠. 전체 주문을 먼저 모아 한 번에 처리합니다.

### 2. 렌더 단계 (The Render Phase - 순수 JavaScript)

이 단계는 이름 때문에 사람들이 가장 혼란스러워하는 부분입니다.

개발자들이 "렌더(render)"라고 들으면 화면에 픽셀을 그리는 것을 생각합니다. 하지만 React에서 **렌더링은 단순히 컴포넌트 함수를 호출하는 것을 의미합니다.**

React는 `Counter()`를 호출합니다. 여러분의 함수는 위에서 아래로 실행되고 JSX를 반환합니다.

그렇다면 JSX는 무엇일까요?

```jsx
return <button className="btn">Click me</button>;
```

내부적으로 컴파일러(Babel 또는 Vite)는 이 JSX를 일반적인 JavaScript 함수 호출로 변환합니다.

```javascript
return React.createElement('button', { className: 'btn' }, 'Click me');
```

그리고 `React.createElement()`는 단순히 경량의 순수 JavaScript 객체를 반환합니다.

```javascript
{
  type: 'button',
  props: {
    className: 'btn',
    children: 'Click me'
  },
  key: null,
  ref: null
}
```

이것이 "가상 DOM 노드(Virtual DOM node)"의 전부입니다. UI가 어떻게 보여야 하는지를 설명하는 단순한 JavaScript 객체일 뿐입니다. 실제 브라우저 DOM과는 아직 아무런 관련이 없습니다.

React는 이렇게 새로 반환된 객체 트리를 이전 객체 트리와 비교합니다. 이 비교 과정을 **재조정(Reconciliation)**이라고 부릅니다.

React는 묻습니다. *"`type`이 변경되었는가? 아니, 여전히 버튼이다. `className`이 변경되었는가? 아니, 여전히 'btn'이다. 텍스트가 변경되었는가? 예, '0'에서 '1'로 변경되었다."*

React는 작은 패치 명령을 기록합니다. `버튼 텍스트를 1로 업데이트하라`.

### 3. 커밋 단계 (The Commit Phase)

이제 React는 필요한 최소한의 변경 사항을 정확히 알았으므로, 커밋 단계로 진입합니다.

이 단계는 동기적이며 중단될 수 없습니다. React는 네이티브 브라우저 API를 사용하여 실제 DOM에 접근합니다.

```javascript
domNode.textContent = '1';
```

변경이 필요한 특정 텍스트 노드만 건드려집니다. 나머지 DOM 트리는 완전히 그대로 유지됩니다.

커밋 단계가 완료되고 레이아웃 효과(layout effects)가 실행되면, 브라우저 엔진이 제어권을 넘겨받아 업데이트된 픽셀을 모니터에 그립니다.

## 훅(Hook) 순서가 중요한 이유: 파이버(Fiber) 연결 리스트

React에 왜 그렇게 엄격하고, 때로는 짜증 나는 규칙이 있는지 궁금해본 적이 있으신가요?

> *"반복문, 조건문, 또는 중첩된 함수 안에서 Hooks를 호출하지 마세요."*

이 규칙을 어기면 콘솔에 다음과 같은 무서운 에러가 폭발합니다.

```plaintext
Error: Rendered fewer hooks than expected. This may be caused by an accidental early return statement.
```

왜 이런 일이 발생할까요? React가 변수 이름으로 상태를 찾아보는 걸까요?

```jsx
const [name, setName] = useState("Dan");
const [age, setAge] = useState(25);
```

`const [name, setName]`을 작성할 때, JavaScript는 React에게 `"name"`이라는 단어를 알려주지 않습니다. `name`이라는 변수명은 여러분의 함수 내에서 완전히 로컬한(지역적인) 것입니다. React는 여러분이 그것을 뭐라고 불렀는지 전혀 모릅니다.

그렇다면 React는 어떻게 첫 번째 `useState`가 `name`에 속하고, 두 번째 `useState`가 `age`에 속하는지 아는 걸까요?

**React는 컴포넌트의 파이버(Fiber) 노드에 훅을 단일 연결 리스트(singly-linked list) 형태로 저장합니다.**

![훅 순서 규칙이 존재하는 이유: 파이버 연결 리스트](https://i.imgur.com/h8AQQlI.jpeg)

화면의 모든 컴포넌트는 내부적으로 `FiberNode` 객체로 표현됩니다. 이 파이버 노드에는 `memoizedState`라는 속성이 있습니다.

컴포넌트가 처음 렌더링될 때, React는 훅 객체들의 체인을 구축합니다.

```plaintext
FiberNode (<UserProfile />)
    |
    v
memoizedState ──> [ Hook 0: useState ('Dan') ]
                         │
                         ▼ (next)
                  [ Hook 1: useEffect (fetchData) ]
                         │
                         ▼ (next)
                  [ Hook 2: useState (25) ]
                         │
                         ▼ (next)
                        null
```

이후의 모든 렌더링에서는 React가 새로운 리스트를 생성하지 않습니다. 대신 `workInProgressHook`이라는 내부 포인터를 리스트의 첫 번째 훅으로 설정합니다.

1.  `useState()`를 호출합니다: React는 Hook 0 (`'Dan'`)을 읽습니다. 포인터는 Hook 1로 이동합니다.
2.  `useEffect()`를 호출합니다: React는 Hook 1을 읽습니다. 포인터는 Hook 2로 이동합니다.
3.  `useState()`를 호출합니다: React는 Hook 2 (`25`)를 읽습니다. 포인터는 null로 이동합니다.

이제 조건문 안에 훅을 넣으면 어떤 일이 발생하는지 살펴봅시다.

```jsx
function UserProfile({ isLoggedIn }) {
  const [name, setName] = useState("Dan"); // Hook 0

  if (isLoggedIn) {
    useEffect(() => {                      // Hook 1 (조건부!)
      fetchUserData();
    }, []);
  }

  const [age, setAge] = useState(25);       // Hook 2
  
  return <div>{name}, {age}</div>;
}
```

첫 번째 렌더링에서 `isLoggedIn`이 `true`였다고 상상해봅시다. React는 세 개의 훅 레코드(`[name, effect, age]`)를 생성했습니다.

두 번째 렌더링에서 `isLoggedIn`이 `false`가 됩니다.

1.  2행에서 `useState()`를 호출합니다: React는 Hook 0 (`name`)을 읽습니다. 포인터는 Hook 1로 이동합니다.
2.  4행의 조건은 `false`입니다! `useEffect`는 건너뛰어집니다.
3.  10행에서 `useState()`를 호출합니다: React는 Hook 1을 읽습니다! 하지만 Hook 1은 `age` 상태가 아니라 이펙트(effect) 객체였어야 합니다!

데이터가 완전히 뒤죽박죽이 됩니다. React는 호출된 훅의 수가 연결 리스트와 일치하지 않는 것을 감지하고, 데이터가 손상되기 전에 오류를 발생시키고 실행을 중단합니다.

사실 제가 초보 시절에 멋모르고 조건문 안에 훅을 넣었다가, 'Rendered fewer hooks than expected' 에러를 수없이 마주하고는 머리를 쥐어뜯었던 기억이 생생합니다. 그 당시에는 "그냥 규칙이라니까 지켜야지" 하고 넘어갔지만, 이렇게 내부 동작을 알고 나면 왜 이 규칙이 절대적인지 명확히 이해할 수 있죠.

이것이 바로 훅의 순서가 모든 렌더링에서 100% 안정적으로 유지되어야 하는 이유입니다.

## 스냅샷 멘탈 모델: 상태가 상수인 이유

처음 시작했던 미스터리로 돌아가 봅시다.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    console.log(count); // 0이 출력됨!
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

이를 진정으로 이해하려면 `count`를 시간이 지남에 따라 변하는 변수라고 생각하는 것을 멈춰야 합니다.

대신 이 규칙을 이해하세요.

**컴포넌트의 어떤 단일 렌더링에서도, props와 state는 상수(constants)입니다.**

![상태 클로저 스냅샷 다이어그램](https://i.imgur.com/tzJNSfb.jpeg)

React가 컴포넌트 함수를 처음 호출할 때, 그것은 사실상 다음 코드를 실행하는 것과 같습니다.

```javascript
// 렌더링 #1
function Counter() {
  const count = 0; // 이 전체 실행 동안 고정된 상수!

  function handleClick() {
    setCount(0 + 1);
    console.log(0); // 말 그대로 0을 로깅합니다
  }

  return <button onClick={handleClick}>0</button>;
}
```

그 함수 호출 내에서 `count`는 `0`입니다. 그 특정 실행 내에서는 `0` 외에 다른 값일 수 없습니다.

`setCount(count + 1)`을 호출할 때, 여러분은 지역 `count` 변수를 변경하는 것이 아닙니다. `const`를 변경할 수는 없죠!

여러분은 React에게 이렇게 말하는 겁니다. *"이봐 React, 내 컴포넌트를 다시 실행할 때, `count` 값으로 `1`을 줘."*

React는 새로운 렌더링을 스케줄링합니다. 몇 밀리초 후 새로운 렌더링이 실행될 때, React는 `Counter()`를 다시 호출합니다. 하지만 이것은 완전히 새로운 함수 호출입니다.

```javascript
// 렌더링 #2 (새로운 함수 실행)
function Counter() {
  const count = 1; // 이 실행을 위한 고정된 상수!

  function handleClick() {
    setCount(1 + 1);
    console.log(1);
  }

  return <button onClick={handleClick}>1</button>;
}
```

모든 렌더링은 고유한 `count`, 고유한 이벤트 핸들러, 그리고 고유한 지역 스코프를 가집니다. 이것이 바로 JavaScript 클로저(closures)의 강력함입니다.

### 비동기 함정 (The Async Trap)

스냅샷을 이해하면 다음과 같은 버그를 즉시 이해할 수 있을 겁니다.

```jsx
function Chat() {
  const [message, setMessage] = useState("");

  function handleSend() {
    setTimeout(() => {
      alert("Sent message: " + message);
    }, 3000);
  }

  return (
    <div>
      <input value={message} onChange={e => setMessage(e.target.value)} />
      <button onClick={handleSend}>Send after 3 seconds</button>
    </div>
  );
}
```

이것을 시도해보세요.
1.  입력창에 `"Hello"`를 입력합니다.
2.  "Send after 3 seconds" 버튼을 클릭합니다.
3.  즉시 입력창 텍스트를 `"Goodbye"`로 변경합니다.
4.  알림이 뜰 때까지 기다립니다.

알림에는 무엇이라고 뜰까요?

`Sent message: Hello`라고 뜹니다.

왜일까요? `handleSend` 함수는 `message`가 `"Hello"`였던 렌더링 중에 생성되었기 때문입니다. `setTimeout` 콜백은 그 스냅샷을 클로저로 캡처(captured)했습니다. 화면의 입력창이 업데이트되었음에도 불구하고, 콜백은 버튼을 클릭한 순간의 상태 "사진"을 붙들고 있었던 겁니다.

만약 비동기 콜백 내부에서 리렌더링을 기다리지 않고 현재 "실시간" 값을 읽어야 하는 경우가 있다면, 정확히 그럴 때 `useRef`가 사용됩니다.

```jsx
const messageRef = useRef(message);
messageRef.current = message; // 항상 최신 값을 가리킴
```

## 컴포넌트가 리렌더링되는 이유: 폭포수(Cascade) 신화

다섯 명의 개발자에게 React 컴포넌트가 왜 리렌더링되는지 물어보면, 최소 세 명은 이렇게 답할 겁니다.

> *"컴포넌트의 props가 변경될 때 리렌더링됩니다."*

이것은 프론트엔드 개발에서 가장 흔한 신화 중 하나입니다.

한번 테스트해 봅시다.

```jsx
function Parent() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Increment</button>
      <ExpensiveChild />
    </div>
  );
}

function ExpensiveChild() {
  console.log("ExpensiveChild re-rendered!");
  return <p>I take 50ms to render.</p>;
}
```

`<ExpensiveChild />`는 **어떤 props도 받지 않습니다.** 상태도 없죠. 전달되는 어떤 것도 변경되지 않습니다.

`Parent` 컴포넌트의 "Increment" 버튼을 클릭합니다.

`ExpensiveChild`가 리렌더링될까요?

**네. 매번 리렌더링됩니다.**

![리렌더링 폭포수와 최적화 방법](https://i.imgur.com/3cxnByt.jpeg)

여기 React 렌더링의 진짜 규칙이 있습니다.

### 진짜 트리거 규칙 (The Real Trigger Rule)

컴포넌트는 다음 경우에만 리렌더링됩니다.

1.  **자신의 상태가 변경되었을 때** (`useState` 또는 `useReducer`를 통해)
2.  **구독하고 있는 Context가 변경되었을 때** (`useContext`를 통해)
3.  **부모 컴포넌트가 리렌더링되었을 때**

기본적으로 부모 컴포넌트가 리렌더링되면, React는 자신의 props가 변경되었는지 여부와 관계없이 **모든** 자식, 손자, 그리고 후손 컴포넌트들을 재귀적으로 리렌더링합니다.

React는 왜 이렇게 할까요? 대부분의 웹 앱에서 JavaScript 함수를 호출하여 몇 개의 가상 DOM 객체를 반환하는 데는 0.01밀리초밖에 걸리지 않기 때문입니다. React는 렌더링이 저렴하고 안전하다고 가정합니다.

실무에서 복잡한 컴포넌트 트리를 다루다 보면, 이렇게 불필요한 리렌더링 때문에 성능 저하를 겪는 경우가 참 많죠. 특히 큰 규모의 데이터나 무거운 연산을 처리하는 컴포넌트가 깊이 중첩되어 있을 때 이런 현상이 두드러집니다.

### `useMemo`를 과도하게 사용하지 않고 폭포수를 멈추는 방법

초보 개발자들은 자식 컴포넌트가 리렌더링되는 것을 보면 패닉에 빠져 즉시 모든 함수를 `useCallback`으로 감싸고 모든 컴포넌트를 `React.memo`로 감쌉니다.

그렇게 하기 전에, 훨씬 깔끔하고 내장된 기술인 **컴포넌트 조합(Component Composition)**을 살펴보세요.

다음 리팩토링된 코드를 보세요.

```jsx
// 1. 상태를 자체적인 작은 래퍼로 이동시킵니다.
function CounterContainer({ children }) {
  const [count, setCount] = useState(0);

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Increment: {count}</button>
      {children}
    </div>
  );
}

// 2. ExpensiveChild를 children prop으로 전달합니다.
function App() {
  return (
    <CounterContainer>
      <ExpensiveChild />
    </CounterContainer>
  );
}
```

`CounterContainer` 내에서 증분 버튼을 클릭하면, `CounterContainer`가 리렌더링됩니다.

**하지만 `ExpensiveChild`는 리렌더링되지 않습니다!**

왜일까요? `<ExpensiveChild />`는 `CounterContainer` 내부가 아닌 `App` 내부에서 생성되었기 때문입니다. `CounterContainer`에게 `children`은 레퍼런스가 변경되지 않은 (즉, `prevProps.children === nextProps.children`) 기존의 prop 객체일 뿐입니다. React는 동일한 객체 레퍼런스를 보고 전체 자식 서브트리 렌더링을 건너뜁니다!

`React.memo`도, `useCallback`도 필요 없습니다. 그저 깔끔한 컴포넌트 아키텍처만으로 해결되는 것이죠.

## 키(Key)가 중요한 이유: 리스트 Diffing 미스터리

React에서 입력창 목록을 렌더링하다가 첫 번째 항목을 삭제했는데, 입력했던 텍스트가 엉뚱한 줄에 남아있는 것을 본 적이 있으신가요?

```jsx
function TodoList() {
  const [items, setItems] = useState(['Buy milk', 'Walk dog', 'Read book']);

  function removeFirst() {
    setItems(items.slice(1));
  }

  return (
    <div>
      <button onClick={removeFirst}>Delete First</button>
      <ul>
        {items.map((item, index) => (
          // 나쁜 예: index를 key로 사용
          <li key={index}>
            <input defaultValue={item} />
          </li>
        ))}
      </ul>
    </div>
  );
}
```

"Delete First"를 클릭합니다.

"Buy milk"가 사라지고, 첫 번째 입력창에 "Walk dog"가 표시될 것으로 예상할 겁니다.

하지만 대신, 입력창은 여전히 "Buy milk"를 표시하고, 세 번째 입력창이 사라집니다!

![키가 중요한 이유: 리스트 Diffing에서 실제로 발생하는 일](https://i.imgur.com/dj9vzvK.jpeg)

왜 이런 일이 발생할까요?

React의 Diffing 알고리즘은 두 가지를 기준으로 자식 컴포넌트를 비교합니다. 바로 **요소 타입(Element Type)**과 **키(Key)**입니다.

배열 인덱스를 키로 사용하면 다음과 같습니다.

*   렌더링 1에서:
    *   키 `0` -> `Buy milk`
    *   키 `1` -> `Walk dog`
    *   키 `2` -> `Read book`

*   렌더링 2에서 ('Buy milk' 삭제 후):
    *   키 `0` -> `Walk dog`
    *   키 `1` -> `Read book`

React는 이전의 키 `0`과 새로운 키 `0`을 비교합니다. 둘 다 키 `0`을 가집니다. 둘 다 `<li><input /></li>`입니다.

React는 이렇게 말합니다. *"좋아! 키 0은 같은 요소잖아. 기존 DOM 노드와 그 내부 상태를 유지해야지."*

`<input />`는 로컬 브라우저 DOM 상태(입력했던 텍스트)를 가지고 있기 때문에, React는 기존 입력 상자를 유지하고 업데이트하지 않습니다. 그리고 React는 키 `2`를 살펴봅니다. 새로운 목록에는 키 `2`가 없으므로, React는 세 번째 DOM 노드를 삭제합니다!

제 경험상, 이 키 버그는 생각보다 흔하게 발생해서 개발자들을 당황하게 만듭니다. 특히 사용자 인터랙션이 많고 목록의 순서가 자주 바뀌는 경우, 잘못된 키 사용은 미묘하면서도 치명적인 UX 문제를 야기할 수 있죠.

### 키의 황금률 (The Golden Rule of Keys)

키는 그저 브라우저 콘솔의 노란색 React 경고를 잠재우기 위해 존재하는 것이 아닙니다.

**키는 렌더링 간에 컴포넌트의 지속적인 정체성(persistent identity)을 제공합니다.**

요소에 안정적이고 고유한 키(예: `key={item.id}`)를 부여하면:

1.  항목의 위치가 인덱스 0에서 인덱스 10으로 이동하더라도 React는 정확한 항목을 일치시킵니다.
2.  목록을 재정렬하는 것은 DOM 노드를 파괴하고 다시 생성하는 대신 단순히 이동시킵니다.
3.  컴포넌트 상태가 올바른 데이터 항목에 계속 연결됩니다.

## 25줄 코드로 나만의 미니 React 만들기

React의 핵심 아이디어가 얼마나 간단한지 직접 눈으로 보면, 멘탈 모델을 더욱 굳건히 할 수 있습니다.

지금 바로 브라우저의 개발자 콘솔(F12)을 열고, 다음 코드를 붙여넣은 후 Enter를 누르세요.

```javascript
// React의 상태 엔진에 대한 25줄짜리 멘탈 모델
const MiniReact = (() => {
  let hooks = [];
  let currentHook = 0;

  function useState(initialValue) {
    const hookIndex = currentHook;
    hooks[hookIndex] = hooks[hookIndex] !== undefined ? hooks[hookIndex] : initialValue;

    const setState = (newValue) => {
      hooks[hookIndex] = newValue;
      render(); // 리렌더링 트리거
    };

    currentHook++;
    return [hooks[hookIndex], setState];
  }

  function render(Component) {
    if (Component) MiniReact.activeComponent = Component;
    currentHook = 0; // 다음 렌더링 패스를 위해 포인터 재설정
    const output = MiniReact.activeComponent();
    console.log("Rendered UI:", output);
    return output;
  }

  return { useState, render };
})();

// 컴포넌트로 시도해보세요!
function MyComponent() {
  const [name, setName] = MiniReact.useState("Alex");
  const [count, setCount] = MiniReact.useState(0);

  return {
    text: `Hello ${name}, click count is ${count}`,
    click: () => setCount(count + 1),
    changeName: (n) => setName(n)
  };
}

// 초기 렌더링
let app = MiniReact.render(MyComponent);

// 버튼 클릭 시뮬레이션
app.click();

// 이름 변경 시뮬레이션
app.changeName("Sarah");
```

이 짧은 코드 조각에서 어떤 일이 일어났는지 주목하세요.

1.  `hooks`는 컴포넌트 외부에 값을 저장하는 단순한 배열입니다.
2.  `currentHook`은 모든 렌더링 패스 전에 0으로 재설정되는 인덱스입니다.
3.  `useState`를 호출하면 `hooks[currentHook]`에서 값을 읽고 인덱스를 증가시킵니다.
4.  `setState`를 호출하면 배열 항목을 업데이트하고 `render()`를 트리거합니다.

실제 React는 파이버 노드의 연결 리스트와 우선순위 큐, 동시성 스케줄링을 사용하지만, 근본적인 아키텍처는 이 25줄과 동일합니다.

마법은 없습니다. 그저 배열, 포인터, 그리고 함수들이 함수를 호출하는 것뿐입니다.

## 완벽한 React 멘탈 모델 치트 시트

다음은 즐겨찾기에 추가해둘 만한 빠른 참조표입니다.

| 질문               | 흔한 오해                                     | React가 실제로 하는 일                                         |
| :----------------- | :-------------------------------------------- | :------------------------------------------------------------- |
| **`setState`는 무엇을 하나요?** | DOM 변수를 직접 업데이트한다            | Fiber 큐에 업데이트를 추가하고 렌더링을 스케줄링한다           |
| **`console.log`가 왜 이전 값을 찍나요?** | 상태 업데이트가 느리거나 비동기적이다 | 상태는 해당 렌더링의 클로저 내부에서 상수 스냅샷이다           |
| **훅은 왜 조건부로 사용할 수 없나요?** | React가 변수명으로 훅을 검색한다      | 훅은 정렬된 연결 리스트로 저장된다; 하나를 건너뛰면 모든 인덱스가 손상된다 |
| **자식 컴포넌트는 언제 리렌더링되나요?** | 자신의 props가 변경될 때만            | 부모가 리렌더링될 때마다 (메모이제이션되거나 children으로 전달된 경우 제외) |
| **JSX가 반환하는 것은 무엇인가요?** | 실제 HTML DOM 요소                    | 순수 JavaScript 객체 (`React.createElement`)                   |
| **커밋 단계는 무엇인가요?** | 가상 DOM diff를 계산하는 것             | 계산된 DOM 변형을 브라우저에 동기적으로 쓰는 것                |
| **키가 왜 중요한가요?**   | 콘솔 경고를 없애기 위한 요구 사항     | React가 DOM 노드를 정확하게 재사용하도록 지속적인 정체성을 제공한다 |

## 마무리하며

React를 마법 같은 블랙박스로 여기는 것을 멈추고 그 밑에 깔린 기계적인 파이프라인을 이해하기 시작하면 모든 것이 달라집니다.

*   상태를 "동기화"하기 위해 방어적인 `useEffect` 체인을 작성하지 않게 됩니다.
*   `console.log`가 이전 값을 찍는 것에 더 이상 놀라지 않습니다.
*   컴포넌트가 언제, 왜 리렌더링되는지 정확히 알게 됩니다.
*   더 빠르고 버그가 적은 코드를 작성하게 됩니다.

다음번에 누군가 `setState`나 훅 에러 때문에 골머리를 앓는 것을 본다면, 미소를 지으며 이렇게 말해줄 수 있을 겁니다.

*"그건 마법이 아니에요. 그저 스냅샷과 연결 리스트일 뿐이죠."*
