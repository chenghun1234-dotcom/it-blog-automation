# Promise.all, 무턱대고 쓰다간 장애 터집니다: 무제한 동시성 제어가 API를 박살내는 이유

---
description: "Promise.all은 모든 비동기 작업을 동일한 이벤트 루프 틱에서 실행합니다. 무제한 동시성이 어떻게 429 폭탄을 유발하고, 유한한 워커 풀로 이를 해결하는 방법을 알아보세요."
---

새벽 2시 14분, 정기 결제 배치 작업이 1,200개의 고객 레코드에 대해 `await Promise.all(invoices.map(syncInvoice))`를 실행했습니다. 그리고 불과 400밀리초 만에, 결제 게이트웨이는 `429 Too Many Requests`를 반환했고, PostgreSQL은 커넥션 풀 타임아웃을 뿜어냈습니다. 결국 마지막 프로미스가 실패하면서 1,199건의 완료된 쓰기 작업은 고아 신세가 되어버렸죠.

대부분의 자바스크립트 및 타입스크립트 개발자들은 비동기 작업 배열을 더 빠르게 실행해야 할 때마다 [`Promise.all`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/all)을 습관적으로 찾습니다. 런타임이 알아서 작업을 책임감 있게 스케줄링해 줄 것이라고 가정하면서 말이죠. 하지만 런타임은 결코 그렇게 해주지 않습니다.

## `Array.map()`이 `Promise.all`을 트래픽 폭탄으로 만드는 방식

느린 순차적인 `for...of` 루프를 대체할 때, `Promise.all(ids.map(fetchUser))`처럼 ID 배열을 직접 매핑하는 것이 표준적인 '반사 신경'처럼 여겨집니다. 로컬 개발 환경에서 5개의 모의 레코드로 테스트할 때는 이 패턴이 깔끔해 보이고 모든 테스트를 통과합니다. 그러나 5,000개의 레코드를 처리하는 프로덕션 환경에서는 스스로를 향한 서비스 거부(DoS) 공격이 됩니다.

이 버그는 **동기화(synchronization)**와 **스케줄링(scheduling)**을 혼동하는 데서 비롯됩니다. `Promise.all`은 실행을 조절하거나 큐에 넣지 않습니다. `Array.prototype.map()`이 동기적으로 동작하기 때문에, Node.js는 모든 비동기 콜백을 이벤트 루프의 *정확히 동일한 틱*에서 호출합니다. `Promise.all`이 프로미스 배열을 받기도 전에, 런타임은 이미 5,000개의 동시 DNS 조회, TLS 핸드셰이크, 소켓 버퍼링, 데이터베이스 쿼리를 시작해버린 상태인 거죠. 제가 실무에서 비슷한 실수를 저질렀을 때, 개발 환경에서 완벽하던 코드가 배포 후 바로 429 에러로 폭발하는 걸 보고 등골이 오싹했던 경험이 있습니다.

## 무제한 동시성이 프로덕션 환경을 망가뜨리는 세 가지 방법

제가 수행한 수많은 프로덕션 감사에서, 이 '무제한 프로미스 배열'을 발사하는 패턴은 항상 세 가지 연쇄적인 장애 모드를 유발했습니다.

*   **하위 시스템의 병목 현상 (Downstream Thundering Herd):** 외부 API는 엄격한 비율 제한(rate limit)을 적용하며, 관계형 데이터베이스는 일반적으로 10개에서 50개 사이의 커넥션 풀을 가집니다. 1,000개의 동시 요청을 한 번에 열면 풀이 즉시 포화 상태가 되어 다른 중요한 엔드포인트들의 요청 처리까지 막아버립니다. 실제로 현업에서, 개발팀이 데이터베이스 커넥션 풀을 고려하지 않아 터지는 장애가 가장 흔했습니다.
*   **실패-빠른 고아 부작용 (Fail-Fast Orphaned Side Effects):** `Promise.all`은 *하나의* 프로미스라도 실패하는 즉시 거부(reject)되지만, 자바스크립트 프로미스는 자동으로 취소되지 않습니다. 남아있는 999개의 HTTP 호출과 데이터베이스 변경 작업은 백그라운드에서 계속 상태를 변경하며 완료를 기다리는 주체 없이 방치됩니다.
*   **V8 힙 및 GC 정지 (V8 Heap and GC Stalls):** 수천 개의 원시 응답 스트림과 파싱된 JSON 페이로드를 동시에 버퍼링하면 메모리가 급격히 치솟아, 전체 시스템을 멈추는(stop-the-world) 가비지 컬렉션(GC) 일시 정지를 유발하거나 컨테이너의 OOM(Out Of Memory) 킬을 초래할 수 있습니다.

## 유한한 워커 풀로 활성 프로미스 제한하기

재현 가능한 벤치마크로 그 차이를 측정하기 위해, 하위 서비스에 대해 200개의 시뮬레이션된 50ms 요청을 실행했습니다. 이 서비스는 **10개의 동시 커넥션**으로 제한되어 있었고(10개를 초과하면 `HTTP 429` 반환). 무제한 `Promise.all`은 52ms 만에 실패했으며, 완료된 작업은 0개였습니다. 반면, 유한한 워커 풀은 모든 200개 작업을 1,045ms 만에 완료했습니다. 이는 순차 루프보다 거의 10배 빠르며, 단 하나의 요청도 드롭하지 않았습니다.

모든 작업을 한 번에 실행하는 대신, `N`개의 경량 워커를 생성하여 공유 인덱스에서 작업을 가져오고, 치명적인 오류 발생 시 큐에 있는 작업을 중지하기 위해 [`AbortController`](https://developer.mozilla.org/en-US/docs/Web/API/AbortController)를 연결하는 방법을 사용할 수 있습니다.

```typescript
export async function mapWithConcurrency<T, R>(
  items: readonly T[],
  limit: number,
  workerFn: (item: T, signal: AbortSignal) => Promise<R>
): Promise<R[]> {
  const results = new Array<R>(items.length);
  const controller = new AbortController();
  let cursor = 0;
  const workers = Array.from({ length: Math.min(limit, items.length) }, async () => {
    while (!controller.signal.aborted) {
      const index = cursor++;
      if (index >= items.length) break;
      try {
        results[index] = await workerFn(items[index], controller.signal);
      } catch (err) {
        controller.abort(err);
        throw err;
      }
    }
  });
  await Promise.all(workers);
  return results;
}
```

하나의 실패가 전체 배치를 중단해서는 안 되는 독립적인 레코드들을 동기화할 때는 `workerFn` 내부에서 오류를 `catch`하고 `{ status: "fulfilled" | "rejected" }` 객체를 반환하세요. 이는 동시성 제한을 유지하면서도 [`Promise.allSettled`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/allSettled)와 유사하게 동작합니다.

{% details 배열을 고정된 청크로 분할하는 것이 여전히 처리량을 낭비하는 이유 %}
배열을 10개씩 청크로 분할하고 루프에서 `Promise.all(chunk)`를 기다리면 429 에러는 방지할 수 있습니다. 하지만 이는 **선두 블로킹(head-of-line blocking)**을 유발합니다. 9개의 빠른 20ms 요청이 다음 배치 작업이 시작되기 전에 1개의 느린 900ms 이상치 요청을 기다리며 유휴 상태에 빠지게 됩니다. 공유 워커 풀은 큐가 소진될 때까지 모든 10개의 슬롯을 지속적으로 채워 처리량을 극대화합니다.

## 올바른 동시성 전략 선택하기

| 전략                         | 최대 동시 요청 수 | 200개 태스크 벤치마크        | 실패 동작                                | 최적의 사용 사례                                |
| :--------------------------- | :---------------- | :--------------------------- | :--------------------------------------- | :---------------------------------------------- |
| `Promise.all(items.map(...))` | 무제한 (`N`)      | 약 52ms에서 실패 (`HTTP 429`) | 인플라이트 작업 중단 없이 실패-빠른 종료 | 2~5개의 독립적인 고정 튜플 호출                 |
| `Promise.allSettled(items.map(...))` | 무제한 (`N`)      | 200개 연결까지 급증 (`HTTP 429`) | 모든 작업 대기; 여전히 하위 시스템 과부하      | 부분적 오류를 허용하는 작고 고정된 튜플         |
| 순차 `for...of`              | 1                 | 10,180ms (100% 성공)         | 첫 번째 오류 발생 시 중단                  | 엄격한 순서 보장 또는 취약한 단일 스레드 API   |
| 유한 워커 풀 (`limit = 10`) | `10`              | 1,045ms (100% 성공)          | `AbortSignal`을 통해 남은 큐 중단        | 동적 배열, DB 배치, 외부 API 동기화           |

## 핵심 요약

`Promise.all`은 사용자 프로필, 권한, 기능 플래그와 같이 API 요청 중 로드해야 하는 작고 고정된 이기종(heterogeneous) 호출 튜플을 기다릴 때 잘 작동합니다. 하지만 입력이 길이가 알려지지 않은 동적 배열이 되는 순간, `.map()`을 `Promise.all`로 감싸는 것은 안정성 측면에서 큰 위험을 초래합니다. 동시성을 명시적으로 제한하여 하위 서비스를 압도하지 않으면서도 높은 처리량을 유지하세요.

무제한 `Promise.all`이 데이터베이스 풀이나 비율 제한 API에 부딪혔을 때 프로덕션에서 어떤 종류의 장애 모드를 겪으셨나요? 댓글로 경험을 공유해 주세요!
