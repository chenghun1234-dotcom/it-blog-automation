## ⭐ 50별은 제게 어떤 의미였을까?

50별 당시, 제가 가장 보여주고 싶었던 건 [`is-kit`](https://github.com/nyaomaru/is-kit)이 단순히 장난감 프로젝트가 아니라는 점이었습니다. 이미 실제 프로덕션 애플리케이션에서 활발히 사용되고 있었거든요. 🚀

해당 애플리케이션에서는 다음과 같은 런타임 체크가 반복적으로 발생하고 있었습니다.

```ts
typeof value === "string";
typeof value === "number";
value === null || value === undefined;
```

HTTP 에러, 리터럴 유니온, 배열, API 값, 일반 객체 같은 것들을 위한 여러 사용자 정의 타입 가드도 있었죠.

여기서 흥미로웠던 점은 `is-kit`이 이러한 체크를 **더 짧게 만들어준다는 것만이 아니었습니다**. 핵심은 `is-kit`이 이 모든 체크에 **재사용 가능한 하나의 형태**를 제공했다는 것이었죠. 작은 가드들을 조합할 수 있었고, 애플리케이션 고유의 헬퍼들이 라이브러리와 피처 코드 사이에 유기적으로 자리 잡을 수 있었습니다. 그리고 그 결과물은 여전히 일반적인 TypeScript 제어 흐름에 완벽하게 참여할 수 있었죠.

이 부분은 지금도 변함이 없습니다. 솔직히 50별 당시에는 제 라이브러리가 실전에서 얼마나 유용하게 쓰일 수 있는지 보여주고 싶다는 마음이 컸죠. 하지만 50별 이후, `is-kit` 라이브러리 자체는 꽤 많이 진화했습니다. 👀

## 🔑 속성 정제(Property Refinement)가 일등 사용 사례가 되다

제가 계속해서 마주쳤던 한 가지 시나리오가 있었습니다.

> 이미 잘 작동하는 타입 가드가 있는데, 이걸 객체의 **특정 속성에만 적용하고 싶다.**

예를 들어볼까요?

```ts
declare const input: unknown;
```

`isString`으로 문자열을 검증하는 방법은 이미 잘 알고 있습니다.

```ts
import { isString } from "is-kit";
```

하지만 이제 "이 객체는 `name`이라는 속성을 가지고 있고, 그 `name` 속성은 문자열이다"라는 로직을 표현하고 싶습니다.

간단해 보이지만, 실제로는 몇 가지 다른 케이스가 존재합니다. 필수 속성은 선택적 속성과 **다르고**, 배열 인덱스는 객체 속성과 **다릅니다**. 그리고 '정의된 것으로 알려진' 선택적 속성은 '여전히 선택적인' 속성과 **다른 방식으로 내로잉되어야 하죠**.

그래서 `is-kit`은 세 가지 속성 정제 헬퍼를 추가했습니다.

-   `refineKey`
-   `refineDefinedKey`
-   `refineIndex`

아이디어는 간단합니다.

> **이미 신뢰하는 타입 가드를 가져와서, 이를 특정 속성이나 배열 요소에 적용하는 것.**

예를 들어, 이렇게요.

```ts
import { isString, refineKey } from "is-kit";

const hasStringName = refineKey("name", isString);
```

이제 `isString` 가드는 다른 커스텀 조건자 안에 재작성될 필요 없이, 더 깊은 수준에서 재사용될 수 있습니다. 제가 개인적으로도 이런 패턴을 자주 사용하면서 느꼈던 갈증이었는데, `is-kit`으로 해결하고 나니 코드가 훨씬 깔끔해지더군요.

이 API는 작지만, `is-kit`의 나머지 부분과 동일한 설계 목표를 따르기 때문에 제가 특히 아끼는 기능입니다. 거대한 하나의 검증기를 만드는 대신, **작고 재사용 가능한 체크들을 만들어 일반 TypeScript 코드에서 활용하는 것**이 핵심이죠.

## 🔍 `discriminatedUnion`이 훨씬 더 강력해지다

50별 이후 가장 큰 추가 사항은 아마 `v1.15.0`에서 소개된 완전한 판별 유니온(discriminated union) API일 것입니다.

흔히 사용되는 TypeScript 타입을 생각해봅시다.

```ts
type Result = { ok: true; value: string } | { ok: false; error: string };
```

런타임에 이 타입을 검증하는 것은 어렵지 않습니다. `ok` 필드를 확인한 다음, 해당 필드에 따라 관련 필드들을 검증하면 되죠.

하지만 또 다른 질문이 있습니다.

> TypeScript가 검증기 자체가 유니온 전체를 커버하는지 **확인해줄 수 있을까?**

바로 여기서 `discriminatedUnion`이 등장합니다.

```ts
import { discriminatedUnion, isString, oneOfValues, typedStruct } from "is-kit";

type Result = { ok: true; value: string } | { ok: false; error: string };

const resultUnion = discriminatedUnion<Result>();

export const isResult = resultUnion("ok", [true, false], {
  true: typedStruct<Extract<Result, { ok: true }>>()({
    ok: oneOfValues(true),
    value: isString,
  }),
  false: typedStruct<Extract<Result, { ok: false }>>()({
    ok: oneOfValues(false),
    error: isString,
  }),
});
```

런타임 동작도 유용하지만, 더 흥미로운 부분은 컴파일 타임 계약입니다. 이 빌더는 다음과 같은 것들을 체크합니다.

-   누락된 판별 브랜치
-   불필요한 브랜치
-   호환되지 않는 브랜치 가드
-   불완전한 판별 튜플

따라서 유니온 타입이 변경되더라도, 가드가 소리 없이 불완전한 상태로 남지 않도록 합니다.

이 점은 매우 중요합니다. 수동으로 작성된 타입 가드가 위험해지는 가장 쉬운 방법 중 하나는 '정합성 불일치'거든요. TypeScript 타입은 진화하는데 런타임 가드는 그대로 남아있는 거죠. 그리고 컴파일러는 일반적으로 두 가지가 더 이상 일치하지 않는다고 알려주지 못합니다. `discriminatedUnion`은 이러한 종류의 실수를 어렵게 만들기 위한 한 가지 시도입니다. 이 기능은 특히 복잡한 비즈니스 로직에서 발생하는 수많은 상태들을 다룰 때 빛을 발했습니다. 팀원들과 제가 실수로 특정 케이스를 누락하는 것을 컴파일러가 잡아주니, 휴먼 에러를 확실히 줄일 수 있었죠.

## 💪 라이브러리도 더욱 엄격해지다

50별과 100별 사이의 모든 개선 사항이 새로운 기능 추가만은 아니었습니다. 많은 작업이 기존 동작을 더 정밀하게 만드는 데 집중되었습니다.

예를 들어, 최근 릴리즈에는 다음 사항에 대한 수정이 포함되었습니다.

-   `recordOf` 리터럴 키 내로잉
-   네이티브 `Error` 브랜드 체크
-   오버라이드된 이터레이터가 있는 배열 가드
-   정확한 `struct` 유효성 검사
-   심볼 키 기반 구조체 스키마
-   크로스-렐름 구조체 스키마

또한, 패키지 레벨 테스트도 더욱 강화되었습니다. `is-kit`은 이제 ESM 및 CommonJS TypeScript 소비자 모두의 발행된 패키지 동작을 확인하며, `Deno` / `JSR` 스모크 테스트 커버리지도 확보했습니다.

이 부분은 코드 스니펫으로 보여주기에는 덜 흥미로울 수 있습니다. 하지만 작은 라이브러리일수록 이런 부분은 기본 중의 기본이라고 생각합니다. 다양한 JS/TS 환경에서 '제대로' 작동하는지가 곧 '진짜' 가치를 증명하는 거니까요.

## 🤖 다른 오픈소스 프로젝트에서도 `is-kit`을 활용하기 시작하다

50별에 도달한 이후, 저는 제가 관리하는 다른 오픈소스 프로젝트에서도 `is-kit`을 더욱 자연스럽게 사용하기 시작했습니다.

예를 들어, 제 체인지로그 도구인 [`changelog-bot`](https://github.com/nyaomaru/changelog-bot)에서는 `define`을 사용하여 작은 조건자들을 재사용하고 조합 가능하게 만듭니다. 모든 런타임 체크를 독립적인 헬퍼로 만들 필요 없이요.

간단히 예를 들면 다음과 같습니다. 👇

```ts
import { define, oneOfValues } from "is-kit";

const CHANGELOG_SECTIONS = ["Added", "Changed", "Fixed", "Removed"] as const;

const isChangelogSection = define<(typeof CHANGELOG_SECTIONS)[number]>(
  oneOfValues(CHANGELOG_SECTIONS),
);
```

정확한 코드가 중요한 것은 아닙니다. 제게 변화가 있다면, 더 이상 "이 라이브러리를 써야겠어"라고 생각하지 않는다는 점입니다. 그냥 필요한 가드를 자연스럽게 사용하게 되죠. 라이브러리가 더 이상 '내가 만든 데모 프로젝트'가 아니라 '정말 필요한 도구'처럼 느껴지기 시작한 거죠. 그 순간부터 개발자에게 진정으로 유용한 라이브러리가 됩니다.

## 🚀 `is-kit` 가드가 `Effect`의 타입 버그를 만나다

이것은 최근 일어난 일들 중 가장 흥미로운 사건 중 하나였습니다.

어떤 `is-kit` 사용자가 `Effect`의 `catchIf`와 함께 `is-kit` 타입 가드를 사용하고 있었습니다. 개념적으로, 그 정제(refinement)는 다음과 같았습니다. 👇

```ts
(error: unknown): error is SomeError => ...
```

이는 `is-kit`에게는 완전히 정상적인 패턴입니다. 사실 `unknown`은 `is-kit` 라이브러리가 시작하도록 설계된 지점과 정확히 일치하죠.

하지만 `Effect.catchIf`와 함께 사용될 때, 이 정제는 예상치 못한 방식으로 제네릭 추론에 영향을 미칠 수 있었습니다. 에러 채널이 `unknown`으로 확장될 수 있었던 것이죠.

이 보고된 케이스는 [`Effect` PR](https://github.com/Effect-TS/effect/pull/9252)로 이어졌고, 성공적으로 머지되었습니다! 👏 🚀

{% embed https://github.com/Effect-TS/effect/pull/9252 %}

관련 타입은 원래 대략 다음과 같았습니다.

```ts
refinement: Predicate.Refinement<E, EB>;
```

그리고 수정 후에는 이렇게 바뀌었습니다.

```ts
refinement: Predicate.Refinement<NoInfer<E>, EB>;
```

여기서 중요한 아이디어는 **정제의 입력 타입이 `Effect`에 의해 이미 확립된 에러 타입을 재정의하는 것을 허용해서는 안 된다**는 것입니다.

해당 PR은 또한 다음과 같은 케이스에 대한 타입 테스트를 추가했습니다.

```ts
const result = Effect.catchIf(
  mixedEffect,
  (e: unknown): e is AiError => e instanceof AiError,
  () => Effect.succeed("ok"),
);
```

수정 전에는 정제 입력이 추론에 참여하여 에러 채널을 확장할 수 있었습니다. `NoInfer`를 사용함으로써, 원래의 에러 타입이 진리의 원천으로 유지됩니다.

동일한 패턴이 `Channel`과 `Stream`에서도 수정되었습니다.

이 이슈에 대한 [Bluesky 게시물](https://bsky.app/profile/evadeva.bsky.social/post/3mxwiqfeo3s2j)도 있었습니다.

이 버그는 정말 흥미로웠습니다. 제가 `is-kit`만 단독으로 테스트했다면 절대 발견할 수 없었을 상호작용이었으니까요. `is-kit`이 `Effect`를 망가뜨린 것도 아니었고, `Effect`가 이상하게 동작한 것도 아니었습니다. 제네릭 API와 의도적으로 넓은 입력 타입을 가진 리파인먼트 사이에서 발생한 미묘한 TypeScript 추론 문제였죠. 라이브러리들이 실제 코드에서 서로 만나기 시작할 때 발생하는 '진짜' 엣지 케이스라고 할 수 있습니다. 이런 피드백은 개발자로서 정말 값지죠.

## 👍 이런 피드백이 바로 제가 원했던 것입니다

`is-kit`이 50별에 도달했을 때, 저는 "누군가 이 아이디어가 유용하다고 생각했군"이라고 썼습니다. 그것만으로도 충분히 기뻤죠.

100별이 되었다고 해서 이 라이브러리가 거대해졌다는 의미는 아닙니다.
별점은 여전히 벤치마크가 아닙니다.
여전히 정확성을 증명하는 것도 아니죠.
그리고 모든 TypeScript 프로젝트가 `is-kit`을 설치해야 한다는 의미도 절대 아닙니다.

하지만 분명히 무언가 달라졌습니다.

사람들은 이제 단순히 저장소에 별을 누르는 것 이상을 하고 있습니다. 그들은:

-   라이브러리를 사용하고
-   질문을 하고
-   엣지 케이스를 발견하고
-   버그를 보고하고
-   다른 유효성 검사 접근 방식과 비교하며
-   다른 TypeScript 라이브러리와 함께 가드를 사용하고
-   제가 이미 완성되었다고 생각했던 API들을 다시 고민하게 만듭니다.

이 모든 것이 숫자 자체보다 훨씬 더 값진 의미를 가집니다. 💖

## 💬 프로젝트를 설명하기도 더 쉬워졌다

50별과 100별 사이에서 또 다른 변화가 있었습니다.

저는 `is-kit`이 **아닌 것**에 대해 훨씬 더 명확해졌습니다.

`is-kit`은 모든 스키마 라이브러리를 대체하려 하지 않습니다.
모든 런타임 값을 스키마 우선 워크플로로 바꾸려 하지도 않습니다.
그리고 일반 TypeScript 제어 흐름을 숨기려 하지도 않습니다.

핵심 질문은 여전히 매우 작습니다.

> **"이 `unknown` 값이 이 브랜치에 안전하게 진입할 수 있는가?"**

때로는 `Zod`, `Valibot`, `ArkType` 등 스키마 라이브러리가 정답일 때도 있습니다. 예를 들어, 다음과 같은 상황에서는 말이죠.

-   풍부한 유효성 검사 오류가 필요할 때
-   데이터 변환이 필요할 때
-   폼 유효성 검사를 해야 할 때
-   시스템 간 공유되는 계약이 필요할 때

하지만 때로는 이미 일반 TypeScript 코드를 가지고 있고, 단순히 재사용 가능한 내로잉 함수만 필요할 때가 있습니다. 바로 이 지점에서 `is-kit`이 유용하기를 바랍니다.

```ts
if (isUser(value)) {
  value.id;
}

if (isHttpClientError(error)) {
  // HTTP 클라이언트 에러 처리
}

items.filter(isString);

result.catch(isHttpClientError);

const isMaybeNumber = nullish(isNumber);
```

작은 런타임 결정.
일반 함수.
일반 TypeScript.

## 🐱 100별이 저에게 의미하는 것

가장 큰 TypeScript 오픈소스 프로젝트들과 비교하면 100별은 여전히 작은 숫자입니다. 괜찮습니다.

저에게 중요한 것은 이 프로젝트가 별점 카운터와는 전혀 상관없는 방식으로 '진짜'가 되어가고 있다는 점입니다. 50별 이정표 이후로:

-   새로운 API가 추가되었고
-   기존 API가 더욱 엄격해졌으며
-   런타임 엣지 케이스가 수정되었고
-   패키지 호환성 테스트가 개선되었으며
-   저 자신이 `is-kit`을 다른 오픈소스 프로젝트에 자연스럽게 사용하기 시작했고
-   외부 사용자가 저 혼자서는 생성할 수 없었던 피드백을 제공했고
-   심지어 `unknown` 기반의 정제가 `Effect`의 추론 엣지 케이스를 드러내는 데 일조했습니다.
