# 당신은 웹 개발자인가, 브라우저 전문가인가? 서버에 사진 한 장 안 올리는 AI 포토 에디터 만들다 깨달은 7가지 통찰

**설명**: 장치 내 AI, WASM 스레드, 목표 크기 압축, 인페인팅, 그리고 3D LUT까지! 이 모든 걸 단 하나의 HTML 파일에 담아낸 'APIC Web'을 개발하며 얻은 7가지 실전 교훈을 공유합니다.

---

대부분의 웹 개발자는 폼을 만들고, API를 호출하고, `div`를 중앙에 배치하는 정도는 식은 죽 먹기죠. 하지만 '브라우저 전문가'는 한 차원 다릅니다. 이들은 브라우저가 **고집스럽게 거부하는** 것들, 노트북이 아닌 **모바일 환경**에서 벌어지는 예상 밖의 일들, 그리고 심지어 **서버 없이**도 진정한 소프트웨어를 어떻게 배포할 수 있는지 꿰뚫고 있죠.

저 역시 'APIC Web'이라는 무료 사진 편집기, 배경/객체 제거기, 변환기, 압축기를 만들면서 제가 어느 쪽에 더 가까운지 명확히 깨달았습니다. APIC Web의 핵심은 **사용자의 사진이 절대 기기를 벗어나지 않는다**는 점이에요. 업로드 대기열도, 백엔드도 없이, 모든 기능이 GitHub Pages에 호스팅된 단 하나의 HTML 파일 안에서 작동합니다.

아래의 각 테스트는 APIC Web을 만들면서 실제로 마주했던 버그나 설계 결정에서 나온 교훈들입니다. 솔직하게 점수를 매겨보세요. 👇

## 테스트 1: AI 작업이 모바일에서 조용히 멈추는 이유는?

APIC은 ONNX Runtime Web(WebAssembly)을 이용해 브라우저에서 AI 모델을 실행합니다. 여기서 멀티 스레드 WASM을 사용하려면 `SharedArrayBuffer`가 필요한데, 이 친구는 COOP/COEP 같은 특별한 응답 헤더를 요구합니다. GitHub Pages 같은 일반적인 정적 호스트는 이런 헤더를 보내지 않으니 `crossOriginIsolated`는 `false`가 되죠.

데스크톱 환경에서는 런타임이 보통 유연하게 처리되지만, 모바일에서는 그렇지 않은 경우가 많습니다. AI 작업이 그냥 에러도 없이 멈춰버리는 끔찍한 상황이 발생하는 거죠. 저도 이 문제를 겪으면서, '데스크톱에서 잘 되는데 뭐'라고 안일하게 생각하기 쉽지만, 실제 사용자 경험은 모바일에서 판가름 난다는 걸 뼈저리게 느꼈습니다. 결국 우회적인 처리 방식에 의존하는 것을 멈춰야 했습니다.

```js
// Static hosts can't send COOP/COEP, so threads aren't available.
// Force the one configuration that behaves the same everywhere.
ort.env.wasm.numThreads = 1;
ort.env.wasm.proxy = false;

const session = await ort.InferenceSession.create(modelBytes, {
  executionProviders: ['wasm'],
  enableCpuMemArena: false,
  enableMemPattern: false,
});
```

헤더 사용이 가능한 환경에서는 APIC이 `self.crossOriginIsolated`를 확인한 뒤에야 여러 스레드를 요청합니다.

**일반 개발자**: "내 노트북에서는 잘 작동하는데?"
**브라우저 전문가**: "부드럽게 대체된다"는 말은 실제로 휴대폰에서 테스트해야 하는 주장이지, 맹목적으로 믿을 약속이 아님을 정확히 압니다.

## 테스트 2: 느린 다운로드와 끊긴 다운로드를 구분할 수 있는가?

APIC의 AI 모델들은 용량이 꽤 큽니다. 배경 제거용으로 5MB(Lite), 44MB(Fast), 176MB(Maximum)이고, 고품질 객체 제거 모델은 약 208MB에 달하죠. 만약 30초 고정 타임아웃을 설정한다면, 느린 휴대폰 연결에서는 모든 작업이 취소될 겁니다.

그래서 APIC은 **정지 기반 타임아웃**을 사용합니다. 즉, **40초 동안 아무런 바이트도 전송되지 않을 때만** 중단시키는 방식이죠. 좋지 않은 Wi-Fi 환경에서 거대한 모델을 다운로드하는 데 시간이 오래 걸려도 기다려줍니다. 반면, 아예 끊긴 연결은 가차 없이 차단하죠. 다운로드된 모델은 Cache API에 저장되어 다음 실행 시에는 즉시 로드됩니다. 이런 상황을 겪으면서, 단순히 '타임아웃'만 걸 것이 아니라 사용자의 연결 상태를 고려한 '기다림'의 미학이 중요하다고 생각했어요.

```js
const CACHE = 'apic-models-v1';
const cache = await caches.open(CACHE);

let hit = await cache.match(url);
if (hit) return hit.arrayBuffer();           // cached: no download

const bytes = await downloadWithStallTimeout(url);   // abort only if the stream goes quiet
await cache.put(url, new Response(bytes));   // wrapped in try/catch: private mode & quota can fail
return bytes;
```

만약 모델 로딩에 실패하더라도, APIC은 완전히 실패하는 대신 울트라(LaMa) → MI-GAN → 간단한 패치 채우기 순으로 **단계적으로 기능을 낮춰** 대체합니다.

**일반 개발자**: 타임아웃을 적용한 `fetch()`를 사용합니다.
**브라우저 전문가**: 진행 상황을 측정하고, 결과를 캐시하며, 항상 플랜 B를 준비합니다.

## 테스트 3: 추측 없이 앱 용량을 '200KB 미만'으로 맞출 수 있는가?

이미지 업로드 폼에는 "최대 200KB"와 같은 제한이 있고, 사용자들은 품질 슬라이더를 이리저리 움직이며 "대충 이 정도면 되겠지?" 하고 품질 '룰렛 게임'을 합니다. APIC의 압축 도구는 이런 추측 대신 JPEG 품질에 대해 **이진 탐색**을 수행합니다. 제가 예전에 이미지 압축 기능을 만들 때는 그저 '품질 0.7'로 고정하고 기도하는 심정이었는데, 이진 탐색을 적용하니 사용자 만족도가 훨씬 높아졌죠.

```js
async function findQualityForTarget(canvas, targetBytes) {
  let lo = 0.05, hi = 0.98, best = null;
  for (let i = 0; i < 7; i++) {
    const mid = (lo + hi) / 2;
    const blob = await toBlob(canvas, 'image/jpeg', mid);
    if (blob.size <= targetBytes) { best = { blob, q: mid }; lo = mid; }  // fits: try higher quality
    else { hi = mid; }                                                   // too big: go lower
  }
  return best;
}
```

7번의 인코딩 시도를 통해 목표 크기에 맞는 가장 높은 품질을 찾아냅니다. 만약 가장 낮은 품질로도 너무 크다면, APIC은 이미지를 약 20% 축소한 뒤 다시 이진 탐색을 시도합니다(최대 8번). 그래도 안 되면, 가짜로 성공한 척하는 대신 **실제 크기를 사용자에게 알려줍니다.**

**일반 개발자**: `quality = 0.7`로 설정하고 운에 맡깁니다.
**브라우저 전문가**: 추측을 탐색으로 바꾸고, 불가능할 때는 솔직하게 '불가능하다'고 말합니다.

## 테스트 4: 투명한 PNG가 JPEG로 변환하면 왜 검은색으로 변할까?

JPEG는 알파 채널을 지원하지 않습니다. 투명한 픽셀이 있는 캔버스를 JPEG로 인코딩하면, 그 투명한 부분은 **검은색**으로 나오게 됩니다. 배경 제거 작업(많은 투명 영역을 생성하는) 후에 이런 현상이 발생하면 정말 불쾌한 서프라이즈가 아닐 수 없죠.

해결책은 간단합니다. 먼저 흰색으로 채우고, 그 위에 이미지를 그리는 거죠. 저도 초창기에는 이 부분에서 몇 번이나 뒤통수를 맞았던 기억이 있습니다. '캔버스에 그렸으니 다 되겠지' 하는 막연한 생각이 이런 실수를 낳더군요.

```js
function flattenToWhite(src) {
  const out = document.createElement('canvas');
  out.width = src.width; out.height = src.height;
  const ctx = out.getContext('2d');
  ctx.fillStyle = '#fff';
  ctx.fillRect(0, 0, out.width, out.height);
  ctx.drawImage(src, 0, 0);
  return out;
}
```

APIC은 변환 패널에서 PNG, WebP처럼 투명도를 유지하는 형식과 그렇지 않은 형식을 명확하게 알려줍니다.

**일반 개발자**: 캔버스는 단순히 픽셀의 집합이라고 생각합니다.
**브라우저 전문가**: 모든 출력 형식이 알파 채널에 대한 규칙을 가지고 있음을 이해합니다.

## 테스트 5: 전체 이미지를 처리하는가, 아니면 변경된 부분만 처리하는가?

객체 제거는 인페인팅 모델(푸리에 컨볼루션 네트워크 기반의 LaMa 또는 경량 MI-GAN)을 실행하는 것을 의미합니다. LaMa는 고정된 **512×512** 창에서 작동하므로, 12메가픽셀 사진 전체를 넣으면 느리고 흐릿한 결과가 나옵니다.

APIC은 사용자가 브러시로 칠한 **영역 주변만** 처리합니다. 무작정 큰 이미지를 통째로 돌리는 것보다, 문제의 범위를 좁히고 정교하게 처리하는 것이 성능과 사용자 경험 두 마리 토끼를 잡는 지름길임을 다시 한번 깨달았습니다.

1.  마스크 주변 영역을 가져옵니다(사진이 허용하는 한 최소 512 네이티브 픽셀).
2.  해당 크롭 영역에만 모델을 실행합니다.
3.  박스 블러로 가장자리를 부드럽게 하고, 채워진 부분이 주변과 색상이 일치하도록 조정한 다음, "너무 깔끔해 보이지 않도록" 필름 그레인을 다시 추가합니다.
4.  원본 이미지에 다시 붙여넣습니다.

작은 편집은 작은 연산으로 처리하여, 사진의 나머지 부분은 **손상되지 않은 채**로 유지됩니다.

**일반 개발자**: 모델을 전체 이미지에 실행합니다.
**브라우저 전문가**: 먼저 문제의 범위를 축소하고, 결과물을 다시 매끄럽게 블렌딩하여 아무도 그 이음새를 눈치채지 못하게 합니다.

## 테스트 6: 전체 색상 보정을 `.cube` LUT 파일로 내보낼 수 있는가?

APIC은 커브, 8밴드 HSL 믹서, 3방향 색상 보정 기능을 제공합니다. 사용자들은 이 보정 내용을 DaVinci Resolve나 Premiere 같은 다른 전문 편집 소프트웨어에서도 사용하고 싶어 했습니다. `.cube` 파일은 3D 룩업 테이블(LUT)로, 모든 입력 색상에 대해 어떤 출력 색상이 나와야 하는지를 정의합니다.

여기서 핵심 트릭은 이렇습니다. 파이프라인을 역공학적으로 분석할 필요가 없어요. 대신 **항등 격자(identity grid)** 형태의 색상들을 동일한 픽셀 함수에 통과시키고, 어떤 결과가 나오는지 기록하기만 하면 됩니다. 이 기능을 구현하면서 개발자가 로직을 역추적하는 것보다, 실제 함수를 샘플링하는 것이 훨씬 우아하고 정확한 해결책임을 배웠죠.

```js
const N = 33;                       // 33×33×33 lattice
const buf = new Uint8ClampedArray(N * N * N * 4);
let i = 0;
for (let b = 0; b < N; b++)
  for (let g = 0; g < N; g++)
    for (let r = 0; r < N; r++) {   // red changes fastest, as .cube requires
      buf[i++] = Math.round(r / (N - 1) * 255);
      buf[i++] = Math.round(g / (N - 1) * 255);
      buf[i++] = Math.round(b / (N - 1) * 255);
      buf[i++] = 255;
    }

processPixels(buf, gradeWithoutSpatialEffects);   // same code that edits your photo

const lines = ['TITLE "APIC grade"', 'LUT_3D_SIZE 33',
               'DOMAIN_MIN 0.0 0.0 0.0', 'DOMAIN_MAX 1.0 1.0 1.0', ''];
for (let j = 0; j < buf.length; j += 4)
  lines.push(`${(buf[j]/255).toFixed(6)} ${(buf[j+1]/255).toFixed(6)} ${(buf[j+2]/255).toFixed(6)}`);
```

한 가지 주의할 점은 LUT는 **색상** 관련 작업만 담을 수 있다는 것입니다. 선명도(Clarity), 샤프닝, 비네팅, 그레인 같은 기능은 주변 픽셀에 의존하기 때문에 제외되며, APIC UI에서도 이 점을 명시합니다.

**일반 개발자**: 보정된 화면을 스크린샷으로 내보냅니다.
**브라우저 전문가**: 함수 자체를 샘플링하여 결과를 추출합니다.

## 테스트 7: 크기 조절된 이미지가 왜 흐릿하게 보일까?

```js
ctx.drawImage(img, 0, 0, smallW, smallH);   // 한 번에 크게 줄이면: 흐릿하고 앨리어싱 발생
```

큰 이미지를 `drawImage` 호출 한 번으로 줄이면 결과물이 뭉개지고 흐릿하게 보입니다. APIC의 크기 조절 도구는 이미지를 **단계별로 절반씩 축소**하여 목표 크기의 2배 이내로 만든 다음, 마지막에 한 번 더 최종 처리하는 방식을 사용합니다. 단순히 `drawImage` 한 번 호출하는 것과 여러 단계를 거치는 것의 결과물 차이는 생각보다 컸습니다. 이런 작은 디테일이 사용자 만족도를 좌우하더군요.

```js
function highQualityResize(src, targetW, targetH) {
  let cur = src, w = src.width, h = src.height;
  while (w > targetW * 2 || h > targetH * 2) {
    const nw = Math.max(targetW, Math.round(w / 2));
    const nh = Math.max(targetH, Math.round(h / 2));
    const step = document.createElement('canvas');
    step.width = nw; step.height = nh;
    const c = step.getContext('2d');
    c.imageSmoothingEnabled = true;
    c.imageSmoothingQuality = 'high';
    c.drawImage(cur, 0, 0, nw, nh);
    cur = step; w = nw; h = nh;
  }
  // ...then one last high-quality pass onto the exact target size
}
```

**일반 개발자**: `drawImage`를 한 번 호출하고 넘어갑니다.
**브라우저 전문가**: 작업 순서가 결과물에 미치는 영향을 정확히 알고 있습니다.

## 보너스: 하나의 HTML 파일 안에 웹 워커를 어떻게 담을까?

빌드 단계도 없고, 별도의 `worker.js` 파일도 필요 없습니다. APIC은 워커의 소스 코드를 문자열로 보관한 뒤, 이를 Blob으로 만들고 Blob URL을 이용해 워커를 시작합니다. 이런 기발한 트릭 덕분에 배포 편의성을 해치지 않으면서도 무거운 작업을 메인 스레드에서 분리할 수 있었죠. 개발자로서 정말 뿌듯했던 순간입니다.

```js
const SRC = `/* worker code as a string */`;
const worker = new Worker(
  URL.createObjectURL(new Blob([SRC], { type: 'application/javascript' }))
);
```

이 덕분에 무거운 인페인팅 작업도 메인 스레드에서 분리되어 실행되며, 앱 전체는 여전히 어디든 호스팅할 수 있는 **하나의 파일**로 유지됩니다.
