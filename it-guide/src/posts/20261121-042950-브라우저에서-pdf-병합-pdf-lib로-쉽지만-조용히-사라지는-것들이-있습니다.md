# 브라우저에서 PDF 병합? `pdf-lib`로 쉽지만, 조용히 사라지는 것들이 있습니다

"PDF 병합" 웹사이트를 이용할 때마다 파일을 먼저 업로드하라고 요구하죠. 40MB짜리 계약서를 서버에 올리는 건 불편하기도 하고, 보안상 찜찜한 일입니다. 사실 PDF 병합은 단순한 바이트 레벨 작업이라 굳이 서버가 필요 없습니다. 저는 오래전부터 `pdf-lib` 라이브러리를 활용해서 클라이언트 측에서 이 작업을 해왔는데요, 흥미로운 부분은 병합 그 자체보다는 `copyPages` 메서드가 **조용히 남겨두는 것들**, 그리고 **버리는 것들**에 있었습니다.

## `copyPages`는 '페이지'를 복사할 뿐, '문서'를 통째로 가져오지 않습니다

`copyPages`는 페이지의 딕셔너리 정보와 콘텐츠 스트림은 그대로 가져옵니다. 하지만 PDF 문서의 카탈로그(Catalog)에 포함된, 문서 전체 구조를 담당하는 요소들은 대부분 제외합니다. 바로 이런 것들이죠.

*   **목차/개요(Outlines).** PDF 뷰어에서 책갈피처럼 보이는 `/Outlines`는 원본 문서에 종속됩니다. 병합 후에는 이 정보들이 사라지기 때문에, 300페이지짜리 매뉴얼은 더 이상 쉽게 탐색할 수 없는 거대한 덩어리가 되어버립니다.
*   **페이지 레이블(Page labels).** `/PageLabels`라는 숫자 트리는 PDF에서 "iv, v, vi, 1, 2, 3"처럼 실제 페이지 번호와 다른 표기법을 가능하게 합니다. 이것 역시 병합 과정에서 살아남지 못합니다.
*   **AcroForm 필드(AcroForm fields).** 폼 필드를 시각적으로 표시하는 위젯 주석은 페이지와 함께 이동하지만, 필드 자체의 딕셔너리는 문서 레벨에 존재합니다. 결과적으로 폼은 화면에 멀쩡히 보이지만, **정작 입력은 안 되는** 현상이 발생합니다. 더 나쁜 경우, 두 개의 원본 문서가 같은 필드 이름을 사용하고 있었다면 병합된 문서에서 키 중복 문제가 생길 수도 있습니다. **제가 실무에서 이 부분을 테스트해 봤을 때, 폼 필드가 멀쩡히 보이는 줄 알았다가 나중에 고객한테 '왜 입력이 안 되냐'는 피드백을 받고서야 문서 레벨 구조의 중요성을 깨달았죠.**
*   **내장 파일(Embedded files).** `/EmbeddedFiles`는 이름 트리(Name Tree)에 속하며, 문서 레벨 구조입니다.
*   **구조 트리(Structure tree).** 태그가 지정된 PDF(Tagged PDF)의 경우, 접근성(Accessibility)을 위한 구조 트리는 처음부터 다시 만들어지거나 완전히 삭제됩니다.

이 모든 것들이 아무런 오류도 발생시키지 않는다는 점이 함정입니다. 결과물은 잘 열리고, 제대로 렌더링되지만, 사실 원본 입력 파일보다 **조용히 품질이 저하된** 상태인 거죠.

## 좋은 소식: 이미지 스트림은 복사되지, 재인코딩되지 않습니다

이것이 바로 로컬 병합이 대부분의 서버 기반 도구보다 우월한 이유입니다. 스캔된 페이지는 PDF 내부에 JPEG 또는 JBIG2 스트림 형태로 존재합니다. `copyPages`는 이 스트림을 바이트 단위로 그대로 옮겨줍니다. 12MB짜리 스캔 파일은 병합 후에도 여전히 12MB이며, **품질 저하가 전혀 발생하지 않습니다.** 서버 측 병합 도구들은 종종 페이지를 정규화하기 위해 래스터화(rasterize)하는데, 이 과정에서 파일 내의 모든 스캔 이미지를 재압축하게 됩니다.

## 알아두면 유용한 두 가지 `save` 플래그

```js
const bytes = await merged.save({
  useObjectStreams: false,
  updateFieldAppearances: false,
});
```

`useObjectStreams: true` (기본값)는 객체를 압축된 스트림에 패키징하여 파일 크기를 줄여줍니다. 대부분의 최신 뷰어는 이를 잘 처리하지만, 구형 인쇄 RIP 장비나 일부 인쇄 전 검사(preflight) 도구에서는 문제가 될 수 있습니다. 병합된 파일이 인쇄소로 갈 예정이라면 이 옵션을 `false`로 설정하는 것이 좋습니다.

`updateFieldAppearances: false`는 폼 필드의 모양을 재생성하는 과정을 건너뛰는데, 필드가 많은 문서의 경우 측정 가능한 성능 향상을 가져옵니다.

## 암호화된 입력 파일은 오류 대신 '쓰레기'를 만듭니다

```
const doc = await PDFDocument.load(bytes, { ignoreEncryption: true });
```

이 플래그(`ignoreEncryption`)의 이름은 다소 오해의 소지가 있습니다. **이것은 암호화를 해독하는 기능이 아닙니다.** 단지 파서가 객체 스트림이 암호화된 파일을 읽을 수 있도록 허용할 뿐입니다. 즉, `copyPages`는 암호화된 텍스트(ciphertext)를 그대로 복사하여, 병합된 것처럼 보이지만 노이즈만 가득한 문서를 만들어냅니다. `doc.isEncrypted` 속성을 확인하여 암호화된 파일은 사용자에게 명확한 메시지를 보여주고 거부하는 것이, 손상된 파일을 제공하는 것보다 훨씬 현명한 방법입니다.

## 메모리가 진정한 한계입니다

20MB짜리 PDF 파일 5개가 합쳐진다고 해서 메모리가 정확히 100MB만 필요한 것은 아닙니다. 각 파일은 객체 그래프로 파싱되고, `Uint8Array` 복사본 생성에도 비용이 듭니다. 파일 크기의 3~5배 정도가 최고 피크 시점에 필요한 메모리라고 보면 현실적인 예측입니다. 한 번에 하나의 원본 문서만 활성화 상태로 유지하고, 다운로드가 시작되면 Blob URL을 해제하며, 바이트를 Base64로 라우팅하는 것은 절대 피해야 합니다. 아무런 이득 없이 33%의 메모리 오버헤드만 추가될 뿐입니다.

이것이 바로 [브라우저에서 PDF 파일을 병합하는](https://privacypdf.org/merge-pdf/) 전체 아키텍처입니다. 파일을 읽고, 로컬에서 병합한 다음, 다운로드합니다. 이 과정에서 네트워크 소켓은 단 한 번도 건드리지 않습니다.

## 병합이 잘못된 작업일 때

만약 책갈피, 페이지 레이블 또는 채울 수 있는 폼 필드가 중요한 요소라면, 단순 병합은 올바른 접근 방식이 아닙니다. 이런 경우에는 대상 문서 내에서 개요(Outline)를 페이지별로, 그리고 자신만의 번호 체계로 의도적으로 재구성해야 합니다. 물론 더 많은 작업이 필요하지만, 이렇게 해야 진정한 책처럼 작동하는 병합 파일을 얻을 수 있습니다.
