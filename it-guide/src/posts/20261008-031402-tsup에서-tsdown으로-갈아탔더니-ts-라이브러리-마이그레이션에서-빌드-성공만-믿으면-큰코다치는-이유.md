# tsup에서 tsdown으로 갈아탔더니? TS 라이브러리 마이그레이션에서 빌드 성공만 믿으면 큰코다치는 이유

> 설정 마이그레이션은 간단했어요. 하지만 패키지 계약을 그대로 유지하는 게 진짜 흥미로운 부분이었죠.

안녕하세요! 프런트엔드 개발자이자 테크 블로거 `@nyaomaru`입니다. 최근에는 숲속에서 버섯을 찾아다니는 취미에 푹 빠져 있었네요. 😸🍄

최근 제가 개발한 라이브러리의 빌드 설정을 [`tsup`](https://github.com/egoist/tsup)에서 [`tsdown`](https://github.com/rolldown/tsdown)으로 마이그레이션하는 작업을 진행했습니다.

처음에는 이 작업이 정말 사소하고 간단할 거라고 예상했어요.

그냥 `tsup` 제거하고,
`tsdown` 설치하고,
설정만 바꾸고,
빌드 실행하면,
끝! 🎉

솔직히 말하면... 설정 변경 자체는 **정말로** 간단했습니다.

하지만 예상치 못한 흥미로운 문제가 하나 터졌지 뭐예요.

> 첫 `tsdown` 빌드는 성공했지만, 기존 패키지의 공개 계약(public contract)에 이미 포함되어 있던 파일들을 조용히 바꿔버렸습니다.

그래서 이 글은 `tsdown`을 단순히 소개하는 내용이 아닙니다.

대신, 실제 배포된 TypeScript 라이브러리를 `tsup`에서 `tsdown`으로 마이그레이션하면서 어떤 일이 벌어졌고, 무엇이 실제로 바뀌었으며, 소비자들이 여전히 동일한 패키지를 받는지 어떻게 검증했는지 자세히 보여드리려고 합니다.

자, 함께 살펴볼까요! 👀

## 🤔 잘 돌아가는 패키지를 굳이 왜 마이그레이션했을까?

[`is-kit`](https://github.com/nyaomaru/is-kit)은 런타임 타입 가드를 위한 제로-의존성(zero-dependency) TypeScript 라이브러리입니다.

이 라이브러리의 빌드 설정은 이미 너무나 "지루하게" 잘 작동하고 있었어요.

그리고 '지루한 빌드 시스템'은 좋은 시스템이죠. 😸

`is-kit` 패키지는 다음과 같은 특징을 가졌습니다.

*   단일 진입점(entry point)
*   ESM 및 CJS 출력 지원
*   번들링된 선언 파일(`.d.ts`)
*   `package.json`의 명시적인 `exports` 정의
*   선언 파일에 추가되는 배너(banner)
*   압축된 패키지 스모크 테스트

마이그레이션 이전에는 아래와 같은 환경에서 빌드되었습니다.

| 환경    | 값                               |
| :------ | :------------------------------- |
| 패키지  | `is-kit@1.14.2`                  |
| 번들러  | `tsup@8.5.1`                     |
| 진입점  | `src/index.ts`                   |
| 출력    | `ESM + CJS + 번들링된 선언 파일` |
| 타겟    | `esnext`                         |

고장 난 빌드를 고치려던 것이 아니었습니다.

주된 동기는 대부분 유지보수 측면이었어요.

`tsdown`은 Rolldown을 기반으로 구축되었고, 활발한 생태계를 가지고 있으며, 현재 `tsup`을 사용하는 프로젝트들을 위한 마이그레이션 경로로 명시적으로 설계되었죠.

그러니 질문은

> `tsdown`이 이 라이브러리를 빌드할 수 있는가?

가 아니었습니다. 진짜 질문은

> 기존 소비자들이 받는 결과물을 변경하지 않고, 빌드 설정을 `tsdown`으로 옮길 수 있는가?

이것이야말로 이미 배포된 라이브러리에는 훨씬 더 유용한 질문이죠.

## 📦 반드시 유지해야 했던 패키지 계약(Package Contract)

애플리케이션의 경우, 출력 파일 이름이 바뀌어도 크게 문제되지 않을 수 있습니다.

하지만 라이브러리의 경우, 이는 곧 **호환성을 깨는 변경(breaking change)**이 될 수 있어요.

`is-kit`은 이미 `package.json`의 `exports`를 통해 파일을 명시적으로 노출하고 있었습니다.

핵심 경로는 다음과 같았죠.

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.js"
    }
  }
}
```

따라서 저는 마이그레이션을 통해 다음 파일들이 유지되기를 원했습니다.

```text
dist/index.mjs
dist/index.js
dist/index.d.ts
```

물론 기존의 ESM/CJS 런타임 동작, 선언 파일 호환성, export 세트, 그리고 선언 파일 배너까지 모두 동일하게 유지되어야 했죠.

다시 말해,

> 여기에서 '계약'은 소스 코드가 아니었습니다. 압축되어 npm에 배포되는 패키지 그 자체였죠.

이러한 구분이 아주 빠르게 중요해졌습니다.

## 🛠️ 마이그레이션은 거의 사소해 보였다

저는 `tsup`을 `tsdown`으로 교체하고,

```text
tsup.config.ts
```

파일을

```text
tsdown.config.mts
```

로 변경했습니다.

의도적으로 `.mts` 확장자를 사용했어요. 패키지 자체는 `"type": "module"`이 아니기 때문에, ESM 전용 설정 확장자를 사용함으로써 Node가 설정 파일을 잘못 해석하고 관련 경고를 내보내는 것을 방지할 수 있습니다.

대부분의 중요한 옵션들은 거의 직접적으로 매핑되었습니다.

```ts
import { defineConfig } from "tsdown";

export default defineConfig({
  entry: ["src/index.ts"],
  format: ["esm", "cjs"],
  dts: true,
  clean: true,
  outDir: "dist",
  target: "esnext",
  banner: {
    dts: dtsBanner,
  },
});
```

선언 파일 배너 역시 `banner: { dts: dtsBanner }`와 같이 `.d.ts` 파일에만 적용되도록 유지했습니다.

여기까지는 모든 것이 순조로워 보였죠.

그리고 빌드를 실행했습니다.

빌드는 성공했습니다.

하지만 패키지 계약은 **잘못**되어 있었죠. 🙀

## 💥 첫 빌드는 성공했고, 제 파일 이름을 바꿔버렸습니다

이 부분이 정말 흥미로웠습니다.

마이그레이션 전에 중요하게 생성된 파일들은 이랬습니다.

| 빌드                      | 주요 생성 파일                                 |
| :------------------------ | :--------------------------------------------- |
| `tsup`                    | `index.mjs`, `index.js`, `index.d.ts`          |
| 기본 `tsdown` 마이그레이션 | `index.mjs`, `index.cjs`, `index.d.mts`, `index.d.cts` |

`tsdown` 빌드는 종료 코드 `0`으로 성공적으로 완료되었습니다.

하지만 제 기존 `package.json`은 여전히 다음을 기대하고 있었습니다.

```text
require → ./dist/index.js
types   → ./dist/index.d.ts
```

이 파일들은 더 이상 생성된 출력물과 일치하지 않았죠.

만약 제가

```bash
pnpm build
```

명령어에서 멈추고 패키지를 배포했다면,

CJS 소비자들과 TypeScript 모듈 해석이 모두 깨졌을 수 있습니다.

이 마이그레이션에서 얻은 가장 중요한 교훈은 바로 이것입니다.

> **빌드 성공 ≠ 패키지 계약 유지.**

번들러는 단순히 출력을 성공적으로 생성했는지 여부만 알 뿐입니다.

그 출력이 이미 배포된 패키지가 약속한 모든 것과 여전히 일치한다는 의미는 아니죠. 제가 실무에서 이런 종류의 사소해 보이는 변경 때문에 몇 번이나 야근을 했는지 모릅니다. 빌드 성공 로그만 보고 배포했다가 새벽에 호출된 경험이 한두 번이 아니거든요.

## 🔧 `outExtensions`로 공개 계약 복구하기

[`tsdown` 마이그레이션 가이드](https://tsdown.dev/guide/migrate-from-tsup)에는 `outExtension`이 `outExtensions`로 변경되었다는 내용이 명시적으로 언급되어 있습니다.

`is-kit`의 경우, 저는 이 옵션을 사용하여 기존 파일 이름을 그대로 유지했습니다.

```ts
outExtensions: ({ format }) => ({
  dts: format === 'cjs' ? '.d.ts' : '.d.mts',
  js: format === 'cjs' ? '.js' : '.mjs',
}),
```

이제 관련 출력물은 다음과 같이 변경되었고,

```text
dist/index.mjs
dist/index.js
dist/index.d.mts
dist/index.d.ts
```

기존 `exports`는 계속해서 올바르게 해석되었습니다.

저는 이 초기 출력 동작을 `tsdown`의 버그라고 생각하지 않습니다.

`tsdown`은 모호한 모듈 해석을 피하기 위해 패키지 타입과 출력 형식에 따라 확장자를 선택합니다.

그것은 합리적인 접근입니다.

하지만 기존 패키지의 경우, **합리적인 새로운 기본값이라도 결국 변경 사항**입니다.

소비자들이 이미 여러분의 파일 이름에 의존하고 있다면, 그 파일 이름들은 호환성 유지에 중요한 부분이죠.

## 🧪 스모크 테스트로 배포 패키지 검증하기

여기서 `is-kit`에 이미 존재하던 **압축 패키지 스모크 테스트**가 큰 도움이 되었습니다.

저는 이미 `pnpm test:package` 명령어를 가지고 있었는데, 이 명령어는 패키지를 빌드하고, `npm pack`을 실행하여 생성된 `.tgz` 파일을 임시 프로젝트에 설치한 다음, 실제 소비자 관점에서 패키지를 검증하는 역할을 합니다.

이것은 다음을 테스트하는 대신

```text
src/index.ts
```

다음과 같이 테스트합니다.

```text
is-kit-1.14.2.tgz
        ↓
임시 소비자 프로젝트
        ↓
npm install
```

라이브러리는 자체 리포지토리 안에서는 완벽하게 작동하더라도, 배포 시에는 깨진 패키지를 발행할 수 있기 때문에, 이 스모크 테스트는 사용자들이 실제로 설치할 아티팩트를 검증합니다.

마이그레이션 후에 저는 패키지 계약의 더 많은 부분을 검증하기 위해 테스트를 확장했습니다 👇

| 계약                                   | 결과             |
| :------------------------------------- | :--------------- |
| `exports["."].import` → `./dist/index.mjs` | ✅ 통과            |
| `exports["."].require` → `./dist/index.js` | ✅ 통과            |
| `exports["."].types` → `./dist/index.d.ts` | ✅ 통과            |
| 런타임 의존성                          | ✅ 0개             |
| ESM exports                            | ✅ 83개 동일       |
| CJS exports                            | ✅ 83개 동일       |
| 선언 파일 배너                         | ✅ 유지됨          |
| ESM 런타임 import                      | ✅ 통과            |
| CJS 런타임 require                     | ✅ 통과            |
| 압축된 TypeScript 소비자               | ✅ 통과            |

저는 또한 `npm pack`으로 생성된 패키지를 TypeScript v5.7부터 v7.0까지의 임시 소비자 프로젝트에 설치해 보았습니다.

모든 프로젝트에서 생성된 선언 파일들을 성공적으로 해석하고 소비했습니다.

이것은 각 TypeScript 버전이 `tsdown`을 통해 선언 파일을 생성할 수 있는지 테스트하는 것이 아닙니다. **제 사용자들이 실제로 설치하는 아티팩트를 테스트**하는 것이죠.

따라서 미래의 빌드 변경으로 인해 확장자, export 경로, 선언 파일 또는 런타임 동작이 우연히 변경되더라도, **이 스모크 테스트가 배포 전에 이를 감지**할 것입니다.

이러한 라이브러리 마이그레이션의 경우, 단순히 "빌드가 성공적으로 종료되었습니다"라고 단정하는 것보다 훨씬 더 의미 있는 일입니다. 제 경험상 라이브러리 개발에서 이 스모크 테스트만큼 소중한 자산이 또 있을까 싶습니다. 실제 사용자가 겪을 문제를 미리 파악하는 거의 유일한 방법이거든요.

## 📏 출력물 크기는 오히려 커졌다

아티팩트 크기에 대해서도 궁금했습니다.

이것은 제가 예상하지 못한 결과를 낳았습니다.

| 지표             | `tsup`      | `tsdown`    | 차이         |
| :--------------- | :---------- | :---------- | :----------- |
| JS + dts 총합    | 116,503 B   | 144,007 B   | **+23.6%**   |
| ESM JavaScript   | 15,787 B    | 29,410 B    | **+86.3%**   |
| CJS JavaScript   | 19,318 B    | 31,155 B    | **+61.3%**   |
| dts, 단일 포맷   | 40,699 B    | 41,721 B    | **+2.5%**    |
| `npm pack` 타르볼 | 37,226 B    | 42,366 B    | **+13.8%**   |

이 설정에서 `tsdown` 출력물은 이전 `tsup` 출력물보다 더 많은 주석과 영역 표시(region markers)를 유지하고 있었습니다.

그래서 순수 JavaScript 파일 크기가 눈에 띄게 커졌죠.

압축을 통해 실제 `npm 타르볼`에서의 차이는 줄었지만, 완전히 사라지지는 않았습니다.

`is-kit`의 경우, 이 정도는 특별히 우려할 만한 사항은 아닙니다.

작은 제로-의존성 유틸리티 라이브러리이며, 최종 타르볼에서 몇 킬로바이트 정도의 차이니까요.

하지만 이것은 여전히 유용한 교훈을 주었습니다.

> 더 빠르거나 새로운 번들러라고 해서 자동으로 더 작은 아티팩트를 의미하지는 않는다.

패키지 크기가 라이브러리의 엄격한 제약 조건이라면, 마이그레이션 전에 생성된 파일들을 비교하고 최적화 전략을 결정하는 것이 좋습니다.

## ⏱️ 빌드 성능은 어땠을까?

벽 시계 빌드 시간도 측정해 보았습니다.

이전 `tsup` 빌드 시간:

```text
1.50 초
```

새로운 `tsdown` 빌드 시간 (세 번 실행):

```text
1.22 초
1.17 초
1.18 초
```

이 숫자만 본다면, 이렇게 말하고 싶은 유혹을 강하게 느낄 겁니다.

> `tsdown`이 빌드를 더 빠르게 만들었다! 🚀

하지만 저는 이 벤치마크가 그러한 결론을 뒷받침한다고 생각하지 않습니다.

이 비교에서 측정된 `tsup` 실행은 단 한 번뿐입니다.

또한, 이것은 선언 파일 생성이 빌드의 상당 부분을 차지하는 아주 작은 단일 진입점 라이브러리입니다.

번들러 자체의 타이밍 출력은 대략 이랬습니다.

```text
tsup
JavaScript: ~22 ms
dts:        ~707 ms

tsdown
완료:       ~717–755 ms
```

실측 시간 결과는 더 좋았지만, `tsup` 샘플이 단 하나뿐이고 이 작은 라이브러리에서는 선언 파일 생성이 압도적인 부분을 차지하고 있기 때문에, 의미 있는 성능 향상이라고 주장하기에는 충분한 증거가 아니라고 봅니다.

저는 300ms 정도를 절약했다고 해서 마이그레이션을 한 건 아닙니다.

---

## 🐱 그럼 마이그레이션은 정말 사소한 작업이었을까?

`is-kit`의 경우, 그렇습니다.

소스 코드 변경은 전혀 없었습니다.

마이그레이션은 기본적으로 다음으로 제한되었습니다.

```text
의존성
설정
작업 문서
패키지 스모크 테스트의 검증 항목
```

중요한 옵션들은 거의 1대1로 매핑되었습니다.

하지만 **왜** 작업이 사소하게 유지되었는지 설명하는 것이 중요하다고 생각합니다.

`is-kit`은 다음과 같은 특징을 가집니다.

*   단일 진입점
*   런타임 의존성 없음
*   번들러 플러그인 없음
*   CSS 파이프라인 없음
*   복잡한 코드 스플리팅 없음

그리고 가장 중요하게는, 이미 패키지를 소비자 입장에서 테스트할 방법이 있었습니다.

만약 여러분의 패키지가 커스텀 플러그인, 특이한 진입점, CSS 처리, 정확한 소스 맵, 생성된 export, 엄격한 바이트 크기 제한 또는 구형 Node 빌드 환경에 의존한다면, 마이그레이션은 훨씬 더 복잡해질 수 있습니다.

또한, 빌드 환경 요구 사항도 확인할 가치가 있습니다.

제가 테스트한 버전의 경우 (tsdown 0.23.0, Rolldown 1.2.8),

관련 Node 엔진 요구 사항은 다음과 같습니다.

```text
^22.18.0 || ^24.11.0 || >=26.0.0
```

제 CI 환경에서는

```text
Node 22.22.0
```

을 사용하고 있었으므로 문제가 없었습니다.

하지만 기여자(contributor)들이 여전히 Node v20 또는 구형 Node v22 버전으로 라이브러리를 빌드한다면, 이는 마이그레이션 전에 해결해야 할 문제입니다.

물론, 이것이 여러분의 **라이브러리 소비자들이** Node v22를 사용해야 한다는 의미는 아닙니다.

그것은 빌드 도구의 요구 사항입니다.

그래도 기여자 및 CI 환경도 마이그레이션 비용의 일부라는 점을 잊지 마세요. 😿

---

## 🎯 그래서, tsup에서 tsdown으로 옮길 가치가 있었을까?

`is-kit`의 경우, 저는 그렇다고 생각합니다.

하지만 성능 때문은 아닙니다.

마이그레이션을 통해 ESM, CJS, 선언 파일, `exports`, 그리고 압축된 패키지 소비자 테스트 전반에 걸쳐 패키지 계약이 그대로 유지되었습니다.

설정 변경은 작고 검토하기 쉬웠습니다.

기존 Node 환경이 새로운 빌드 요구 사항을 만족했습니다.

그리고 빌드 설정이 이제 활발하게 발전 중인 Rolldown 생태계와 정렬되었습니다.

물론 비용도 분명히 있었습니다.

*   아티팩트 크기가 증가했습니다.
*   Node 빌드 요구 사항이 높아졌습니다.
*   출력 확장자에 명시적인 설정이 필요했습니다.

그래서 저는 이것을 이렇게 설명하고 싶지는 않습니다.

> `tsdown`이 더 빠르니 `tsup`을 사용하는 모든 사람은 즉시 마이그레이션해야 합니다!

이것은 이번 실험에서 보여준 결론이 아닙니다.

저에게 더 나은 결론은 이렇습니다.

> 프로젝트가 이미 Node 요구 사항을 충족하고 빌드 설정을 Rolldown 생태계로 옮기고 싶다면, 작은 라이브러리를 `tsup`에서 `tsdown`으로 마이그레이션하는 것은 매우 합리적인 변경이 될 수 있습니다.

하지만 반드시 **여러분께서 배포하는 패키지를 검증**하세요.

소스 코드만 보지 말고,
설정 파일만 보지 말고,
그리고 확실히 초록색 빌드 성공 메시지만 믿지 마세요. 😸

왜냐하면 이번 마이그레이션에서 가장 흥미로운 버그는 빌드가 모든 것이 괜찮다고 말할 때 발생했으니까요. 이게 정말 핵심입니다. 실무에서 가장 위험한 버그는 에러 메시지조차 없이 조용히 잘못된 결과를 내뱉는 경우니까요.

---

이 글의 패키지를 실제 프로젝트에서 보고 싶으시다면, `is-kit`은 오픈 소스입니다.

런타임 유효성 검사 및 안전한 타입 좁히기에 초점을 맞춘 가볍고 제로-의존성 TypeScript 타입 가드 라이브러리입니다.
