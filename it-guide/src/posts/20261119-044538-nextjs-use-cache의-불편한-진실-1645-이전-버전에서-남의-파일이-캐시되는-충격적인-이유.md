# Next.js `use cache`의 불편한 진실: 16.4.5 이전 버전에서 남의 파일이 캐시되는 충격적인 이유

Next.js에서 `use cache` 디렉티브는 서버 컴포넌트나 서버 액션의 성능을 비약적으로 끌어올리는 강력한 도구입니다. 공식 문서에서도 `use cache` 함수에 전달되는 직렬화 가능한 인자들이 캐시 키의 일부가 된다고 명확히 안내하고 있죠. 심지어 어떤 타입이 지원되는지도 상세히 설명되어 있습니다. 하지만, 문서가 미처 보여주지 못하는 부분이 있습니다. 바로 바이너리 값이 캐시 키에 어떻게 포함되는지, 그리고 무엇이 소리 소문 없이 누락되는지에 대한 것입니다.

이 간극은 개발자에게 치명적일 수 있습니다. 캐시 키는 일종의 "약속"이기 때문이죠. 동일한 키를 가진 두 호출은 언제나 동일한 결과를 반환해야 합니다. 만약 키 자체가 무언가를 놓치고 있다면, 한 사용자가 다른 사용자의 결과를 받아보는 끔찍한 상황이 발생할 수도 있습니다. 제가 실무에서 `use cache`를 도입하고 나서 예상치 못한 동작에 마주쳤을 때, '설마' 하는 마음으로 직접 코드를 파고들어 확인해 본 경험이 있습니다. 이번에도 문서만으로는 뭔가 부족하다는 느낌을 지울 수 없었죠. 그래서 며칠 밤낮으로 테스트 환경을 구축하고 Next.js 내부 코드를 분석하면서, 문서에 없는 비공개적인(하지만 치명적일 수 있는) 동작 방식을 직접 확인해야겠다고 결심했습니다.

직접 테스트하지 않고서는 알 수 없다는 생각에, 저는 Next.js 16.4.4, 16.4.5, 16.4.6 버전에서 54쌍의 서로 다른 입력값을 `use cache` 함수에 통과시켰습니다. 그리고 그 결과가 왜 그렇게 나오는지 알아내기 위해 캐시 키를 빌드하는 Next.js 내부 코드를 열어보았죠. 결과는 예상보다 훨씬 충격적이었습니다. 동일한 바이트를 가졌지만 이름이 다른 두 `File` 객체가 같은 캐시 엔트리를 공유했습니다. 심지어 홀수 길이의 바이트 배열과 그 배열에 0 바이트 하나를 추가한 짝수 길이의 배열조차도 동일하게 취급되었죠. 이는 Next.js가 16.4.5 수정사항과 함께 발표한 보안 권고, GHSA-rhh4-g77r-r9qj와도 정확히 일치하는 부분입니다. 아래에서 더 자세히 다루겠습니다.

> 저는 `next start` 명령, 기본 인메모리 캐시 핸들러, 그리고 `cacheComponents`를 `true`로 설정한 환경에서 테스트를 진행했습니다. 캐시된 함수들은 라우트 핸들러와 한 서버 액션 페이지에서 호출되었습니다. 이 모든 테스트는 `npm run demo` 명령 하나로 재현 가능하며, 상세한 코드는 [nextjs-use-cache-key-lab](https://github.com/shubhrapokhariya/nextjs-use-cache-key-lab) 저장소에서 확인할 수 있습니다.

## 핵심 요약: 바쁘다면 이것만 보세요

시간이 부족하신 분들을 위해 제가 발견한 주요 내용은 다음과 같습니다.

*   **대부분의 입력값은 예상대로 작동합니다.** 16.4.6 버전에서는 제가 테스트한 54쌍 중 46쌍이 고유한 캐시 엔트리를 가졌습니다.
*   **16.4.5 버전 이전에는 두 개의 다른 바이너리 값이 하나의 캐시 엔트리를 공유할 수 있었습니다.** 캐시 키가 `File` 객체의 이름과 타입을 무시했던 것이죠. 동일한 바이트를 가진 `Blob`과 `File`을 하나의 값으로 취급하기도 했습니다. 또한, 홀수 길이의 바이트 배열과 그 배열 끝에 0 바이트 하나를 추가한 배열을 동일하게 간주했습니다. 이 모든 문제는 16.4.5에서 해결되었습니다.
*   **`File.lastModified`는 여전히 캐시 키의 일부가 아닙니다.** 소스 코드를 보면 의도적인 것으로 보입니다. 폼 업로드의 경우, 이 값은 단지 서버가 요청을 파싱한 시간일 뿐이기 때문입니다.
*   **캐시가 읽을 수 없는 값들** (클래스 인스턴스, 함수, RegExp, Symbol)은 함수가 이들을 무시할 때는 하나의 엔트리를 공유하지만, 클로저가 이들을 캡처하면 오류를 발생시킵니다.
*   **약 250,000바이트를 초과하는 `Uint8Array`나 `Blob` 인자는 `RangeError: Maximum call stack size exceeded` 오류를 발생시킵니다.** 정확한 임계값은 사용자의 시스템에 따라 달라집니다. 저는 이 오류를 유발하는 코드 라인을 찾아냈으며, 일반 Node.js 환경에서도 재현됩니다.

## Next.js `use cache` 키에는 무엇이 들어갈까?

공식 문서에 따르면 `use cache` 키는 몇 가지 요소로 구성됩니다. 빌드 ID(또는 `deploymentId` 설정 시 해당 ID), 함수 ID, 전달하는 직렬화 가능한 인자들, 그리고 개발 환경에서는 HMR 해시가 포함됩니다. 함수가 외부 스코프에서 캡처하는 변수들도 인자로 바인딩되므로 캐시 키에 영향을 미칩니다. 이 모든 개념이 생소하시다면, 제 [Next.js 16 캐시 컴포넌트 마이그레이션 가이드](https://shubhra.dev/tutorials/nextjs-16-cache-components)에서 기본을 다루고 있으며, 공식 [`use cache` 문서](https://nextjs.org/docs/app/api-reference/directives/use-cache)가 참고 자료입니다.

빌드 ID와 함수 ID는 큰 이슈가 되지 않습니다. 동일한 빌드 내에서 동일한 함수를 호출하면 항상 같은 값을 가지니까요. 문제는 바로 "인자"에서 발생합니다. 제가 테스트를 집중한 부분도 바로 이 인자들입니다.

## `use cache` 키를 어떻게 테스트했나?

테스트 아이디어는 간단합니다. 각 테스트 케이스마다 단 한 가지만 다른 두 개의 값(A와 B)을 준비합니다. 그런 다음 캐시된 함수를 값 A로 한 번 호출하고, 다시 값 A로 호출합니다(이것은 호출이 실제로 캐시되었는지 확인하는 대조군입니다). 마지막으로 값 B로 호출합니다. 함수는 실제로 실행될 때마다 새로운 마커(랜덤 토큰, 또는 아래 예시에서는 타임스탬프)를 반환하도록 합니다. 만약 값 B로 호출했을 때 A의 마커가 반환된다면, B가 A의 캐시 엔트리를 재사용했다는 의미입니다.

물론 캐시 엔트리를 공유하는 것이 항상 문제는 아닙니다. 저는 또한 캐시가 없었을 때 B가 어떤 결과를 반환했어야 하는지도 계산했습니다. 이를 통해 무해한 별칭 공유와 잘못된 결과 반환을 구분할 수 있었습니다.

| 상태       | 의미                                                                    |
| :--------- | :---------------------------------------------------------------------- |
| `SEPARATE` | B가 자신만의 고유한 캐시 엔트리를 가짐                                  |
| `SHARED`   | B가 A의 엔트리를 재사용했지만, 출력은 B가 원래 생성했을 내용과 동일함 |
| `SHARED-WRONG` | B가 A의 엔트리를 재사용했고, **다른 입력값을 위해 계산된 결과를 받음** |

저는 제 시스템에서 16.4.4, 16.4.5, 16.4.6 세 가지 버전을 테스트했습니다. 이 세 버전 중에서 결과가 달라지는 경계는 정확히 16.4.4와 16.4.5 사이였습니다. 만약 `cacheComponents`를 켜는 것만으로도 빌드가 깨진다면, 제가 [Next.js 캐시 컴포넌트를 망가뜨릴 수 있는 모든 방법들](https://shubhra.dev/tutorials/nextjs-cache-components-build-errors)이라는 글에서 겪었던 오류들을 정리해 두었습니다.

저장소에는 12개 버전(16.0.0부터 16.4.6까지, 그리고 Node 20 및 24)에 대한 참조 결과도 포함되어 있습니다. 이들은 제 시스템이 아닌 다른 시스템에서 얻은 결과입니다. 이 결과들을 보면 16.4.4까지는 모든 버전에서 키 결과가 동일했고, 16.4.5와 16.4.6에서는 동일했습니다. 제가 직접 다른 버전을 실행하지 않았으므로, 이 데이터는 제 테스트를 뒷받침하는 보조 데이터로 간주합니다.

## 테스트 결과: 무엇이 달랐을까?

가장 중요한 내용은 **볼드체**로 표시된 행부터 읽어보세요.

| A와 B의 차이점                                                                                                           | 16.4.4            | 16.4.5 및 16.4.6 |
| :----------------------------------------------------------------------------------------------------------------------- | :---------------- | :----------------- |
| 문자열, 숫자, 불리언, BigInt, `null` vs `undefined`, `0` vs `-0`, `'1'` vs `1`, `undefined` vs 문자열 `'$undefined'` | `SEPARATE`        | `SEPARATE`         |
| 객체 값, 중첩된 값, `[1,2]` vs `[2,1]`, 배열 vs 숫자 키를 가진 객체, `{}` vs `[]`                                        | `SEPARATE`        | `SEPARATE`         |
| 객체 키 순서 변경 (`{a, b}` vs `{b, a}`)                                                                                 | `SEPARATE`        | `SEPARATE`         |
| Map, Set 및 FormData 삽입 순서 변경                                                                                      | `SEPARATE`        | `SEPARATE`         |
| Date, Map 및 Set 값, FormData, URL, URLSearchParams                                                                      | `SEPARATE`        | `SEPARATE`         |
| 다른 바이트를 가진 TypedArray (200,000 바이트 중 마지막 바이트만 다름), Uint8 vs Int8, Uint8 vs ArrayBuffer, Uint8 vs Buffer | `SEPARATE`        | `SEPARATE`         |
| 다른 바이트를 가진 Blob 또는 File (200,000 바이트 중 마지막 바이트만 다름)                                                | `SEPARATE`        | `SEPARATE`         |
| 배열 홀 (`[1,,3]` vs `[1, undefined, 3]`)                                                                                | `SHARED` (무해)   | `SHARED` (무해)    |
| 독립적인 4바이트 배열 vs 더 큰 버퍼의 뷰로서의 동일한 4바이트                                                               | `SHARED` (무해)   | `SHARED` (무해)    |
| **File 이름이 다름** (바이트는 같음)                                                                                     | **`SHARED-WRONG`** | `SEPARATE`         |
| **Blob 또는 File 타입이 다름** (바이트는 같음)                                                                           | **`SHARED-WRONG`** | `SEPARATE`         |
| **Blob vs File** (바이트는 같음)                                                                                         | **`SHARED-WRONG`** | `SEPARATE`         |
| **홀수 길이 바이너리 값 vs 동일한 값에 0 바이트 하나 추가** (Uint8Array, Blob, File)                                    | **`SHARED-WRONG`** | `SEPARATE`         |
| **`File.lastModified`가 다름**                                                                                           | **`SHARED-WRONG`** | **`SHARED-WRONG`** |
| 함수가 무시하는 클래스 인스턴스, 함수, RegExp 또는 Symbol                                                                | `SHARED`          | `SHARED`           |

전체 결과는 16.4.4에서 38 `SEPARATE`, 7 `SHARED`, 9 `SHARED-WRONG`이었고, 16.4.6에서는 46 `SEPARATE`, 7 `SHARED`, 1 `SHARED-WRONG`입니다. 전체 54개 행 테이블은 저장소에서 확인할 수 있습니다.

## 앨리스의 파일을 가로챈 밥의 사례

이 문제의 심각성을 가장 쉽게 파악할 수 있는 방법은 `File`을 인자로 받는 아주 작은 캐시 함수를 살펴보는 것입니다.

```js
// lib/inspect.js
"use cache";

export async function inspectUpload(file) {
  return {
    name: file.name,
    type: file.type,
    size: file.size,
    filledAt: Date.now(),
  };
}
```

저는 이 함수를 동일한 32바이트를 가지고 있지만 이름이 다른 두 `File`로 호출했습니다. 다음은 16.4.4 버전에서 제가 실행했을 때의 실제 출력입니다.

```plaintext
inspectUpload(File "alice.pdf") -> { "name": "alice.pdf", ... "filledAt": 1794584074839 }
inspectUpload(File "bob.pdf")   -> { "name": "alice.pdf", ... "filledAt": 1794584074839 }
```

두 번째 줄을 보세요. 밥의 호출이 앨리스의 결과를 받아왔습니다! `filledAt` 값이 동일하다는 것은 함수 본문이 전혀 실행되지 않았다는 의미입니다. 16.4.5 버전에서는 밥이 `bob.pdf`라는 예상대로의 결과를 받습니다.

바이트 레벨에서의 사례는 더욱 기이합니다. 다음 함수를 보시죠.

```js
export async function describeBytes(bytes) {
  return {
    length: bytes.length,
    last: bytes[bytes.length - 1],
    filledAt: Date.now(),
  };
}
```

16.4.4 버전에서 `describeBytes(Uint8Array.from([61, 62, 63]))`를 호출하면 `length: 3`이 반환됩니다. 이는 올바른 결과입니다. 그런데 제가 네 바이트를 가진 다른 배열인 `describeBytes(Uint8Array.from([61, 62, 63, 0]))`를 호출하자, 여전히 `length: 3`이 반환되었습니다. 16.4.5 버전에서는 `length: 4`가 정확히 반환됩니다.

한 가지 주의할 점은, 공식 문서에는 TypedArray와 ArrayBuffer가 지원되는 인자로 명시되어 있지만 `Blob`이나 `File`은 언급되지 않았다는 것입니다. 따라서 이 두 가지에 대해 제가 보고하는 내용은 제가 테스트한 버전에서의 "관찰된 동작"이지, 문서화된 보장은 아닙니다.

제로 바이트 하나가 추가되었을 뿐인데, 캐시는 그 차이를 구별하지 못했습니다.

### `use cache` 파일 버그는 실제 폼 업로드에서도 발생할까?

위의 모든 테스트는 라우트 핸들러에서 캐시된 함수를 호출하는 방식이었습니다. 실제 애플리케이션에서는 `File`이 주로 Server Action을 통해 전달되므로, 이 경로도 테스트했습니다. 평범한 `<form action={upload}>` 태그를 사용했고, `upload` 액션은 `formData.get('file')`을 받아 동일한 캐시된 `inspectUpload` 함수로 전달합니다. 저는 JavaScript가 없는 브라우저처럼 폼을 제출했습니다. 다른 Server Action 관련 문제는 [Next.js 16 Server Actions 및 프로덕션에서만 나타나는 버그들](https://shubhra.dev/tutorials/nextjs-16-server-actions-loading-errors)에서 다룬 바 있습니다.

결과는 동일했습니다. 16.4.4 버전에서는 `bob.pdf` 업로드가 `alice.pdf`의 결과를 반환했고, 4바이트 파일이 이전에 업로드된 3바이트 파일의 결과를 반환했습니다. 16.4.5 버전에서는 각 업로드마다 고유한 결과를 얻었습니다. Server Action 내부에서 값은 실제 `File` 객체였습니다. `npm run action` 명령으로 직접 실행해 볼 수 있습니다.

### 왜 이런 일이 발생했을까?

캐시 키를 빌드하는 코드는 여러분의 코드에 있는 것이 아니라 Next.js의 서버 번들 내부에 존재합니다. 여러분의 인자들은 먼저 React의 응답 인코더를 거칩니다. 인자 중 하나가 바이너리 데이터를 포함하면 그 결과는 `FormData`가 되고, `encodeFormData`라는 함수가 이를 캐시 키에 사용되는 문자열로 변환합니다. 이 코드는 제가 테스트한 세 가지 버전 모두 `node_modules/next/dist/server/use-cache/use-cache-wrapper.js`에서 읽을 수 있으며, 제 `diagnose` 스크립트는 빌드 출력에서 축소된 복사본도 출력합니다. 다음은 16.4.4 버전(수정 전 마지막 버전)의 `encodeFormData` 함수 중 바이너리 브랜치 부분을 간소화하고 이름을 변경한 복사본입니다. Next.js의 실제 키 빌더와 완전히 동일하지는 않습니다. 저장소의 참조 결과에 있는 `diagnose` 출력은 16.0.0부터 16.4.4까지 모든 빌드에서 동일한 필드가 키에서 누락되었음을 보여주지만, 제가 직접 이 버전들을 실행하지는 않았습니다.

```js
async function encodeFormData(formData) {
  let key = "";
  for (const [field, value] of formData) {
    let text;
    key += field.length.toString(16) + ":" + field;
    if (typeof value === "string") {
      text = value;
    } else {
      const buf = await value.arrayBuffer();
      text =
        buf.byteLength % 2 === 0
          ? String.fromCodePoint(...new Uint16Array(buf))
          : String.fromCodePoint(
              ...new Uint16Array(buf, 0, (buf.byteLength - 1) / 2),
            ) +
            String.fromCodePoint(new Uint8Array(buf, buf.byteLength - 1, 1)[0]);
    }
    key += text.length.toString(16) + ":" + text;
  }
  return key;
}
```

이 코드는 다음과 같은 의미를 가집니다. 바이트 데이터는 두 바이트씩 문자열로 변환되며, 이 문자열만이 해당 인자의 키로 사용됩니다. 파일 이름도, 타입도, `Blob`인지 `File`인지에 대한 기록도 전혀 없습니다. 게다가 홀수 길이의 바이트는 마지막 바이트가 단독으로 하나의 코드 유닛으로 읽힙니다. 리틀 엔디안 CPU(x86 및 사실상 ARM)에서는 `[x, 0]`을 16비트 숫자로 읽었을 때와 동일한 코드 유닛이 됩니다. 따라서 `[61, 62, 63]`과 `[61, 62, 63, 0]`은 동일한 길이의 동일한 문자열을 생성하게 됩니다. 이 로직을 따라가 보면 짝수 길이 배열은 이런 식으로 충돌하지 않는다는 것을 알 수 있습니다. 짝수 길이 배열에 0 바이트를 추가하면 홀수 길이가 되지만, 홀수 길이 배열은 마지막 바이트가 추가 코드 유닛으로 붙기 때문에 두 문자열은 서로 달라집니다. 제 실험실에서는 3바이트와 4바이트 사례를 테스트했으므로, 짝수 길이 부분은 코드를 읽은 결과이지 직접 실행한 결과는 아닙니다.

16.4.5 버전부터는 이 바이너리 브랜치에서 이름, 타입, 바이트 길이도 텍스트 앞에 기록합니다.

```js
key +=
  "B" +
  value.name.length.toString(16) +
  ":" +
  value.name +
  value.type.length.toString(16) +
  ":" +
  value.type +
  buf.byteLength.toString(16) +
  ":" +
  text;
```

축소된 코드를 읽는 것도 중요하지만, 저는 실제 키가 어떻게 생겼는지 직접 확인하고 싶었습니다. 그래서 Next.js의 기본 캐시 핸들러를 래핑하고 수신하는 모든 키를 로깅하는 작은 캐시 핸들러를 작성했습니다. 다음은 제가 실행했을 때의 출력입니다. 16진수 ID는 빌드마다 다르므로, 한 버전 내에서 두 줄을 비교해 보세요.

```plaintext
16.4.4  alice.pdf  1:110:܇܇܇܇܇܇܇܇܇܇܇܇܇܇܇܇1:050:["c084f7f0…",["$B1"],["VTD4as…"]]   miss
16.4.4  bob.pdf    1:110:܇܇܇܇܇܇܇܇܇܇܇܇܇܇܇܇1:050:["c084f7f0…",["$B1"],["VTD4as…"]]   HIT, same string

16.4.5  alice.pdf  1:1B9:alice.pdf0:20:܇܇܇܇܇܇܇܇܇܇܇܇܇܇܇܇1:050:["c02d82da…",["$B1"],["noVPW1…"]]
16.4.5  bob.pdf    1:1B7:bob.pdf0:20:܇܇܇܇܇܇܇܇܇܇܇܇܇܇܇܇1:050:["c02d82da…",["$B1"],["noVPW1…"]]
```

이상한 문자 U+0707은 제 32바이트(각 값 7)가 16개의 16비트 코드 유닛으로 두 바이트씩 읽힌 결과입니다. 16.4.4에서는 두 키가 동일한 문자열이므로 두 번째 호출이 캐시 히트(HIT)됩니다. 16.4.5에서는 파일 이름이 키에 포함되어 있습니다. `[61,62,63]`과 `[61,62,63,0]`에 대한 동일한 실험에서는 16.4.5에서 `0:3:`과 `0:4:`로 나타나는데, 이는 16.4.4에서 누락되었던 바이트 길이입니다. `npm run keys`로 직접 실행해 볼 수 있습니다.

이 단 하나의 변경사항이 모든 '뒤바뀐' 행의 이유를 설명합니다. 또한 `lastModified`가 왜 바뀌지 않았는지도 설명합니다. `lastModified`는 이 라인에 포함되지 않았기 때문입니다. `npm run diagnose`를 통해 여러분의 빌드에서 이 함수를 직접 출력하여 제 말이 맞는지 확인할 수 있습니다.

## 이것이 `use cache` 교차 사용자 캐시 노출 권고와 관련이 있을까?

그렇습니다, 정확히 일치합니다. Next.js의 [11월 3일 보안 릴리스](https://nextjs.org/blog/november-2026-security-release)에는 `use cache` 바이너리 인자를 통한 _교차 사용자 캐시 노출 및 오염_이 명시되어 있습니다. 이에 대한 [GitHub 권고](https://github.com/vercel/next.js/security/advisories/GHSA-rhh4-g77r-r9qj)(GHSA-rhh4-g77r-r9qj, CVE-2026-119349)는 보통(Moderate) 등급으로 분류되어 있으며, 릴리스 게시물에서는 중간(Medium)으로 표기하고 있습니다. 16.0.0부터 16.4.4까지의 버전이 영향을 받으며, 16.4.5가 수정 버전으로 명시되어 있습니다. 이 권고는 `use cache` 함수에 바이너리 인자(예: Uint8Array 또는 Blob 값)를 전달하는 애플리케이션이 "서로 다른 인자에 대해 동일한 캐시 키를 생성할 수 있다"고 경고합니다.

제 테스트 결과는 이와 완벽하게 일치합니다. 16.4.4 버전에서 저는 다른 `File` 및 `Uint8Array` 값에 대해 동일한 키 문자열을 얻었으며, `Blob` 값에 대해서도 공유된 결과를 얻었습니다 (Blob 키는 출력하지 않았습니다). 키 함수는 16.4.5에서 변경되었습니다. 저는 16.4.4, 16.4.5, 16.4.6 버전만 직접 실행했으므로, 나머지 영향을 받는 범위는 권고 내용을 따른 것이지 제 측정치는 아닙니다. 저는 어떤 취약점도 악용하려고 시도하지 않았습니다. 제 실험실이 보여주는 것은 잘못된 캐시 재사용이며, 여러분이 얼마나 노출되어 있는지는 여러분의 앱과 캐시 핸들러에 따라 달라집니다.

### 이 문제가 당신의 앱에 영향을 줄까?

권고는 이 부분에 대해 신중하게 접근하고 있으며, 여러분도 그래야 합니다. 권고에 따르면, 이 위험은 애플리케이션이 바이너리 인자를 "사용자 또는 계정을 구별하기 위해" 사용하고, 캐시 동일성 입력이 일치하며, 캐시 엔트리가 호출자 간에 공유될 때 발생합니다. 또한, 이것이 "관련 없는 캐시 엔트리에 대한 임의의 접근을 허용하지는 않는다"고 덧붙였습니다.

제 테스트에서 실질적인 의미는, 충돌이 발생하려면 **키가 무시한 어떤 것에 결과가 의존하는** 함수여야 한다는 것입니다. 이 특정 충돌은 문자열과 숫자만 받는 함수에는 적용되지 않습니다. 우려되는 지점은 고유한 바이너리 값이 함수의 반환값을 변경하지만, 키는 이들을 동일하게 취급하는 경우입니다. 만약 `File`을 전달하고 그 이름이나 타입에서 파생된 무언가를 반환하거나, 바이트 배열로 사용자를 식별한다면, 즉시 16.4.5 버전 이상으로 업그레이드해야 합니다. 문서에서는 또한 기본 인메모리 핸들러의 경우 엔트리가 서버리스 요청 간에 지속되지 않는 경우가 많고, 호스트가 캐시 핸들러를 교체할 수 있다고 명시하고 있습니다. 따라서 여러분의 노출 정도는 호스팅 환경에 따라 달라집니다.

동일한 보안 릴리스에는 중첩 함수 및 `unstable_cache`에 대한 다른 `use cache` 권고도 포함되어 있습니다. 이들은 다른 버그이며 이 글에서는 다루지 않습니다.

오래된 버전을 실행하는 경우 한 가지 더 있습니다. 별도의 [권고](https://github.com/vercel/next.js/security/advisories/GHSA-673q-mjm6-r5xr)(GHSA-673q-mjm6-r5xr, Critical, CVE 없음)는 여러 Typed Array를 반환하는 `use cache` 함수를 가진 App Router 앱에서 인증되지 않은 원격 코드 실행(RCE)을 설명합니다. 이는 16.0.0부터 16.4.0까지의 버전에 영향을 미치며, 16.4.1에서 수정되었고, 권고에는 알려진 해결 방법이 없다고 명시되어 있습니다. 제가 테스트한 세 버전은 이 범위에 포함되지 않으며 제 실험실에서는 이 문제를 유발하지 않습니다. 그럼에도 불구하고, 인터넷에 연결된 환경에서 오래된 버전을 실행하지 않아야 하는 좋은 이유입니다.

## `File.lastModified`는 `use cache` 키의 일부일까?

아닙니다. 그리고 이는 의도적인 것으로 보입니다. 동일한 바이트, 이름, 타입을 가졌지만 `lastModified`가 다른 두 `File`은 16.4.6에서도 하나의 엔트리를 공유합니다. 두 번째 호출자는 첫 번째 호출자의 값을 받게 되는 것이죠.

16.4.5 및 16.4.6 버전과 함께 제공되는 읽기 쉬운 소스 코드(`next/dist/server/use-cache/use-cache-wrapper.js`)에는 키 빌더 옆에 주석이 있습니다. 이 주석은 이름과 타입이 캐시된 함수에서 관찰되므로 키의 일부라고 말합니다. 또한 "lastModified는 제외된다"며, "기본적으로 생성 시간이며 멀티파트 제출을 통해 유지되지 않는다"고 명시되어 있습니다.

저는 랩의 서버 액션 테스트에서 16.4.6 버전으로 이 주석의 후반부를 확인했습니다. `lastModified`를 1000으로 설정한 파일을 업로드했지만, 액션에서는 서버의 현재 시간을 보았습니다. 해당 옵션 없이 `File`을 생성하면 `lastModified`도 현재 시간을 가지며, [`File` 생성자에 대한 MDN 페이지](https://developer.mozilla.org/en-US/docs/Web/API/File/File)에도 이 옵션이 문서화되어 있습니다. 따라서 폼 업로드의 경우 `lastModified`는 서버가 요청을 파싱한 시간입니다. 캐시된 함수 내에서 이 값을 읽고 사용자의 파일에서 온 날짜를 기대하지 마세요.

## 캐시가 읽을 수 없는 값들은 어떻게 될까?

문서에서는 직렬화 불가능한 값을 "내부적으로 검사하지 않는 한" 전달할 수 있다고 합니다. 저는 이것이 실제로 무엇을 의미하는지 알고 싶어서 두 가지 상황을 테스트했습니다. 하나는 값을 인자로 전달하는 것이고, 다른 하나는 캐시된 함수 내의 클로저에서 이를 캡처하는 것입니다.

| 값                             | 인자로 전달된 경우 (함수가 불투명한 값을 읽지 않음) | 캐시된 함수 내의 클로저에 의해 캡처된 경우 |
| :----------------------------- | :---------------------------------------------------- | :----------------------------------------- |
| 클래스 인스턴스                | 하나의 공유 엔트리                                    | 오류 발생                                  |
| 함수                           | 하나의 공유 엔트리                                    | 오류 발생                                  |
| RegExp                         | 하나의 공유 엔트리                                    | 오류 발생                                  |
| `Symbol('a')`                  | 하나의 공유 엔트리                                    | 오류 발생                                  |
| `Symbol.for('a')`              | 하나의 공유 엔트리                                    | 언급만 되면 공유, 읽으면 오류 발생         |
| Date, Map, Set, 일반 객체      | 별도의 엔트리                                         | 별도의 엔트리                              |

"하나의 공유 엔트리"란, 예를 들어 `Symbol.for('a')`와 `Symbol.for('b')`가 동일한 캐시 결과를 얻는다는 의미입니다. 이는 함수가 이들을 읽지 않아야 한다는 설계에 따른 것이므로 의도된 동작입니다. 하지만 이 값들이 키에 전혀 영향을 미치지 않는다는 점은 알아둘 가치가 있습니다. 오류는 일반적인 Flight 오류입니다. 예를 들어 "Only plain objects, and a few built-ins, can be passed to Client Components from Server Components. Classes or null prototypes are not supported."와 같은 메시지가 나옵니다. 캡처된 `Symbol.for`를 읽으려 하면 서버에서 "Cannot access constructor on the server"가 로깅됩니다.

한 가지 더 특이한 점은, 문서에서는 `URL` 인스턴스가 지원되지 않는다고 명시하고 있지만, 제 테스트에서는 `URL`이 인자로 잘 작동했습니다. 함수 내부에서는 문자열로 전달되었고, 다른 URL들은 별도의 엔트리를 얻었습니다. 하지만 이 동작에 의존하지 않는 것이 좋습니다.

## 눈치채지 못하고 유발하는 캐시 미스

이제 반대되는 문제입니다. 이 모든 경우에 별도의 엔트리가 생성되었는데, 이는 올바른 동작이지만 각각 잠재적인 추가 캐시 미스입니다.

*   키 순서가 다른 객체는 다른 엔트리가 됩니다.
*   Map, Set, FormData의 삽입 순서가 중요합니다.
*   `0`과 `-0`은 다르게 취급되며, `null`과 `undefined`도 마찬가지입니다.
*   공유 참조를 가진 객체는 두 개의 동일한 복사본과 다르게 취급됩니다.

이 중 어느 것도 버그는 아닙니다. 만약 다른 곳에서 인자 객체를 구성한다면, 대신 ID나 문자열과 같은 원시 값을 전달하고 함수가 나머지를 찾아보도록 하는 것이 좋습니다.

## `use cache`의 최대 인자 크기는?

특정 크기를 초과하는 바이너리 인자는 오류를 발생시킵니다.

```plaintext
RangeError: Maximum call stack size exceeded
```

제 시스템에서는 새 프로세스에서 작동하는 가장 큰 `Uint8Array`는 250,871바이트였습니다. 250,872바이트에서는 오류가 발생했지만, 프로세스가 워밍업되면 임계값이 약간 변동됩니다. 다른 시스템에서는 동일한 테스트가 약 247,000바이트에서 멈췄으므로, 정확한 숫자는 여러분의 시스템과 Node 버전에 따라 달라지며, 250,000바이트 근처의 값은 경계선으로 간주해야 합니다.

`Blob`도 비슷한 크기에서 실패합니다 (저는 `File`을 별도로 측정하지 않았습니다). Typed Array는 요소 유형에 관계없이 거의 동일한 바이트 수에서 실패합니다. 이는 `Uint16Array`의 경우 125,435 요소, `Float64Array`의 경우 31,358 요소에 해당합니다. 제가 실행한 세 가지 버전에서 `Uint8Array`의 한계는 변하지 않았지만, 다른 것들은 수십 바이트 정도 움직였습니다. `Uint16Array`는 16.4.4와 16.4.5에서 125,447이었고 16.4.6에서는 125,435였으며, `Blob`은 한 번 실행에서 250,895, 다른 실행에서는 250,871로 측정되었습니다. 따라서 이 숫자들은 정확한 값이 아니라 "대략적인" 값으로 읽어주세요. 제가 직접 여러 환경에서 테스트했을 때, 이 한계치는 정말 미묘하게 변하더군요. '대략 250KB'라고 말씀드리지만, 실제 서비스에서는 훨씬 보수적으로 접근해야겠다는 생각이 강하게 들었습니다. 이 부분은 저 또한 실무에서 꽤나 고생했던 기억이 납니다.

원인은 이전에 보았던 `String.fromCodePoint(...new Uint16Array(buf))` 라인 때문으로 보입니다. [`String.fromCodePoint`에 대한 MDN 페이지](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/String/fromCodePoint)에서 볼 수 있듯이, 이 함수는 입력값을 개별 인자로 받으므로, 스프레드 연산자는 두 바이트당 하나의 함수 인자를 전달하고, 각 인자는 호출 스택의 슬롯을 차지합니다. 두 가지 사실이 이를 뒷받침합니다.

*   **Next.js 없이도 재현됩니다.** 일반 Node.js에서 `String.fromCodePoint(...new Uint16Array(n))`는 약 125,235 요소를 초과하면 실패합니다.
*   **워밍업에 따라 변합니다.** 새 프로세스에서는 250,872바이트가 실패했지만, 300개의 다른 요청 후에는 동일한 크기가 통과되었고, 워밍업된 최대값은 250,899였습니다.

실험실에는 `--stack-size` 실험도 있습니다. 저는 제 시스템에서 직접 실행하지 않았으므로 이에 대한 주장을 하지 않습니다. 다른 시스템에서 실행된 참조 실행에서는 `--stack-size=500`일 때 한계가 대략 절반으로 줄었고, 2000일 때 대략 두 배로 늘었는데, 이는 스택 설명과 일치하지만 이는 제 측정치는 아닙니다.

따라서 암기할 정확한 숫자는 없습니다. 기본 스택에서는 약 240KB를 한계로 간주하고, 그보다 훨씬 낮은 수준으로 유지하세요. 그리고 이 문제를 피하기 위해 프로덕션에서 `--stack-size`를 높이지 마세요. 더 적은 데이터를 전달해야 합니다.

버퍼와 문자열에는 별도의 한계가 있습니다. Node `Buffer`는 정확히 1,000,000바이트에서, 문자열은 약 999,930자에서 다른 오류 메시지와 함께 실패합니다. 메시지는 "Maximum array nesting exceeded. Large nested arrays can be dangerous. Try adding intermediate objects."입니다. 이는 React의 Flight 디코더에서 발생하며, 기본 `arraySizeLimit`는 `1e6`입니다. 버퍼와 문자열이 왜 이 한계에 포함되는지는 추적하지 않았습니다. 다른 시스템의 참조 결과에서는 이 한계가 16.0.0 및 16.1.0에서는 없었고 16.1.7부터 존재했습니다. 저는 이 버전들을 직접 실행하지 않았습니다.

## 그렇다면 실질적으로 어떻게 해야 할까?

1.  **바이너리 값을 `use cache`에 전달한다면, 16.4.5 버전 이상으로 즉시 업그레이드하세요.**
2.  **파일 자체가 아닌 ID를 전달하세요.** 파일을 업로드한 후 저장소에 보관하고, 그 파일의 ID(문자열)를 캐시된 함수에 전달합니다. 캐시된 함수 내부에서 바이트를 읽어오도록 합니다. 이때 ID는 내용이 변경될 때마다 달라져야 하며, 콘텐츠 해시나 버전 번호를 사용하는 것이 좋습니다. 만약 편집된 내용에 대해 하나의 ID를 재사용하면, 캐시는 기꺼이 이전 결과를 반환할 것입니다. 간략한 예시는 다음과 같습니다.
    ```js
    export async function analyze(fileId) {
      "use cache";
      const bytes = await storage.read(fileId); // 캐시 내부에서 읽기
      return expensiveAnalysis(bytes);
    }
    ```
3.  **캐시된 함수의 인자로 바이너리 값을 사용자나 계정 식별자로 절대 사용하지 마세요.**
4.  **인자 크기를 작게 유지하세요.** 제 경험상 약 100KB 미만으로 유지하는 것이 좋습니다. 이는 최대 한계치보다 훨씬 여유 있는 마진을 제공합니다.
5.  **함수가 읽는 메타데이터만 전달하고, 폼 업로드에서 오는 `File.lastModified`는 전달하지 마세요.** 16.4.4 버전에서는 `name`, `type`, `size`를 별도의 인자로 전달함으로써 제가 발견한 이름, 타입, 그리고 후행 바이트 충돌을 막을 수 있었습니다(`npm run workaround`). 하지만 `lastModified`는 제가 직접 전달할 때까지 공유된 상태를 유지했습니다. 16.4.5 버전 이상에서는 이 세 가지가 이미 키에 포함됩니다. 하지만 `lastModified`는 포함되지 않으며, 멀티파트 폼을 통해 온 파일의 경우 서버가 요청을 파싱한 시간을 의미하므로, 이를 인자로 전달하면 모든 업로드 시 불필요한 캐시 미스가 발생할 수 있습니다. 수정 날짜가 필요하다면 별도의 폼 필드로 보내세요.
6.  **다른 곳에서 생성하는 객체 대신 원시 값을 전달하세요.**

## 제가 테스트하지 않은 것들

제 결과가 어디까지 유효한지 명확히 알려드리는 것이 여러분이 직접 문제를 발견하는 것보다 낫다고 생각합니다.

*   두 번째 캐시 핸들러 (Redis, `use cache: remote`) 또는 `use cache: private`.
*   페이지 및 컴포넌트 렌더링. 저는 라우트 핸들러와 한 서버 액션에서 캐시된 함수를 호출했습니다.
*   `next dev` 환경, 그리고 Node 외의 런타임.
*   후행 0이 있는 짝수 길이 바이트 배열. 코드에 따르면 충돌하지 않지만, 제 실험실은 3바이트와 4바이트 사례만 실행합니다.
*   16.4.4, 16.4.5, 16.4.6 버전 외의 버전들. 저장소의 참조 결과는 12개 버전을 다루지만, 이는 다른 시스템에서 얻은 결과이지 제가 직접 실행한 것이 아닙니다.
*   Next.js 15.x. 릴리스 게시물에 따르면 15.5.29도 동일한 릴리스에서 패치를 받았지만, 저는 16.x만 테스트했으므로 15.x에 대해서는 어떤 주장도 하지 않습니다.
*   다른 운영체제 및 Node 버전. 제 실행은 하나의 설정으로 이루어졌으며, 두 번째 시스템의 결과는 키 결과 측면에서 일치했습니다.
*   저는 Next.js의 TypeScript 소스가 아닌, 각 버전에서 제공되는 컴파일된 JavaScript를 읽었습니다.

## 직접 실행해 보세요

저장소에는 테스트 코드와 참조 결과가 있으므로, 이 모든 것을 직접 확인할 수 있습니다. 몇 가지 명령만으로 실행 가능합니다.

```bash
git clone https://github.com/shubhrapokhariya/nextjs-use-cache-key-lab.git
cd nextjs-use-cache-key-lab
npm run demo        # 위의 두 가지 예시 (첫 실행 시 Next.js 설치로 시간이 좀 걸립니다)
npm run quick       # 16.4.4, 16.4.5, 16.4.6에서 54쌍의 입력 테스트
npm run summarize
npm run diagnose    # 여러분의 빌드에서 키 함수를 출력합니다
npm run keys        # 앨리스/밥 및 후행 0 사례에 대한 실제 캐시 키를 출력합니다
npm run action      # 폼 업로드와 서버 액션을 통한 동일한 버그 테스트
npm run workaround  # 어떤 추가 인자들이 어떤 충돌을 피하는지 확인
npm run limits      # 크기 실험
```

`npm run quick`는 세 가지 버전을 테스트합니다. `npm run full`은 모든 12개 버전을 테스트하며 훨씬 오래 걸립니다. `limits` 스크립트에는 선택적인 스택 크기 실험이 포함되어 있으며, 여러분의 시스템에서 실패할 경우 이를 건너뛰는 방법이 README에 설명되어 있습니다. 이 실험실은 알려진 보안 권고가 있는 오래된 Next.js 버전을 설치하므로, 실제 서비스 서버가 아닌 임시 시스템에서 실행하세요.

54쌍의 입력값은 `template/app/lib/cases.js`에 있습니다. 여러분의 시스템에서 다르게 동작하는 사례를 발견한다면, 꼭 알려주시면 감사하겠습니다.

_Next.js는 자주 업데이트되므로, 동작이 변경되면 이 게시물을 업데이트할 예정입니다._
