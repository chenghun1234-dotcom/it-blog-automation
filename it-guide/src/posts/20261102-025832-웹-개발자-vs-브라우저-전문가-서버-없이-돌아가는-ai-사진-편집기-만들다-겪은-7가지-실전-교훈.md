# 웹 개발자 vs. 브라우저 전문가? 서버 없이 돌아가는 AI 사진 편집기 만들다 겪은 7가지 실전 교훈

**원본 저자:** Akhouri Anmol Kumar

**설명:** 기기 내 AI, WASM 스레드, 목표 크기 압축, 인페인팅, 3D LUT까지 단 하나의 HTML 파일로! APIC Web을 만들며 얻은 7가지 실제 교훈을 공개합니다.

---

대부분의 웹 개발자라면 폼을 만들고, API를 호출하고, `div`를 가운데 정렬하는 것쯤은 쉽게 해낼 겁니다. 하지만 '브라우저 전문가'는 한 단계 더 나아가죠. 브라우저가 특정 작업을 왜 거부하는지, 노트북에서 잘 되던 기능이 모바일에서는 왜 다르게 작동하는지, 그리고 서버 없이도 완벽한 소프트웨어를 어떻게 배포할 수 있는지 깊이 이해하고 있습니다.

저는 바로 이 지점에서 제가 어디에 속하는지 깨달았습니다. 바로 **APIC Web**을 개발하면서 말이죠. APIC Web은 무료 사진 편집기이자 배경, 객체 제거 도구, 변환기, 압축기인데, 가장 큰 특징은 **사용자의 사진이 디바이스를 절대 벗어나지 않는다**는 겁니다. 업로드 대기열도 없고, 백엔드도 없으며, 전체 앱이 GitHub Pages에 호스팅된 단 하나의 HTML 파일로 작동합니다.

아래 각 테스트는 APIC Web을 만들면서 실제로 겪었던 버그나 중요한 설계 결정들입니다. 여러분은 과연 몇 개나 알고 있었을까요? 솔직하게 점수를 매겨보세요. 👇

## 테스트 1: AI 작업이 모바일에서 소리 없이 멈춘 이유는 뭘까요?

APIC은 ONNX Runtime Web(WebAssembly)을 이용해 브라우저 내에서 AI 모델을 실행합니다. 여기서 멀티 스레드 WASM을 사용하려면 `SharedArrayBuffer`가 필요한데, 이를 위해서는 COOP/COEP 같은 특별한 응답 헤더가 필수적입니다. 하지만 GitHub Pages 같은 일반적인 정적 호스트는 이런 헤더를 전송하지 않기 때문에 `crossOriginIsolated` 값이 `false`가 됩니다.

데스크톱 환경에서는 보통 런타임이 이런 상황을 '우아하게' 처리하며 단일 스레드로 전환되지만, 모바일에서는 그렇지 않은 경우가 많아 AI 단계가 아무런 에러 메시지 없이 그냥 멈춰버리는 현상을 겪었습니다. 해결책은 이런 모호한 폴백(fallback) 동작에 의존하는 대신, 모든 환경에서 동일하게 작동하도록 설정을 강제하는 것이었습니다.

```js
// 정적 호스트는 COOP/COEP를 보낼 수 없으므로 스레드를 사용할 수 없습니다.
// 모든 곳에서 동일하게 작동하는 한 가지 구성만 강제합니다.
ort.env.wasm.numThreads = 1;
ort.env.wasm.proxy = false;

const session = await ort.InferenceSession.create(modelBytes, {
  executionProviders: ['wasm'],
  enableCpuMemArena: false,
  enableMemPattern: false,
});
```

물론 헤더를 사용할 수 있는 환경에서는 APIC이 `self.crossOriginIsolated`를 먼저 확인하여 더 많은 스레드를 요청하도록 설계되어 있습니다. 제가 실무에서 모바일 환경 최적화를 할 때, 데스크톱에서 완벽히 작동하던 기능이 모바일에서 버벅이거나 아예 멈추는 경우가 허다했습니다. 특히 WebGL이나 WASM 관련 작업은 더욱 그랬죠. 단순히 "내 노트북에선 잘 되는데?"라고 생각하는 순간, 수많은 모바일 사용자를 놓칠 수 있다는 걸 다시 한번 깨달았습니다.

**일반 개발자:** "내 노트북에선 잘 작동하는데요."
**브라우저 전문가:** '우아하게 폴백된다'는 주장은 실제 모바일 기기에서 반드시 테스트해야 할 과제이지, 맹목적으로 믿을 약속이 아니라는 것을 압니다.

## 테스트 2: 느린 다운로드와 끊긴 다운로드를 구분할 수 있나요?

APIC의 AI 모델들은 용량이 꽤 큽니다. 배경 제거용으로는 최소 5MB(Lite)부터 최대 176MB(Maximum), 객체 제거 모델은 가장 고품질 버전이 약 208MB에 달하죠. 이런 대용량 모델을 느린 모바일 네트워크 환경에서 다운로드할 때, 무조건 30초 같은 고정된 타임아웃을 설정하면 연결은 살아있지만 느리게 다운로드되는 모든 경우를 끊어버릴 겁니다.

그래서 APIC은 **정체 기반(stall-based) 타임아웃**을 사용합니다. 스트림에서 40초 동안 아무런 바이트도 전송되지 않을 때만 다운로드를 중단하는 방식이죠. 덕분에 불안정한 Wi-Fi 환경에서 거대한 모델을 다운로드하더라도 필요한 시간만큼 기다려줄 수 있습니다. 물론 완전히 끊긴 링크는 바로 차단합니다. 한번 다운로드된 모델은 Cache API에 저장되어 다음 실행 시에는 즉시 로드됩니다.

```js
const CACHE = 'apic-models-v1';
const cache = await caches.open(CACHE);

let hit = await cache.match(url);
if (hit) return hit.arrayBuffer();           // 캐시됨: 다운로드 없음

const bytes = await downloadWithStallTimeout(url);   // 스트림이 조용해지면 중단
await cache.put(url, new Response(bytes));   // try/catch로 감싸야 합니다: 비공개 모드 및 할당량으로 인해 실패할 수 있음
return bytes;
```

만약 어떤 모델도 아예 로드할 수 없는 상황이 오면, APIC은 완전히 실패하는 대신 더 간단한 도구로 **단계적으로 전환**합니다. 예를 들어, Ultra(LaMa) 모델이 안 되면 MI-GAN으로, 그것도 안 되면 빠른 패치 채우기 방식으로 넘어가는 식이죠.

**일반 개발자:** 단순히 `fetch()`에 타임아웃을 걸어둡니다.
**브라우저 전문가:** 다운로드 진행 상황을 측정하고, 결과를 캐시하며, 항상 비상 계획(Plan B)을 준비합니다.

## 테스트 3: "200KB 이하" 목표를 대충 찍지 않고 달성할 수 있나요?

많은 업로드 폼에서 "최대 200KB" 같은 파일 크기 제한을 요구합니다. 사용자들은 이 제한에 맞추기 위해 품질 슬라이더를 이리저리 움직이며 '룰렛 게임'을 하곤 합니다. APIC의 압축 도구는 이런 추측 대신, JPEG 품질에 대한 **이진 탐색**을 수행합니다.

```js
async function findQualityForTarget(canvas, targetBytes) {
  let lo = 0.05, hi = 0.98, best = null;
  for (let i = 0; i < 7; i++) {
    const mid = (lo + hi) / 2;
    const blob = await toBlob(canvas, 'image/jpeg', mid);
    if (blob.size <= targetBytes) { best = { blob, q: mid }; lo = mid; }  // 맞으면: 더 높은 품질 시도
    else { hi = mid; }                                                   // 너무 크면: 품질 낮춤
  }
  return best;
}
```

7번의 인코딩 시도를 통해 목표 바이트 내에서 가장 높은 품질을 찾아냅니다. 만약 가장 낮은 품질로도 파일이 너무 크다면, APIC은 이미지를 약 20% 줄이고 다시 검색하는 과정을 최대 8번 반복합니다. 그럼에도 불구하고 목표를 달성할 수 없다면, 불가능하다고 거짓말하는 대신 **실제 파일 크기**를 사용자에게 정확히 알려줍니다.

**일반 개발자:** `quality = 0.7`처럼 임의의 값을 설정하고 잘 되길 바랍니다.
**브라우저 전문가:** 막연한 추측을 정밀한 탐색으로 바꾸고, 불가능할 땐 솔직하게 인정합니다.

## 테스트 4: 투명한 PNG를 JPEG로 변환했더니 왜 검은색으로 변했나요?

JPEG는 알파 채널을 지원하지 않습니다. 투명한 픽셀이 있는 캔버스를 JPEG로 인코딩하면, 그 투명한 부분들이 결국 **검은색**으로 나타나게 됩니다. 배경을 제거하여 투명한 영역이 많이 생긴 이미지의 경우, 이 문제는 꽤나 불쾌한 결과를 초래할 수 있습니다.

해결책은 간단합니다. 먼저 캔버스에 흰색 배경을 칠한 다음, 그 위에 이미지를 그리는 것이죠.

```js
function flattenToWhite(src) {
  const out = document.createElement('canvas');
  out.width = src.width; out.height = src.height;
  const ctx = out.getContext('2d');
  ctx.fillStyle = '#fff';
  ctx.fillRect(0, 0, out.width, out.height);
  ctx.drawImage(src, 0, 0);
  return out;
}
```

APIC은 또한 변환 패널에서 어떤 형식이 투명도를 유지하고(PNG, WebP), 어떤 형식이 유지하지 않는지 사용자에게 명확하게 알려줍니다. 제가 실제 프로젝트에서 이 부분을 간과했을 때, 클라이언트로부터 "분명 투명한 배경이었는데 왜 시커멓게 나왔나요?"라는 불평을 들었던 기억이 생생합니다. 단순한 픽셀 작업이라 생각하기 쉽지만, 파일 형식별 특성을 이해하는 것이 얼마나 중요한지 깨닫는 순간이었죠.

**일반 개발자:** 캔버스는 그냥 픽셀의 집합이라고 생각합니다.
**브라우저 전문가:** 모든 출력 형식이 알파 채널에 대한 고유한 규칙을 가지고 있다는 것을 압니다.

## 테스트 5: 이미지 전체를 처리하나요, 아니면 변경된 부분만 처리하나요?

객체 제거는 인페인팅 모델(LaMa, 또는 경량화된 MI-GAN)을 실행하는 것을 의미합니다. LaMa는 고정된 **512x512** 크기의 윈도우에서 작동하기 때문에, 12메가픽셀짜리 사진 전체를 모델에 넣는다면 엄청나게 느릴 뿐만 아니라 결과물의 품질도 저하될 수 있습니다.

APIC은 사용자가 브러시로 마스킹한 **주변 영역만 처리합니다.**
1.  마스크 주변 영역을 추출합니다 (사진이 허용하는 한 최소 512 고유 픽셀).
2.  이 잘라낸 영역에만 모델을 실행합니다.
3.  가장자리를 박스 블러로 부드럽게 처리하고, 채워진 부분의 색상을 주변과 일치시키며, "너무 깨끗해" 보이지 않도록 필름 그레인을 다시 추가합니다.
4.  원본 이미지에 다시 붙여넣습니다.

작은 편집은 적은 컴퓨팅 자원을 사용하며, 사진의 나머지 부분은 **전혀 건드리지 않습니다.** 이는 사용자 경험 측면에서 지연 시간을 줄여줄 뿐 아니라, 불필요한 연산을 막아 전력 소모도 줄이는 효과적인 방법입니다.

**일반 개발자:** 이미지 전체에 모델을 실행합니다.
**브라우저 전문가:** 문제를 먼저 작게 축소하고, 그 결과를 다시 원본에 자연스럽게 블렌딩하여 경계가 보이지 않게 만듭니다.

## 테스트 6: 여러분의 전체 색 보정 값을 `.cube` LUT 파일로 내보낼 수 있나요?

APIC은 커브, 8밴드 HSL 믹서, 3방향 색 보정 등 전문가 수준의 색상 조절 기능을 제공합니다. 사용자들은 이렇게 만든 색상 그레이딩을 DaVinci Resolve나 Premiere Pro 같은 다른 영상 편집 소프트웨어에서도 사용하고 싶어 했습니다. 여기서 `.cube` 파일은 3D 룩업 테이블(LUT)로, 특정 입력 색상에 대해 어떤 출력 색상이 나와야 하는지를 정의하는 파일입니다.

해결책은 의외로 간단합니다. 여러분이 적용한 픽셀 함수에 대해 **'아이덴티티 그리드'(identity grid)**, 즉 모든 가능한 색상을 체계적으로 나열한 색상표를 입력으로 넣고, 그 결과로 나오는 색상을 기록하면 됩니다.

```js
const N = 33;                       // 33×33×33 격자
const buf = new Uint8ClampedArray(N * N * N * 4);
let i = 0;
for (let b = 0; b < N; b++)
  for (let g = 0; g < N; g++)
    for (let r = 0; r < N; r++) {   // .cube 요구사항에 따라 빨강이 가장 빠르게 변화
      buf[i++] = Math.round(r / (N - 1) * 255);
      buf[i++] = Math.round(g / (N - 1) * 255);
      buf[i++] = Math.round(b / (N - 1) * 255);
      buf[i++] = 255;
    }

processPixels(buf, gradeWithoutSpatialEffects);   // 사진을 편집하는 동일한 코드

const lines = ['TITLE "APIC grade"', 'LUT_3D_SIZE 33',
               'DOMAIN_MIN 0.0 0.0 0.0', 'DOMAIN_MAX 1.0 1.0 1.0', ''];
for (let j = 0; j < buf.length; j += 4)
  lines.push(`${(buf[j]/255).toFixed(6)} ${(buf[j+1]/255).toFixed(6)} ${(buf[j+2]/255).toFixed(6)}`);
```

한 가지 주의할 점이 있습니다. LUT는 오직 **색상** 관련 작업만 담을 수 있습니다. 선명도, 샤프닝, 비네팅, 그레인 같은 효과들은 주변 픽셀에 의존하는 공간적 효과이므로 LUT에 포함될 수 없습니다. APIC은 이런 점을 사용자 인터페이스에서 명확하게 안내해 줍니다.

**일반 개발자:** 보정된 결과물의 스크린샷을 내보냅니다.
**브라우저 전문가:** 함수 자체를 샘플링하여 재현 가능한 결과물을 만듭니다.

## 테스트 7: 이미지 크기를 줄였는데 왜 흐릿하게 보일까요?

```js
ctx.drawImage(img, 0, 0, smallW, smallH);   // 한 번에 크게 줄이면: 흐릿하고 앨리어싱 발생
```

큰 이미지를 `drawImage` 호출 한 번으로 급격하게 축소하면 결과물이 전반적으로 흐릿하고 앨리어싱(계단 현상)이 생길 수 있습니다. APIC의 크기 조절 도구는 이런 문제를 해결하기 위해 **이미지를 단계적으로 절반씩 축소합니다.** 목표 크기의 2배 이내로 줄어들 때까지 이 과정을 반복한 다음, 마지막으로 한 번 더 최종 목표 크기로 다듬는 방식을 사용합니다.

```js
function highQualityResize(src, targetW, targetH) {
  let cur = src, w = src.width, h = src.height;
  while (w > targetW * 2 || h > targetH * 2) {
    const nw = Math.max(targetW, Math.round(w / 2));
    const nh = Math.max(targetH, Math.round(h / 2));
    const step = document.createElement('canvas');
    step.width = nw; step.height = nh;
    const c = step.getContext('2d');
    c.imageSmoothingEnabled = true;
    c.imageSmoothingQuality = 'high';
    c.drawImage(cur, 0, 0, nw, nh);
    cur = step; w = nw; h = nh;
  }
  // ...그 다음, 정확한 목표 크기로 마지막 고품질 패스를 적용합니다.
}
```

이렇게 여러 단계를 거쳐 이미지를 축소하면, 단 한 번에 줄이는 것보다 훨씬 선명하고 깨끗한 결과물을 얻을 수 있습니다. 제가 처음 이 문제를 마주했을 때, `drawImage` 하나면 충분하다고 생각했지만, 결과물 품질이 너무 낮아 당황했던 기억이 납니다. 이미지 처리에서는 연산의 순서와 방식이 최종 결과에 얼마나 큰 영향을 미치는지 보여주는 좋은 예시죠.

**일반 개발자:** `drawImage` 한 번 호출하고 넘어갑니다.
**브라우저 전문가:** 연산의 순서가 결과물을 바꾼다는 것을 알고 있습니다.

## 보너스: 단일 HTML 파일 안에 웹 워커를 어떻게 포함시킬까요?

별도의 빌드 과정도 없고, 따로 `worker.js` 파일도 만들고 싶지 않다면 어떻게 해야 할까요? APIC은 워커의 소스 코드를 문자열 형태로 저장한 다음, 이 문자열을 Blob으로 변환하고, Blob URL을 이용해 워커를 실행하는 방식을 사용합니다.

```js
const SRC = `/* 워커 코드를 문자열로 */`;
const worker = new Worker(
  URL.createObjectURL(new Blob([SRC], { type: 'application/javascript' }))
);
```

이 덕분에 무거운 인페인팅 작업이 메인 스레드에서 벗어나 백그라운드에서 처리되면서도, 전체 앱은 여전히 **하나의 파일**로 어디든 호스팅할 수 있습니다.
