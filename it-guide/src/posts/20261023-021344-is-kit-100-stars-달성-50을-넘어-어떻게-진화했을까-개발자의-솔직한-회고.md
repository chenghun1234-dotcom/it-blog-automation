## ⭐ 50 Stars, 그때는 어떤 의미였을까요?

50 스타를 달성했을 때 제가 가장 보여주고 싶었던 건, [`is-kit`](https://github.com/nyaomaru/is-kit)이 단순히 장난감 같은 토이 프로젝트가 아니라는 점이었어요. 이미 실제 프로덕션 애플리케이션에서 활발하게 사용되고 있었죠. 🚀

그 애플리케이션은 아래와 같은 반복적인 런타임 검사를 수없이 수행하고 있었습니다.

```ts
typeof value === "string";
typeof value === "number";
value === null || value === undefined;
```

또한, HTTP 에러, 리터럴 유니온, 배열, API 값, 일반 객체 등 다양한 케이스를 위한 사용자 정의 타입 가드도 여러 개 필요했고요.

여기서 흥미로웠던 점은 `is-kit`이 이러한 검사 로직을 단순히 짧게 만들어줬다는 것이 아니었습니다. 진짜 매력은 `is-kit`이 이 모든 검사에 **재사용 가능한 하나의 통일된 형태**를 부여했다는 사실이었죠.

작은 가드들은 서로 조합될 수 있었습니다. 애플리케이션 고유의 헬퍼 함수들을 라이브러리와 피처 코드 사이에 두고 활용할 수도 있었고요. 그럼에도 불구하고 결과물은 TypeScript의 일반적인 제어 흐름에 완벽하게 통합될 수 있었습니다.

이 핵심적인 가치는 변하지 않았습니다. 하지만 50 스타 이후로 라이브러리 자체는 꽤나 많은 발전을 거듭했습니다. 👀

## 🔑 객체 속성 정제(Property Refinement)가 핵심 사용 사례로 부상하다

제가 개발하면서 계속해서 마주쳤던 한 가지 패턴이 있습니다.

> "이미 훌륭한 타입 가드가 있는데, 이걸 객체의 **특정 속성 하나에만 적용**하고 싶다."

예를 들어볼까요.

```ts
declare const input: unknown;
```

저는 이미 문자열을 검증하는 방법을 알고 있습니다.

```ts
import { isString } from "is-kit";
```

하지만 이제 "이 객체는 `name`이라는 속성을 가지고 있고, 그 속성은 문자열이다"라는 로직을 표현하고 싶습니다.

간단해 보이지만, 실제로는 몇 가지 다른 경우가 존재합니다. **필수 속성**은 **선택적 속성**과 다릅니다. **배열 인덱스**는 **객체 속성**과 다르고요. 그리고 정의된 것으로 알려진 **선택적 속성**은 여전히 선택적인 속성과는 다르게 타입을 좁혀야 합니다.

이러한 요구사항을 해결하기 위해 `is-kit`은 세 가지 속성 정제(property refinement) 헬퍼를 추가했습니다.

-   `refineKey`
-   `refineDefinedKey`
-   `refineIndex`

아이디어는 간단합니다. "이미 신뢰하는 타입 가드를 가져와서, 이를 객체의 특정 속성이나 배열 요소에 적용한다."

예를 들면 다음과 같습니다.

```ts
import { isString, refineKey } from "is-kit";

const hasStringName = refineKey("name", isString);
```

이제 문자열 가드는 또 다른 커스텀 타입 가드 안에 재작성될 필요 없이, 더 깊은 수준에서 재사용 가능해집니다. 제가 실무에서 객체 속성 검증 때문에 몇 번 헤맸던 경험이 있는데, 이 `refineKey` 같은 기능이 그때 있었다면 얼마나 좋았을까 싶더군요. 작은 API지만, `is-kit`의 다른 기능들과 마찬가지로 "하나의 거대한 유효성 검사기를 만들지 마라"는 핵심 설계 목표를 따르고 있어서 개인적으로 매우 만족하는 기능입니다.

**작고 재사용 가능한 검사 로직을 만들고, 이를 일반적인 TypeScript 코드에서 활용하자.** 이것이 `is-kit`의 철학입니다.

## 🔍 그리고 `discriminatedUnion`은 훨씬 더 강력해졌다

50 스타 기사 이후 가장 큰 추가 기능은 아마도 `v1.15.0`에 도입된 완벽한 식별된 유니온(discriminated union) API일 것입니다.

흔히 사용되는 TypeScript 타입을 생각해볼까요?

```ts
type Result = { ok: true; value: string } | { ok: false; error: string };
```

런타임에 이 타입을 검증하는 것은 그리 어렵지 않습니다. `ok` 속성을 확인한 다음, 해당 필드를 검증하면 됩니다.

하지만 또 다른 질문이 생깁니다.

> "TypeScript가 유효성 검사기 자체가 전체 유니온을 커버하는지 확인할 수 있을까?"

바로 이 지점에서 `discriminatedUnion`이 빛을 발합니다.

```ts
import { discriminatedUnion, isString, oneOfValues, typedStruct } from "is-kit";

type Result = { ok: true; value: string } | { ok: false; error: string };

const resultUnion = discriminatedUnion<Result>();

export const isResult = resultUnion("ok", [true, false], {
  true: typedStruct<Extract<Result, { ok: true }>>()({
    ok: oneOfValues(true),
    value: isString,
  }),
  false: typedStruct<Extract<Result, { ok: false }>>()({
    ok: oneOfValues(false),
    error: isString,
  }),
});
```

런타임 동작은 물론 유용합니다. 하지만 더 흥미로운 부분은 컴파일 타임 계약입니다. 빌더는 다음과 같은 사항들을 검사합니다.

-   누락된 식별자 브랜치
-   불필요한 브랜치
-   호환되지 않는 브랜치 가드
-   불완전한 식별자 튜플

따라서 유니온 타입이 변경되더라도, 타입 가드가 소리 없이 불완전한 상태로 남아있을 수 없습니다.

이 점이 중요한 이유는, 수동으로 작성된 타입 가드가 위험해지는 가장 쉬운 방법 중 하나가 바로 **"타입 드리프트(drift)"**이기 때문입니다. TypeScript 타입은 진화하지만, 런타임 가드는 그렇지 않습니다. 그리고 컴파일러는 일반적으로 이 둘이 더 이상 일치하지 않는다는 것을 알려주지 못하죠. `discriminatedUnion`은 이러한 종류의 실수를 어렵게 만들기 위한 시도 중 하나입니다.

## 💪 라이브러리는 더 엄격해졌다

50 스타와 100 스타 사이의 모든 개선 사항이 새로운 기능 추가만 있었던 것은 아닙니다. 기존 동작을 더욱 정밀하게 만드는 데 많은 노력이 투입되었습니다.

예를 들어, 최근 릴리스에는 다음과 같은 부분에 대한 수정이 포함되었습니다.

-   `recordOf` 리터럴 키 추론
-   네이티브 `Error` 브랜드 체크
-   오버라이드된 이터레이터를 가진 배열 가드
-   정확한 `struct` 유효성 검사
-   심볼 키를 사용하는 구조체 스키마
-   크로스-렐름 구조체 스키마

패키지 수준의 테스트도 강화되었습니다. `is-kit`은 이제 발행된 패키지가 ESM 및 CommonJS TypeScript 소비자 모두에서 올바르게 동작하는지 확인하며, `Deno` / `JSR` 스모크 테스트 커버리지도 확보했습니다.

이 부분은 코드 스니펫으로 보여주기에는 덜 흥미롭습니다. 하지만 작은 라이브러리에게는 매우 중요하다고 생각합니다. 이상한 JavaScript 및 TypeScript 환경에서도 올바르게 작동하는지 확인하는 것이야말로 라이브러리를 진정으로 "실전"에 투입하는 과정이니까요.

## 🤖 다른 오픈소스 프로젝트에서도 `is-kit`을 사용하기 시작하다

50 스타를 달성한 이후로, 저 역시 `is-kit`을 제가 관리하는 다른 오픈소스 프로젝트에서 더 자연스럽게 사용하기 시작했습니다.

예를 들어, 제 변경 로그 툴인 [`changelog-bot`](https://github.com/nyaomaru/changelog-bot)에서는 작은 조건자를 재사용하고 조합할 수 있도록 `define`을 사용하고 있습니다. 모든 런타임 검사를 개별적인 헬퍼로 만들지 않고요.

간단한 예시는 다음과 같습니다. 👇

```ts
import { define, oneOfValues } from "is-kit";

const CHANGELOG_SECTIONS = ["Added", "Changed", "Fixed", "Removed"] as const;

const isChangelogSection = define<(typeof CHANGELOG_SECTIONS)[number]>(
  oneOfValues(CHANGELOG_SECTIONS),
);
```

정확한 코드가 중요한 것은 아닙니다. 저에게 변화가 생긴 것은 더 이상 "내 라이브러리를 여기에서 사용해야지"라고 생각하지 않게 되었다는 점입니다. 그냥 필요한 가드를 자연스럽게 사용합니다. 사실, 저도 처음엔 '내 라이브러리 써야지!' 하는 의무감도 살짝 있었지만, 지금은 그냥 자연스럽게 손이 갈 정도로 익숙해졌습니다. 이게 진짜 효용성을 느낄 때 오는 변화 같아요.

라이브러리가 스스로를 시연하는 데 그치지 않고, 관리자에게도 유용하다고 느껴질 때 비로소 그 진정한 가치를 발휘하기 시작한다고 생각합니다.

## 🚀 그리고 `is-kit` 가드가 Effect 타입 버그를 찾아내다

최근에 일어난 일 중 가장 흥미로운 사건이었습니다. `is-kit` 사용자가 Effect의 `catchIf`와 함께 타입 가드를 사용하고 있었죠.

개념적으로 타입 정제는 다음과 같았습니다. 👇

```ts
(error: unknown): error is SomeError => ...
```

이것은 `is-kit`에게는 완전히 정상적인 사용법입니다. 사실, `unknown`은 라이브러리가 설계된 정확한 시작 지점이니까요.

하지만 `Effect.catchIf`에서는 이 정제가 예상치 못한 방식으로 제네릭 추론에 영향을 미칠 수 있었습니다. 에러 채널이 `unknown`으로 확장될 수 있었던 것이죠.

이 보고된 케이스는 결국 Effect PR로 이어졌고, 성공적으로 머지되었습니다! 👏 🚀

[Effect-TS/effect PR #9252](https://github.com/Effect-TS/effect/pull/9252)

관련 타입은 원래 대략 다음과 같았습니다.

```ts
refinement: Predicate.Refinement<E, EB>;
```

그리고 수정 후에는 이렇게 바뀌었습니다.

```ts
refinement: Predicate.Refinement<NoInfer<E>, EB>;
```

여기서 중요한 아이디어는 **정제의 입력 타입이 `Effect`에 의해 이미 설정된 에러 타입을 재정의하도록 허용해서는 안 된다**는 것입니다.

해당 PR은 또한 다음과 같은 케이스에 대한 타입 테스트도 추가합니다.

```ts
const result = Effect.catchIf(
  mixedEffect,
  (e: unknown): e is AiError => e instanceof AiError,
  () => Effect.succeed("ok"),
);
```

수정 전에는 정제 입력이 추론에 참여하여 에러 채널을 확장할 수 있었습니다. `NoInfer`를 사용함으로써, 원래의 에러 타입이 진실의 원천으로 유지됩니다.

동일한 패턴이 `Channel`과 `Stream`에서도 수정되었습니다. 이 문제에 대한 Bluesky 게시물도 있습니다.

[Bluesky post about the Effect issue](https://bsky.app/profile/evadeva.bsky.social/post/3mxwiqfeo3s2j)

저는 이 버그가 정말 마음에 들었습니다. **제가 `is-kit`만 단독으로 테스트해서는 절대 발견할 수 없었을 상호작용**에서 비롯되었기 때문이죠. `is-kit`이 `Effect`를 "망가뜨린" 것도 아니었고, `Effect`가 터무니없는 행동을 한 것도 아니었습니다. 그것은 제네릭 API와 의도적으로 넓은 입력 타입을 가진 정제 사이에 발생하는 미묘한 TypeScript 추론 상호작용이었습니다. 이런 교차 검증은 혼자서는 절대 발견하기 힘든 보석 같은 피드백이죠. 실전에서 부딪히며 성장하는 라이브러리를 볼 때마다 짜릿함을 느낍니다.

이것이야말로 라이브러리들이 실제 코드에서 서로 만나기 시작할 때 나타나는 종류의 엣지 케이스입니다.

## 👍 제가 원했던 피드백은 바로 이런 것입니다

`is-kit`이 50 스타를 달성했을 때 저는 이렇게 썼습니다.

> "누군가 이 아이디어를 유용하게 생각했다."

그것만으로도 이미 충분히 행복했습니다.

100 스타도 여전히 라이브러리가 거대하다는 것을 의미하지는 않습니다. 별의 개수는 여전히 벤치마크가 아닙니다. 정확성을 증명하는 것도 아니고요. 그리고 모든 TypeScript 프로젝트가 `is-kit`을 설치해야 한다는 것을 의미하는 것은 더욱 아닙니다.

하지만 뭔가 달라졌습니다.

사람들은 더 이상 단순히 저장소에 스타만 누르지 않습니다. 그들은 이제

-   라이브러리를 사용하고
-   질문하고
-   엣지 케이스를 발견하고
-   버그를 보고하고
-   다른 유효성 검사 방식과 비교하고
-   `is-kit` 가드를 다른 TypeScript 라이브러리와 함께 사용하고
-   이미 완성되었다고 생각했던 API를 다시 고민하게 만듭니다.

이것은 숫자 그 자체보다 훨씬 더 값진 것입니다. 💖

## 💬 프로젝트를 설명하기도 더 쉬워졌다

50 스타와 100 스타 사이 또 다른 변화는, `is-kit`이 **아닌 것**에 대해 제가 훨씬 더 명확해졌다는 점입니다.

`is-kit`은 모든 스키마 라이브러리를 대체하려는 것이 **아닙니다**.
모든 런타임 값을 스키마 우선 워크플로우로 전환하려는 것도 **아닙니다**.
그리고 일반적인 TypeScript 제어 흐름을 숨기려 하지도 **않습니다**.

핵심 질문은 여전히 매우 작습니다.

> **"이 `unknown` 값은 이 브랜치로 안전하게 진입할 수 있는가?"**

때로는 스키마 라이브러리가 올바른 해답일 수 있습니다. 예를 들어, 다음과 같은 기능이 필요하다면

-   풍부한 유효성 검사 에러
-   값 변환
-   폼 유효성 검사
-   시스템 간 공유되는 계약

`Zod`, `Valibot`, `ArkType` 또는 다른 스키마 라이브러리가 더 적합할 것입니다.

하지만 때로는 이미 일반적인 TypeScript 코드가 있고, 단순히 재사용 가능한 타입 좁히기(narrowing) 함수만 필요한 경우가 있습니다. 바로 그 지점에서 `is-kit`이 유용하게 사용되기를 바랍니다.

```ts
if (isUser(value)) {
  value.id;
}

if (isHttpClientError(error)) {
  // HTTP 클라이언트 에러 처리
}

items.filter(isString);

result.catch(isHttpClientError);

const isMaybeNumber = nullish(isNumber);
```

작은 런타임 결정.
일반 함수.
일반 TypeScript.

## 🐱 100 Stars가 저에게 의미하는 것

100 스타는 가장 큰 TypeScript 오픈소스 프로젝트들에 비하면 여전히 작은 숫자입니다. 괜찮습니다.

저에게 중요한 것은 프로젝트가 스타 카운터와는 아무런 관련 없는 방식으로 더욱 "실제"가 되어가고 있다는 점입니다. 50 스타 이정표 이후로:

-   새로운 API가 추가되었습니다.
-   기존 API가 더욱 엄격해졌습니다.
-   런타임 엣지 케이스가 수정되었습니다.
-   패키지 호환성 테스트가 개선되었습니다.
-   제가 다른 오픈소스 프로젝트에서 `is-kit`을 자연스럽게 사용하기 시작했습니다.
-   외부 사용으로 인해 저 혼자서는 만들 수 없는 피드백이 생성되었습니다.
-   `unknown` 기반 정제가 Effect의 추론 엣지 케이스를 노출하는 데 도움이 되기까지 했습니다.

마지막 부분이 아마도 제가 가장 좋아하는 부분일 것입니다. 애초에 목표는 그저 `README`에서만 멋지게 보이는 라이브러리를 만드는 것이 아니었으니까요!

목표는 **재사용 가능한 런타임 타입 좁히기(narrowing) 기능이 실제 TypeScript 코드 내에서 자연스럽게 작동하도록 만드는 것**입니다. 그리고 이제는 제 저장소 밖에서도 이런 일들이 일어나는 것을 보기 시작했습니다.
