# 더 이상 이메일에 끌려다니지 마세요: TabPFN, Gemma, Temporal로 만든 AI 비서 'Let It Die'

*이 글은 [Hacktoberfest 오픈소스 AI 챌린지 3주차: Slow and Steady](https://dev.to/challenges/hacktoberfest-week3-2026-10-19) 제출작입니다.*

## 제가 만든 것은?

대부분의 '게으른' 에이전트들은 당신의 잡무를 더 빨리 처리해 줍니다. 하지만 제가 만든 'Let It Die'는 한 걸음 더 나아가, 애초에 그 잡무를 *해야 할 필요가 있는지* 묻습니다.

이 친구는 새로 도착한 이메일을 읽고, 해당 이메일을 무시했을 때 발생할 수 있는 잠재적 손실 가능성에 따라 점수를 매깁니다. 그리고 그 점수에 따라 다음 세 가지 중 하나의 조치를 취합니다.

*   **확인 필요 (Need you)** (점수 상위 20%): 로컬에서 구동되는 Gemma 모델이 두 줄짜리 요약과 제안된 행동을 작성하여 아침 다이제스트에 포함시킵니다.
*   **낮은 우선순위 (Low priority)** (중간 60%): 특별한 조치 없이 내버려 두며, 다이제스트에 단순히 집계됩니다.
*   **사라져라 (Let it die)** (하위 20%): Temporal 타이머에 7일간 '주차'됩니다. 만약 발신자가 7일 이내에 다시 답장을 보내면, 해당 이메일은 '확인 필요'로 격상됩니다. 아무런 후속 조치가 없다면, 자동으로 보관 처리됩니다.

메일함이 알아서 정리되는 것을 경험해 본 사람이라면 누구나 조금 더 게을러질 수 있습니다. 가장 저렴한 작업은 애초에 시작하지 않는 것이죠. 중요한 건 어떤 작업을 시작하지 말아야 할지 정확히 알아내는 것입니다. 제가 보유한 테스트 이메일 1,981개 중 398개(20%)가 주차되었고, 이 중 약 85%는 실제로 답장이 필요 없었습니다. 제가 실무에서 이 부분을 테스트해 봤을 때, 이런 자동화된 분류가 주는 정신적 여유는 단순히 시간 절약 이상의 가치가 있다는 것을 깨달았습니다.

## 어떻게 만들었을까요?

```plaintext
이메일 -> TabPFN 점수 -> 분류 -+- 확인 필요 -> Gemma 요약 -> 아침 다이제스트
                                  +- 낮은 우선순위 -> 집계만
                                  +- 사라져라 -> Temporal 타이머 (7일)
                                                    +- 후속 신호 -> 격상
                                                    +- 타임아웃 -> 보관
```

*   **TabPFN** (Prior Labs)은 이메일이 도착하기 전에 사용 가능한 정보(발신자 이력, 수신자, 시간대, 제목 및 본문 단서, 스레드 길이)만으로 '7일 이내에 소유자가 답장했는지 여부'를 예측합니다. 놀랍게도 별도의 학습 과정이 필요 없다는 점이 가장 큰 특징입니다. 제가 실무에서 TabPFN을 접했을 때 가장 놀랐던 점은 바로 이 '학습 과정이 필요 없다'는 점이었죠. 복잡한 모델 훈련 없이도 뛰어난 예측 성능을 보여준다는 것이 인상 깊었습니다.
*   **Gemma** (Ollama를 통해 로컬에서 구동되는 gemma3:4b)는 '확인 필요' 버킷에 대한 이메일 요약과 제안된 행동을 작성합니다. 모든 처리가 로컬에서 이루어지기 때문에 개인 정보 보호 측면에서 안심할 수 있습니다.
*   **Temporal**은 주차된 이메일당 하나의 워크플로우를 실행합니다. 후속 신호가 오거나 7일의 타임아웃이 발생할 때까지 기다린 다음, 이메일을 격상시키거나 보관 처리합니다. 데모에서는 Temporal의 시간 건너뛰기 테스트 서버를 사용하여 일주일의 대기 시간을 몇 초 만에 처리했습니다. 제가 의도적으로 첫 번째 보관 시도를 실패하게 만들었을 때, Temporal은 모든 이메일을 자동으로 재시도했고, 7개의 보관된 이메일 모두 두 번째 시도를 기록했습니다. 프로젝트를 진행하며 Temporal의 견고함에 다시 한번 감탄했습니다. 특히 제가 테스트 환경에서 의도적으로 실패를 유도했을 때, 자동으로 재시도하며 안정적으로 작업을 처리하는 모습을 보고 '이게 바로 프로덕션 레벨의 내구성이지!' 싶었죠.
*   **Sentry**는 전체 실행 과정을 추적합니다. 에이전트, 분류 단계, 각 Gemma 호출(모델, 토큰 수, 전체 프롬프트 및 응답) 및 Temporal 단계를 모두 기록합니다. 총 23초 중 약 22초가 다섯 번의 로컬 Gemma 호출(각각 127.0.0.1, 즉 제 로컬 머신에 대한 HTTP 호출)에 소요되었습니다. 분류는 약 1밀리초, 8개의 이메일 주차는 약 1.3초가 걸렸습니다.

**데이터에 대하여.** 저만의 양방향 메일함이 없었기 때문에, 공개된 Enron 말뭉치(CMU, 2015년 5월 릴리스)에서 약 28,000개의 메시지가 있는 메일함 하나를 사용했습니다. 여기에는 보낸 편지함도 포함되어 있어 답장 여부 레이블을 파생할 수 있었습니다. 레이블은 "소유자가 7일 이내에 같은 스레드에 답장했음"으로 정의했습니다. 2001년 5월 이후에는 보낸 메일이 보관되지 않아, 이후의 모든 이메일은 답장되지 않은 것처럼 보였습니다. 그래서 타임라인을 1999년 11월부터 2001년 5월까지로 잘라냈고, 그 결과 9,902개의 유효한 이메일을 얻었습니다. 이 중 초기 80%(7,921개)로 학습하고, 최신 20%(1,981개, 이 중 70.5%는 답장이 없었음)로 테스트했습니다. 분할은 시간 순서대로 이루어져, 모델이 미래를 볼 수 없도록 했습니다.

| 모델               | ROC AUC | 하위 10% 무시: 실제로 답장 없음 / 놓친 답장된 메일 | 하위 20% 무시 |
| :----------------- | :------ | :------------------------------------------------ | :------------ |
| 발신자 답장률 규칙 | 0.579   | 68.2% / 10.8%                                   | 73.7% / 17.8% |
| 그라디언트 부스팅  | 0.662   | 92.4% / 2.6%                                    | 88.4% / 7.9%  |
| TabPFN             | 0.687   | 92.9% / 2.4%                                    | 84.6% / 10.4% |

여기서 얻은 결론은 다음과 같습니다.

*   두 모델 모두 발신자의 과거 답장률 기반 규칙보다 훨씬 뛰어난 성능을 보였습니다.
*   TabPFN의 AUC는 0.024 더 높지만(부트스트랩 95% CI 0.003~0.043), 20% 버킷에서는 그라디언트 부스팅이 더 나은 결과를 보여주었습니다. 저는 이 둘을 비슷한 수준으로 봅니다.
*   실용적인 핵심은 이겁니다: 에이전트는 이메일 10개 중 약 1개를 주차시킬 수 있으며, 그 판단이 92~93%의 확률로 옳고, 실제로 답장된 메일을 놓치는 비율은 약 2.5%에 불과하다는 것입니다.
*   테스트 섹션에서 '확인 필요' 버킷은 전체 30% 대비 46%의 비율로 답장이 있었고, '사라져라' 버킷은 약 15%였습니다. 이 에이전트는 예언자가 아니라, 우선순위를 정해주는 도구인 셈입니다.

**무엇이 잘못되었고, 어떻게 해결했을까요?**

*   **모든 파일이 없는 것처럼 보였습니다.** Enron 파일 이름은 점으로 끝났는데(1., 10.), Windows가 이를 자동으로 제거했습니다. 그래서 Python은 빈 메일함을 보는 것처럼 작동했고, Windows의 확장 길이 경로 접두사를 사용하도록 변경한 후에야 문제가 해결되었습니다. 이런 사소한 파일 시스템 호환성 문제가 개발자를 얼마나 당황하게 하는지, 정말이지 뼈저리게 느꼈죠.
*   **첫 번째 테스트 세트에 긍정적인 샘플이 없었습니다.** 모델은 의미 없는 98%의 정확도를 기록했습니다. 월별 표를 살펴보니 2001년 6월부터 답장이 정확히 0으로 떨어지는 것을 발견했습니다. 이는 아카이브에 보낸 메일이 더 이상 포함되지 않았기 때문이었습니다. 이 지점에서 타임라인을 잘라냈습니다.
*   **Gemma가 엉뚱한 메시지를 요약했습니다.** 발신자가 긴 전달 체인 위에 한 줄을 덧붙인 이메일의 경우, Gemma는 가장 오래된 전달된 메시지를 요약했습니다. 저는 캐시된 이메일 텍스트와 요약을 비교하여 이 문제를 찾아냈습니다. 각 이메일을 첫 번째 전달 메시지 마커에서 잘라내는 방식으로 이 경우를 해결했습니다. 여러 번의 실행(각각 마지막 두 번은 온도 0, 고정 시드 사용)에서, 수정 전 버전은 매번 전달된 메시지를 요약했지만, 수정 후 버전은 매번 발신자의 답장을 요약했습니다. 해당 이메일의 프롬프트 또한 649토큰에서 90토큰으로 줄어들었습니다.

**한계점**

*   "7일 이내 답장"은 "조치가 필요함"에 대한 대리 지표일 뿐이며, "발신자가 다시 연락함"은 노이즈가 많은 후속 신호입니다. 데모에서 격상된 한 이메일은 동일한 제목을 다시 보낸 메일링 리스트에서 온 것이었습니다.
*   하나의 메일함, 하나의 시간 기반 분할만 사용했습니다. 부트스트랩 구간은 이메일을 독립적으로 취급하지만, 스레드와 발신자가 묶여 있기 때문에 실제보다 조금 더 타이트할 수 있습니다.
*   주차 데모는 8개의 이메일과 시뮬레이션된 시계를 사용하며, "보관"은 실제 메일을 이동시키는 대신 로그 파일에 기록합니다.
*   Gemma의 출력은 비결정적이며, 동일한 프롬프트라도 실행마다 지연 시간이 약 2배 차이가 났습니다. 따라서 저는 전달 체인 수정에 대한 토큰 수만 인용했습니다. 이 수정은 하나의 이메일에 대한 것이며 벤치마크가 아니고, 제안된 행동은 실행마다 다를 수 있습니다.
*   첨부 파일은 이메일 텍스트에 포함되지 않으므로, 첨부 파일만 있는 이메일에 대한 제안된 행동은 일반적일 수 있습니다.

## 왜 오픈 이노베이션이 중요할까요?

*   **제 메일을 읽는 모델은 제 머신에서 실행됩니다.** Gemma는 Ollama를 통해 로컬에서 실행되며, Sentry 추적을 보면 모든 모델 호출이 127.0.0.1로 가는 것을 확인할 수 있습니다. API 비용도 들지 않고, 제 텍스트를 읽는 제3자도 없습니다. 개인 정보 보호 측면에서 이보다 더 좋을 순 없죠.
*   **대기 과정이 견고하고 스케줄러를 직접 실행할 필요가 없습니다.** Temporal의 오픈소스 툴링 덕분에 저는 재시작에도 살아남고 불안정한 단계에 대한 재시도 기능을 갖춘 타이머를 얻었습니다. 별도의 Cron Job이나 직접 만든 큐를 관리할 필요가 전혀 없었죠.
*   **별도의 학습 과정이 없습니다.** TabPFN은 학습 단계 없이 작은 개인 메일함에도 적용할 수 있습니다. 솔직히 말하면, 저는 호스팅된 API를 사용했기 때문에 5,000개의 학습 행이 Prior Labs 서버로 전송되기는 했습니다. 이는 공개 Enron 데이터에만 적용했으며, 개인 메일에 배포하려면 로컬 가중치를 사용하거나 이러한 트레이드오프를 수용해야 합니다.
*   **누구나 수치를 재현할 수 있습니다.** 데이터는 공개되어 있고 코드는 GitHub 리포지토리에 있습니다. 투명성과 재현성은 오픈소스의 핵심 가치라고 생각합니다.

저는 호스팅된 LLM을 테스트하지 않았기 때문에 요약 품질 면에서 오픈소스가 우수하다고 주장할 수는 없습니다. 하지만 여기서 오픈소스가 가진 강점은 명확합니다: 개인 정보 보호, 비용 절감, 그리고 특정 서비스에 대한 의존성 감소입니다.

## 게으름의 보상

아직 제 실제 메일함에 이 에이전트를 연결하지는 않았습니다. 양방향 메일함이 없기 때문이죠. 따라서 이 수치들은 공개된 Enron 메일에서 나온 것이며, 제 일주일간의 경험을 대변하지는 않습니다. 하지만 보유 테스트 세트인 1,981개의 이메일에서 이 에이전트는 소유자가 처리해야 할 398개(20%)의 이메일을 대신 처리해 주었고, 이 중 약 85%는 실제로 답장이 필요 없었습니다. 이 '게으름'의 대가는 나머지 15%, 즉 약 60개의 이메일입니다. 이 이메일들은 답장이 필요한 경우였지만, 발신자가 다시 연락하지 않았다면 보관 처리되었을 것입니다. 이는 전체 답장된 메일의 약 10%에 해당합니다. 각 요약은 제 노트북에서 약 4초가 걸립니다. 솔직히 절약된 시간을 정확한 분 단위로 계산할 수는 없기에, 그 시도는 하지 않겠습니다.

## 수상 부문 (예상)

*   **TabPFN 최우수 활용:** 규칙 기반 및 그라디언트 부스팅 모델과 비교하여 '무시 또는 조치' 예측기를 구축했으며, 차이에 대한 부트스트랩 구간까지 분석했습니다.
