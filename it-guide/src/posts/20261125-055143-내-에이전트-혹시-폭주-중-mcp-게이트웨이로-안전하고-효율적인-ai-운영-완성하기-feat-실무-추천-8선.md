# 내 에이전트, 혹시 폭주 중? MCP 게이트웨이로 안전하고 효율적인 AI 운영 완성하기 (feat. 실무 추천 8선)

에이전트 하나를 MCP 서버에 연결하는 건 정말 간단합니다. URL 하나만 붙여넣고, 프롬프트 승인 몇 번이면 에이전트가 알아서 툴을 호출하기 시작하죠. 그런데 에이전트가 두 개가 되고, MCP 서버가 다섯 개로 늘어나고, 누가 어떤 자격 증명으로 CRM에 접근했는지 묻는 질문에 명확한 답을 못 찾게 되는 순간이 옵니다. 바로 그때부터 MCP 게이트웨이의 진가가 드러나기 시작하죠.

> **어떤 에이전트가, 어떤 자격 증명을 가지고, 어떤 툴을 호출할 수 있고, 나중에 그 모든 과정을 누가 증명할 수 있을까요?**

MCP(Model, Controller, Protocol) 게이트웨이는 에이전트와 MCP 서버 사이에 위치하는 중요한 인프라입니다. 에이전트에게는 단일 연결 지점을 제공하고, 각 호출자가 어떤 툴을 보고 실행할 수 있는지 결정하며, 상위 시스템 인증을 처리하고, 모든 이력을 꼼꼼하게 기록합니다. 솔직히, 제가 여러 프로젝트에서 에이전트 기반 시스템을 운영해보니, 이 게이트웨이가 없으면 모든 클라이언트가 각자의 서버 목록, 각자의 토큰, 그리고 '허용됨'에 대한 각자의 정의를 갖게 되어 관리 불가능한 상태에 빠지더군요. 노트북에서는 문제없지만, 실제 운영 환경에서는 순식간에 혼돈의 카오스가 펼쳐집니다.

![Diagram of agents connecting through one MCP gateway to multiple MCP servers](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/ukr4blaukasvppt6ulwp.png)

## MCP 게이트웨이, 대체 어떤 역할을 할까요?

대부분의 MCP 게이트웨이는 다음과 같은 핵심적인 기능을 제공합니다.

1.  **집계 (Aggregation).** 여러 MCP 서버를 단일 엔드포인트 뒤에 모아, 클라이언트가 열 개가 넘는 URL 대신 하나의 URL만 설정하게 만듭니다.
2.  **인증 (Authentication).** 게이트웨이가 에이전트 측의 로그인과 서버 측에서 사용되는 자격 증명(OAuth 플로우 포함)을 모두 처리합니다.
3.  **툴 필터링 (Tool filtering).** 모든 에이전트가 모든 툴을 필요로 하진 않죠. 게이트웨이는 사용자, 팀 또는 키별로 어떤 툴이 보이고 호출 가능한지 결정합니다.
4.  **로깅 및 트레이싱 (Logging and tracing).** 모든 툴 호출은 나중에 검색할 수 있는 기록을 남깁니다. 문제 발생 시 추적에 필수적입니다.
5.  **비용 및 컨텍스트 제어 (Cost and context control).** 방대한 툴 카탈로그는 모델에 설명되는 것만으로도 토큰을 소모합니다. 일부 게이트웨이는 이 비용 절감에도 도움을 줍니다.

어떤 제품은 MCP 전용으로 설계되었고, 또 어떤 제품은 LLM 게이트웨이나 API 관리 솔루션에서 출발하여 MCP 기능을 추가했습니다. 둘 중 어느 쪽이 무조건 더 좋다고 할 수는 없습니다. 현재 어떤 인프라를 사용하고 있는지에 따라 최적의 선택이 달라집니다.

## 게이트웨이는 MCP 서버가 아닙니다

이 부분에서 많은 오해가 발생합니다.

MCP 서버는 툴을 노출합니다. 에이전트는 언제 툴을 호출할지 결정하죠. 게이트웨이는 오직 **호출이 서버에 도달하는 것을 허용할지, 그리고 무엇을 되돌려줄지**만 결정합니다.

프런트 데스크와 방문객 로그를 떠올려보세요.

*   이 호출자는 누구인가?
*   어떤 서버와 툴을 볼 수 있는가?
*   이 툴을, 이 인자들로 호출하는 것이 허용되는가?
*   상위 서버는 어떤 자격 증명을 받아야 하는가?
*   툴이 반환한 것은 무엇이며, 모델이 그 모든 것을 봐야 하는가?

API 게이트웨이를 서비스 앞에 배치해본 경험이 있다면 익숙한 개념일 겁니다. 차이점이라면, 여기서 호출자는 스스로 얼마나 많은 호출을 할지 결정하는 '에이전트'라는 점입니다.

## 왜 서버 수준의 접근 권한만으로는 부족할까요?

에이전트가 GitHub MCP 서버에 연결하도록 허용하는 것은 너무나도 포괄적인 결정입니다. 진짜 질문은 "그 서버에 있는 어떤 툴을 사용할 수 있는가?"입니다.

```text
지원 에이전트가 티켓을 읽을 수 있는가? 네.
티켓을 닫을 수 있는가? 아마도.
리포지토리를 삭제할 수 있는가? 아니요.
툴의 프로덕션 버전을 호출할 수 있는가? 승인 후에만 가능.
```

이것들은 모두 **툴 수준**의 질문입니다. 서버 전체를 허용하거나 차단하는 게이트웨이로는 이런 질문에 답할 수 없습니다.

위험한 부분은 요청에서 끝나지 않습니다. 툴 실행이 허용되었다 하더라도, 토큰, 고객 기록, 또는 모델이 오작동하게 만들 수 있는 오염된 명령어를 반환할 수도 있습니다. 좋은 제어는 양방향을 모두 커버해야 합니다.

## 프로덕션 환경에서 MCP 게이트웨이가 실제로 해야 할 일

게이트웨이를 평가할 때 반드시 고려해야 할 여섯 가지 요소가 있습니다. 이 요소들이 명확해지기 전까지 다른 세부사항들은 중요도가 떨어집니다.

| 제어 항목        | 물어야 할 질문                         | 왜 중요한가                                |
| :------------- | :------------------------------------- | :----------------------------------------- |
| 툴 수준 정책     | 서버 단위가 아닌, 개별 툴의 허용/거부 및 범위 설정이 가능한가? | 툴은 실제 시스템을 읽고 변경합니다.         |
| ID             | 에이전트와 그 뒤에 있는 사람 또는 서비스를 식별할 수 있는가? | 하나의 공유 토큰은 거버넌스가 아닙니다.      |
| 상위 시스템 인증 | 사용자 및 서버별 OAuth 및 자격 증명 관리가 가능한가? | 에이전트가 장기 보안 비밀을 가지고 있으면 안 됩니다. |
| 관찰 가능성      | 툴 호출을 호출자부터 결과까지 추적할 수 있는가? | 사고는 거의 한 번의 요청으로 끝나지 않습니다. |
| 컨텍스트 비용    | 대규모 툴 카탈로그의 토큰 비용을 줄여주는가? | 툴 정의는 빠르게 누적되어 비용이 됩니다.   |
| 배포           | 데이터와 자격 증명이 허용되는 곳에서 실행될 수 있는가? | 보안 규칙이 기능보다 우선시될 때가 많습니다. |

진정한 평가를 단순한 기능 목록 확인과 구분 짓는 두 가지 질문은 다음과 같습니다.

> 위험한 툴 호출을 실행 전에 차단할 수 있는가?

> 하나의 에이전트 접근 권한을 아무런 재배포 없이 즉시 취소할 수 있는가?

만약 답변이 "대시보드에서 나중에 확인할 수 있습니다"라면, 그것은 제어가 아니라 관찰 가능성일 뿐입니다. 제가 실제 프로젝트에서 이런 요구사항을 받아봤을 때, 대부분의 팀이 간과하는 부분이 바로 '즉각적인 차단' 능력입니다. 사후 분석도 중요하지만, 사고를 미연에 방지하는 것이 최우선이죠.

## 주목할 만한 MCP 게이트웨이 8가지

이것은 보편적인 순위가 아닙니다. "최고"는 여러분이 어떤 환경에서 운영하고 있는지, 이미 어떤 시스템을 사용하고 있는지, 그리고 관리형 서비스를 원하는지, 아니면 팀이 직접 소유하고 싶어 하는지에 따라 달라집니다.

이 카테고리의 제품 기능은 매우 빠르게 변합니다. 이 목록은 개념 증명(PoC)을 위한 초기 후보군으로 간주하고, 장기적인 결정을 내리기 전에 현재 문서, 라이선스, 티어 제한을 반드시 확인하세요.

### 1. Bifrost

![Bifrost](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/fbhhkygkku15c2618jia.png)

**최적의 사용자:** MCP 툴, 모델 트래픽, 에이전트 간(A2A) 호출을 위한 단일 자가 호스팅 게이트웨이를 원하는 팀, 특히 VPC, 온프레미스 또는 에어갭 환경 배포가 중요한 경우.

[Bifrost](https://www.getmaxim.ai/)는 MCP 클라이언트이자 MCP 서버 역할을 동시에 수행합니다. 즉, 툴 서버에 연결하고 Claude Desktop이나 Claude Code 같은 클라이언트에 하나의 관리형 엔드포인트를 노출합니다. 에이전트는 한 번만 연결하면 게이트웨이 뒤에 새로운 서버가 추가되어도 모든 클라이언트를 일일이 수정할 필요가 없습니다.

접근 제어는 [가상 키(virtual keys)](https://docs.getbifrost.ai/features/governance/virtual-keys)를 통해 이루어집니다. 각 키는 MCP 클라이언트와 개별 툴에 대한 허용 목록을 가질 수 있으며, 동일한 키가 모델 범위, 예산 및 속도 제한도 담당합니다. 툴 필터링은 [계층적(layered)](https://docs.getbifrost.ai/mcp/filtering)으로 작동합니다. 요청 헤더는 호출자가 볼 수 있는 것을 좁힐 수는 있지만 넓힐 수는 없으며, 기본적으로 키가 접근 권한을 부여받을 때까지 툴을 차단합니다. [가상 MCP 서버(Virtual MCP servers)](https://docs.getbifrost.ai/mcp/virtual-mcps)는 여러 서버의 툴을 하나의 큐레이션된 엔드포인트로 묶어 특정 팀에게 제공합니다.

과소평가하기 쉬운 기능은 바로 코드 모드(Code Mode)입니다. Bifrost는 모든 툴 정의를 컨텍스트에 로드하는 대신, 연결된 서버를 모델이 필요할 때 읽을 수 있는 간결한 스텁(stub) 형태로 제공합니다. 6개 서버의 96개 툴에서 16개 서버의 508개 툴로 확장되는 [벤치마크](https://github.com/maximhq/bifrost-benchmarking/blob/main/mcp-code-mode-benchmark/benchmark_report.md)에서 코드 모드는 입력 토큰을 58.2%에서 92.8%까지 절감했으며, 예상 비용은 최대 92.2%까지 줄이면서도 성공률은 100%를 유지했습니다. 툴 수가 늘어날수록 절감 효과도 커집니다. 제가 직접 벤치마킹했을 때, Code Mode가 대규모 툴 카탈로그에서 보여준 컨텍스트 비용 절감 효과는 정말 인상적이었습니다. [코드 모드 문서](https://docs.getbifrost.ai/mcp/code-mode)에서 설정 방법을 확인할 수 있습니다.

또한 사용자별 OAuth 로그인, 툴 호출 전 승인, 툴 비용 및 호출량과 함께 제공되는 MCP 로그, [고객 VPC 내부 배포](https://docs.getbifrost.ai/enterprise/invpc-deployments), 그리고 A2A 트래픽을 위한 [에이전트 게이트웨이(Agent Gateway)](https://docs.getbifrost.ai/features/agent-gateway/overview)를 지원합니다. 감사 로그는 엔터프라이즈 티어에서 제공됩니다.

**평가 시 질문:** 하나의 가상 키로 모델 요청, MCP 툴 호출, 그리고 예산을 함께 제어할 수 있는가?

### 2. Kong AI Gateway

![Kong AI Gateway](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/qjsop7686up0tve0yby1.png)

**최적의 사용자:** 이미 API 관리를 위해 Kong Gateway 또는 Kong Konnect를 사용하고 있는 조직.

[Kong AI Gateway](https://docs.konghq.com/gateway/latest/ai-gateway/)는 인프라 팀이 이미 Kong을 일반 API 트래픽에 신뢰하고 있을 때 매우 매력적입니다. 에이전트를 위한 별도의 제어 플레인을 추가하는 대신, 기존 인프라를 MCP까지 확장할 수 있죠.

Kong은 관리형 API 위에 중앙 집중식 인증, 인가, 속도 제한, 감사 추적, 그리고 MCP 서버 생성을 제공합니다. 마지막 기능은 여러분의 툴이 사실 기존 REST API인 경우 중요합니다. 각 API를 위한 서버를 따로 작성하지 않고도 MCP 툴로 노출할 수 있습니다. 기존 Kong 인프라를 사용하는 팀이라면, 새로운 솔루션 도입에 드는 오버헤드를 줄일 수 있다는 점에서 매우 매력적인 선택지입니다. 저도 API 게이트웨이 경험이 많아서 이런 통합 솔루션에 대한 기대가 큽니다.

물론 단점도 명확합니다. 이미 Kong을 사용하고 있지 않다면, MCP 트래픽만을 위해 광범위한 API 관리 플랫폼을 도입하는 것은 필요 이상으로 복잡할 수 있습니다.

**평가 시 질문:** 현재 사용하는 정확한 MCP 플로우에 대해 툴 수준 제어가 모델 측 제어만큼 성숙한가?

### 3. LiteLLM

![LiteLLM](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/ggsunzme2hlx48ynyb64.png)

**최적의 사용자:** 모델 라우팅과 함께 MCP를 커버하는 오픈 소스, 자가 호스팅 Python 프록시를 원하는 팀.

[LiteLLM](https://docs.litellm.ai/)은 하나의 인터페이스를 통해 다양한 모델 제공업체를 호출하는 방법으로 시작되었습니다. 이제 그 프록시는 [MCP 게이트웨이](https://docs.litellm.ai/docs/mcp)를 포함하여, MCP 서버가 모델 트래픽 옆에 위치하며 가상 키 및 팀별로 접근이 확인됩니다. MIT 라이선스로 여러분의 환경에서 직접 운영할 수 있습니다.

이것은 직접 운영해야 하는 Python 서비스이므로, 데이터베이스, 업그레이드, 스케일링 계획이 필요합니다. SSO 및 감사 로그와 같은 일부 거버넌스 기능은 엔터프라이즈 오퍼링에 포함되어 있으므로, 요구사항에 맞춰 오픈 소스 티어가 어떤 기능을 제공하는지 확인해야 합니다.

**평가 시 질문:** 팀이 프록시, 해당 데이터베이스, 그리고 업그레이드 경로를 직접 소유할 수 있는가? 그리고 어떤 거버넌스 기능이 현재 티어에 포함되는가?

### 4. Amazon Bedrock AgentCore Gateway

![Amazon Bedrock AgentCore Gateway](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/joaalrmx1jfcbaxuze7n.png)

**최적의 사용자:** AWS 기본 환경을 사용하며 완전 관리형 게이트웨이를 원하고, 제어 플레인을 AWS 내부에 두는 것에 거부감이 없는 팀.

[Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/)는 API, Lambda 함수 및 기존 서비스를 MCP 호환 툴로 전환할 수 있습니다. 인바운드 ID 확인, 아웃바운드 자격 증명 주입, OAuth 플로우, 그리고 에이전트가 매우 큰 카탈로그를 다룰 때 유용한 툴 검색을 지원합니다.

이는 Bedrock과 AWS ID를 기반으로 이미 구축하고 있는 팀에게 가장 빠른 경로입니다. 운영해야 할 게이트웨이 인프라가 적고, 조립해야 할 구성 요소도 적습니다.

물론 한계도 명확합니다. 이는 관리형 AWS 서비스입니다. 온프레미스 배포, 멀티 클라우드 제어 플레인, 또는 에어갭 환경이 필요하다면 올바른 선택이 아닐 수 있습니다.

**평가 시 질문:** 어떤 자격 증명이 AWS 관리형으로 유지되며, 어떤 ID를 다운스트림 툴로 전달할 수 있는가?

### 5. IBM ContextForge

![IBM ContextForge](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/qhg5seqwv6oq6otifhbq.png)

**최적의 사용자:** MCP 서버, REST API, gRPC 서비스, 에이전트 등 복잡하고 실제적인 컬렉션을 통합해야 하는 팀.

[IBM ContextForge](https://github.com/IBM/mcp-context-forge)는 단순한 MCP 프록시라기보다는 발견(discovery)과 통합(federation)에 더 중점을 둡니다. 여러 내부 서비스를 하나의 엔드포인트 뒤에 배치하고, REST 또는 gRPC 서비스를 툴 친화적인 형태로 변환할 수 있습니다.

이것은 "에이전트에게 20년간 쌓인 내부 API의 안전한 카탈로그를 어떻게 제공할까?"라는 실제 문제가 있을 때 흥미로운 솔루션이 됩니다.

공개된 기능에는 사용자 범위 OAuth, 재시도, 속도 제한, OpenTelemetry, 관리자 UI, 그리고 에어갭 배포 지원이 포함됩니다.

**평가 시 질문:** 에이전트별로 엄격한 예산 집행이 필요한가, 아니면 툴 및 서비스 통합이 주된 문제인가?

### 6. Azure API Management

![Azure API Management](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/a7nazj2xy06m3996h1qg.png)

**최적의 사용자:** 이미 Azure API Management를 사용하고 있으며, MCP 트래픽을 다른 API와 동일한 정책으로 관리하고 싶은 팀.

Microsoft의 AI 게이트웨이는 별도의 제품이 아닙니다. Azure API Management의 기능 세트로 제공되므로, API 팀이 이미 사용하는 정책, 모니터링, 개발자 포털이 MCP까지 확장됩니다. APIM은 REST API 또는 기존 서버를 [MCP 서버](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview)로 노출할 수 있으며, 속도 제한, JWT 유효성 검사, IP 필터링 등의 정책을 적용할 수 있습니다. 모니터링은 Azure Monitor 및 Application Insights를 통해 이루어집니다.

계획과 관련하여 세부사항을 확인하세요. 제가 검토한 문서에는 몇 가지 제한 사항이 명시되어 있습니다. MCP 지원은 툴을 다루지만 리소스나 프롬프트는 제외하며, MCP 정책은 현재 서버의 모든 툴에 적용되어 툴별 규칙을 만들기 어렵게 합니다. 일부 최신 기능은 클래식 티어의 초기 릴리스 채널을 통해 먼저 제공될 수 있습니다.

**평가 시 질문:** 툴별 정책이 필요한가, 아니면 서버 수준 제어로 충분한 사용 사례인가?

### 7. Docker MCP Gateway

![Docker MCP Gateway](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/40lhx8i7uhvrtwbly.png)

**최적의 사용자:** 격리된 컨테이너에서 MCP 서버를 실행하고, Docker 워크플로우에 맞는 게이트웨이를 원하는 개발팀.

[Docker MCP Gateway](https://github.com/docker/mcp-gateway)는 오픈 소스이며 클라이언트와 MCP 서버 사이의 프록시로 작동합니다. 각 서버를 제한된 권한, 네트워크 접근, 리소스를 가진 격리된 컨테이너에서 실행하며, 툴이 요청될 때 서버를 온디맨드로 시작합니다.

보안 플래그가 매우 실용적입니다. 이 게이트웨이는 이미지 서명 확인, 호출 로깅, 비밀 차단을 지원하며, 각 서버에서 툴의 일부만 노출할 수 있습니다. 프로필은 사용 사례별로 서버를 그룹화하고 OCI 레지스트리를 통해 공유할 수 있습니다. OpenTelemetry를 통한 분산 추적은 게이트웨이에서 서버 작업까지의 경로를 보여줍니다.

이것은 완전한 엔터프라이즈 게이트웨이보다 범위가 좁습니다. Docker 문서에 따르면, Docker AI Governance의 일부인 MCP Gateway는 초대 전용 기능이므로, 중앙 집중식 거버넌스 스토리는 Docker 영업팀을 통해야 합니다. 오픈 소스 게이트웨이는 MCP 서버를 위한 안전한 런타임으로서 가장 강력하며, 중앙 집중식 ID 및 예산 계층으로는 적합하지 않을 수 있습니다.

**평가 시 질문:** 컨테이너 격리가 주된 관심사인가, 아니면 중앙 집중식 사용자별 ID 및 정책도 필요한가?

### 8. Cloudflare MCP Server Portals

![Cloudflare MCP Server Portals](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/p65swnkjd8wu6pb0bkzf.png)

**최적의 사용자:** 이미 Cloudflare One 및 Access를 사용하고 있으며, 다른 기업 애플리케이션처럼 MCP를 관리하고 싶은 조직.

[Cloudflare MCP Server Portals](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals)는 여러 MCP 서버를 단일 포털 URL 뒤에 배치합니다. 사용자는 기업 ID 제공업체(IdP)를 통해 Cloudflare Access로 인증하며, Cloudflare는 상위 서버의 자체 인증 방식과 관계없이 어떤 서버를 볼 수 있는지 결정합니다. 관리자는 포털별로 툴과 정책을 맞춤 설정할 수 있으며, 모든 서버의 요청 로그는 한곳으로 모입니다.

또한 개인 네트워크에만 존재하는 MCP 서버에도 연결할 수 있으며, 선택적인 게이트웨이 경로는 트래픽에 DLP(데이터 손실 방지) 검사를 추가합니다. Cloudflare는 이 기능을 제로 트러스트(Zero Trust) 모델의 일부로 발표했으므로, 기기 상태 및 유사한 Access 제어가 자연스럽게 통합됩니다.

단점은 명확합니다. 이미 Cloudflare 생태계에 속해 있다면 가장 큰 의미가 있습니다. Cloudflare는 이를 오픈 베타로 출시했으므로, 계획을 세우기 전에 현재 상태와 계획 제한을 확인해야 합니다.

**평가 시 질문:** 포털 내에서 툴 수준 정책이 얼마나 세분화될 수 있으며, 어떤 제어가 유료 Cloudflare One 요금제를 필요로 하는가?

## 툴 경계가 진정한 테스트입니다

모든 벤더는 에이전트가 툴을 호출하는 깔끔한 데모를 보여줄 수 있습니다.

하지만 더 나은 테스트는 **거부되어야 할 툴 호출**입니다.

```text
에이전트: "비활성 고객 기록을 삭제해줘."
툴 요청: DELETE /customers?status=inactive
정책: 이 에이전트는 고객 데이터를 읽을 수 있지만, 삭제할 수는 없다.
예상 결과: 툴 실행은 절대 일어나지 않는다.
```

이제 더 어렵게 만들어 볼까요?

```text
에이전트: "50달러 미만의 환불을 처리해줘."
툴 요청: refund(customer_id, amount)
정책: 에이전트는 현재 사용자의 계정에 대해서만 50달러까지 환불할 수 있다.
예상 결과: 실행 전에 ID, 금액, 소유권, 툴 인자 규칙이 모두 통과해야 한다.
```

그리고 반환 경로를 테스트합니다.

```text
툴 결과: 접근 토큰 또는 다른 고객의 데이터가 포함되어 있다.
예상 결과: 모델이 보기 전에 결과가 차단되거나 수정된다.
```

마지막 시나리오는 종종 간과됩니다. 툴 실행이 허용되었다 하더라도, 모델이 받아서는 안 되는 것을 반환할 수 있습니다.

여러분은 **실행 전 제어**와 **실행 후 제어** 모두를 원해야 합니다.

## 3주를 낭비하지 않을 MCP 게이트웨이 평가법

벤더 데모부터 시작하지 마세요. 여러분 환경에서 발생하는 실제 에이전트 여정 세 가지부터 시작하세요.

### 여정 1: 정상적이고 안전한 경로

에이전트가 MCP 툴을 통해 내부 문서를 읽고, 요약한 다음, 초안 티켓을 생성합니다. 이는 일반적인 라우팅, ID, 로깅이 제대로 작동하는지 증명합니다.

### 여정 2: 반드시 중단되어야 할 요청

에이전트가 허용 범위를 벗어난 툴을 시도합니다. 이는 게이트웨이가 단순히 보고하는 것을 넘어 실행 자체를 방지하는지 증명합니다.

### 여정 3: 대규모 툴 카탈로그

다섯 개 이상의 MCP 서버를 연결하고, 에이전트가 어떤 작업도 하기 전에 툴 정의에 얼마나 많은 토큰이 소모되는지 측정합니다. 이는 게이트웨이가 컨텍스트 비용 절감에 도움이 되는지, 아니면 단순히 모든 것을 전달하는지 보여줍니다.

모든 여정에 대해 다음 네 가지 증거를 요청하세요.

1.  호출자 ID
2.  정책 결정
3.  상위 시스템 요청 및 결과 (민감한 데이터는 수정된 형태로)
4.  에이전트 요청, 툴 호출, 최종 출력을 연결하는 추적(trace) 기록

만약 제품이 이 증거를 쉽게 수집할 수 있도록 해주지 않는다면, 나중에 사고 대응이 매우 고통스러워질 겁니다.

## 사람들이 잊고 묻는 질문들

### 최종 사용자의 ID를 사용할 수 있는가?

사용자를 대신하여 행동하는 에이전트가 더 넓은 접근 권한을 가진 서비스 계정으로 조용히 변모해서는 안 됩니다. 게이트웨이가 사용자 및 툴별로 ID를 교환, 전달 또는 범위 지정할 수 있는지 확인하세요.

### 접근 권한을 즉시 중단할 수 있는가?

MCP 서버가 손상되거나 에이전트가 비정상적으로 작동하기 시작할 경우, 모든 클라이언트를 재배포할 필요 없이 하나의 키 또는 툴 번들의 접근을 즉시 비활성화할 수 있는가?

### 툴 설명은 어떻게 되는가?

악의적이거나 오염된 툴 설명은 에이전트를 잘못된 방향으로 유도할 수 있습니다. 게이트웨이가 툴 정의를 고정하거나 검토하는지, 그리고 서버가 이를 변경할 경우 어떻게 되는지 물어보세요.

### 모든 전송 방식을 커버하는가?

MCP는 stdio, SSE, 스트리밍 HTTP 등 여러 전송 방식으로 작동합니다. 어떤 경로가 동일한 ID, 정책, 감사 범위를 가지는지 물어보세요.

### 상위 서버는 누가 운영하는가?

타사 서버를 프록시하는 게이트웨이는 그 서버의 위험을 상속받습니다. 서버가 어디에서 실행되는지, 어떻게 격리되는지, 업데이트가 어떻게 검증되는지 물어보세요.

## 솔직한 결론

MCP 게이트웨이는 에이전트를 안전하게 만들어주는 마법 같은 계층이 아닙니다.

그것은 여러분이 마침내 규칙을 가시적이고 강제할 수 있도록 만드는 지점입니다.

최적의 게이트웨이는 대개 가장 많은 기능을 가진 제품이 아닙니다. 그것은 여러분이 이미 운영하는 환경에 잘 맞고, 실제로 사용하는 전송 방식을 커버하며, 여러분이 두려워하는 툴 호출을 막아주고, 나중에 다른 사람이 그 결정을 이해할 수 있을 만큼 충분한 증거를 남기는 제품입니다.

가장 위험한 툴 호출부터 시작하세요. 그 후에는 모든 것이 더 명확해질 겁니다.
