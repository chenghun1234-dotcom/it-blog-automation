# 디스코드 링크 미리보기, 이제 Open Graph를 넘어 커스텀 컴포넌트로 SEO와 사용자 경험을 한 번에 잡는 법

웹사이트 링크를 디스코드 채널에 툭 던져 넣으면, 어떤 일이 벌어질까요? 잠시 후, 제목과 설명, 그리고 멋진 이미지가 담긴 작은 카드 하나가 짠하고 나타나죠. 이건 별다른 코드 없이도 기본적으로 제공되는 기능이라 다들 익숙하실 겁니다.

그런데 최근 디스코드에 새로운 옵션이 추가됐다는 소식, 들으셨나요? 이제 이 기본 카드를 완전히 대체할 수 있는 '커스텀 미리보기'를 만들 수 있게 되었습니다. 단순히 텍스트와 이미지뿐만 아니라, 포맷팅된 텍스트, 이미지 갤러리, 심지어 버튼까지 넣을 수 있죠.

10년 차 IT 실무자이자 테크 블로거로서 이 새로운 기능을 제 블로그에 직접 적용해 봤습니다. 지금부터 그 과정과 핵심 포인트를 자세히 공유해 드릴게요.

시작하기 전에, 아래 몇 가지 설정이 필수적으로 되어 있어야 합니다.

*   **HTTPS**로 서비스되는 웹사이트
*   **오픈 그래프(Open Graph) 태그** 존재 (새로운 임베드 컴포넌트를 사용하더라도 여전히 필수입니다.)
*   **서버 사이드 렌더링(SSR)**: HTML 응답 자체에 태그가 포함되어야 하며, JavaScript 스크립트 실행 후 추가되는 방식은 안 됩니다.
*   **Discordbot 크롤러 허용**: 만약 WAF, CDN, 또는 속도 제한기가 웹사이트 앞에 있다면, `Discordbot` 크롤러를 명시적으로 허용해야 합니다.
*   **임베드 컴포넌트용 JSON 페이로드 준비**: 이건 다음 섹션에서 자세히 다룰 내용입니다.

## 기본 동작: 오픈 그래프 태그

자세히 설명하지 않아도 많은 분이 아시겠지만, 링크를 공유했을 때 무슨 일이 일어나는지 간략하게 짚고 넘어가죠. 디스코드는 여러분의 URL로 요청을 보내 서버에서 반환된 HTML을 읽습니다. 그리고 `<head>` 요소 안에 있는 오픈 그래프(Open Graph) 태그를 찾습니다.

이 태그들이 존재한다면, 카드 미리보기가 자동으로 생성됩니다.

```html
<meta property="og:title" content="이 페이지의 제목" />
<meta property="og:description" content="이 페이지에 대한 설명" />
<meta property="og:image" content="https://example.com/og-image.png" />
<meta property="og:url" content="https://example.com/page" />
<meta name="twitter:card" content="summary_large_image" />
```

이 태그들만으로 디스코드에 어떻게 표시되는지 한번 볼까요?

![오픈 그래프 태그만으로 디스코드 링크 미리보기: 제목, 설명, 이미지](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/m9dflhpvw5h3marmp2d3.png)

이 방식에 대한 세 가지 핵심 사항이 있습니다. 뒤에 이어질 내용에도 매우 중요하니 꼭 기억해 주세요.

*   태그는 **서버에서 보낸 HTML** 안에 있어야 합니다. 디스코드는 JavaScript를 실행하지 않습니다. 클라이언트 사이드 JS로 나중에 추가된 태그는 디스코드에게는 존재하지 않는 것이나 마찬가지예요.
*   크롤러는 `Mozilla/5.0 (compatible; Discordbot/2.0; +https://discordapp.com)` 사용자 에이전트로 자신을 식별합니다. 만약 WAF나 속도 제한기가 봇을 차단하고 있다면, 반드시 **Discordbot**을 명시적으로 허용해야 합니다.
*   미리보기는 약 **30분** 동안 캐시됩니다. 테스트 중에 강제로 새로고침하려면, URL 뒤에 간단히 `?v=2`를 추가하면 됩니다. 제가 실무에서 이 부분을 테스트해 봤을 때, 캐시 때문에 변경 사항이 바로 반영되지 않아 답답했던 적이 한두 번이 아니었죠. `?v=2` 꼼수는 정말 시간 절약에 큰 도움이 됩니다.

오픈 그래프 태그(이미지 크기, 트위터 카드 태그 등)에 대해 더 자세히 알아보고 싶으시다면, "[SEO 개선을 위한 몇 가지 팁](https://dev.to/thomasbnt/a-few-tips-for-improving-your-seo-5df3)" 글을 참고해 보세요.

## 새로운 형식: 컴포넌트 임베드

페이지에 임베드 컴포넌트가 없다면, 디스코드는 위에서 보여드린 카드 미리보기만 표시합니다.

이것은 기존 기능을 **대체하는 것이 아니라 추가적인 옵션**입니다. `og:*` 태그는 여전히 모든 경우에 필수적입니다. 임베드 컴포넌트를 표시할 수 없는 상황(예: 지원되지 않는 컨텍스트, 유효하지 않은 페이로드 등)에서 이 태그들이 폴백(fallback) 역할을 해주기 때문이죠.

크롤러 측면에서의 동작은 표준 카드와 동일하며, 한 가지 추가 단계가 있습니다.

1.  디스코드 메시지에 여러분의 페이지 링크가 게시됩니다.
2.  디스코드는 해당 URL을 가져와 HTML을 읽습니다.
3.  추가적으로 `embed` 컴포넌트 태그를 찾습니다. 만약 존재한다면, JSON을 파싱하고 페이로드 내 각 이미지의 메타데이터를 검색합니다.
4.  페이로드가 유효하면, 오픈 그래프 카드를 이 커스텀 렌더링으로 대체합니다. 그렇지 않으면 이전 단계로 돌아가 기본 카드를 표시합니다.

이 JSON을 표시하는 두 가지 방법이 있습니다.

**옵션 1, 인라인 방식**: `<head>` 내 `<script>` 태그 안에 직접 넣는 방법입니다.

```html
<script id="discord:component-embed" type="application/json">
  {
    "component": {
      "type": 17,
      "components": [
        {
          "type": 10,
          "content": "# 패치 노트\n- 표시 버그 수정"
        }
      ]
    }
  }
</script>
```

**옵션 2, 외부 JSON 파일 방식**: 동일 도메인(또는 서브도메인)의 파일을 가리키는 링크를 사용하는 방법입니다.

```html
<link
  rel="discord:component-embed"
  type="application/json"
  href="https://exemple.com/embeds/article.json"
/>
```

이 옵션에는 엄격한 제한이 있습니다. 원본 파일의 크기가 **3,000바이트**를 넘을 수 없습니다. 이미지 갤러리나 버튼이 포함된 임베드라면, 인라인 방식이 더 큰 크기를 허용하므로 유리할 수 있습니다.

루트 `component`는 반드시 **컨테이너(`type: 17`)**여야 합니다.

총 **40개의 컴포넌트**까지 포함할 수 있으며, 아래 표에 나열된 유형 중 하나여야 합니다. 다른 컴포넌트 유형은 전체 페이로드를 무효화하므로 주의하세요.

| Type | 컴포넌트       | 설명                                                      |
| :--- | :------------- | :-------------------------------------------------------- |
| 1    | Action Row     | 버튼 행                                                   |
| 2    | Button         | 링크 스타일만 (`style: 5`), `label` 및/또는 `emoji` 포함 |
| 9    | Section        | 텍스트 + 요소 (썸네일 또는 버튼)                          |
| 10   | Text Display   | 디스코드 마크다운 (제목, 볼드체, 목록, 링크 등)           |
| 11   | Thumbnail      | 섹션에 첨부되는 작은 이미지                               |
| 12   | Media Gallery  | 여러 이미지/비디오를 큰 형식으로 표시                   |
| 14   | Separator      | 구분선                                                    |
| 17   | Container      | 루트 컴포넌트                                             |

이미지(썸네일 및 미디어 갤러리)의 경우, URL만 제공하면 됩니다. 디스코드가 자동으로 크기와 파일 형식을 가져옵니다.

```json
{ "url": "https://exemple.com/images/hero.webp" }
```

지원되는 형식은 PNG, GIF, JPEG, WebP, AVIF이며, 미디어 갤러리의 경우 MP4/MOV/WebM도 지원됩니다.

## 제 블로그에 설정한 방식

제 [블로그](https://thomasbnt.dev/blog)의 모든 게시물에는 표준 오픈 그래프 태그(여전히 숨겨져 있지만 존재합니다) 외에도 임베드 컴포넌트가 포함되어 있습니다.

이 컴포넌트는 표준 카드와 동일한 데이터를 사용하여 구축됩니다. 즉, 게시물의 제목, 설명, 커버 이미지, 그리고 강조 색상을 활용합니다.

간략하게 표현된 구조는 다음과 같습니다.

```json
{
  "component": {
    "type": 17,
    "accent_color": 5793266,
    "components": [
      {
        "type": 10,
        "content": "# [게시물 제목](https://thomasbnt.dev/blog/...)\n설명입니다."
      },
      {
        "type": 12,
        "items": [{ "media": { "url": "https://thomasbnt.dev/.../index.png" } }]
      },
      {
        "type": 1,
        "components": [
          {
            "type": 2,
            "style": 5,
            "url": "https://thomasbnt.dev/blog/...",
            "label": "글 읽기"
          },
          {
            "type": 2,
            "style": 5,
            "url": "https://thomasbnt.dev/blog/",
            "label": "블로그"
          }
        ]
      }
    ]
  }
}
```

디스코드에서 최종 결과는 이렇습니다.

![디스코드에서 이 글의 임베드 컴포넌트 미리보기, 전체 크기 이미지와 "글 읽기" 및 "블로그" 두 버튼](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/h8dh3s7isfv5kc1z1771.png)

구축 과정에서 내린 몇 가지 결정들입니다.

*   **썸네일 대신 미디어 갤러리**: 처음에는 섹션 + 썸네일 조합을 사용했지만, 이미지가 텍스트 옆에서 너무 작아 보였습니다. 미디어 갤러리는 마치 실제 배너처럼 이미지를 전체 크기로 표시해 줍니다.
*   **구분선 사용 안 함**: 텍스트와 이미지 사이에서 임베드를 시각적으로 불필요하게 끊어 놓는 느낌이 들었습니다.
*   **두 개의 버튼**: 하나는 게시물을 읽기 위한 것이고, 다른 하나는 블로그 홈으로 돌아가기 위한 것입니다. 간단하지만, 디스코드에서 직접 추가적인 진입점을 제공한다는 점에서 좋았습니다.
*   **`accent_color`**: 이것은 헥스(hex) 색상이 아닌 정수(integer) 값입니다. 제 블로그는 이미 각 게시물마다 `backgroundColor`라는 프론트매터에 색상이 할당되어 있습니다. 새로운 색상을 관리하기보다, 단순히 헥스 값을 십진수로 변환(`parseInt(hex.replace("#", ""), 16)`)하여 사용했습니다.

OG 태그와 마찬가지로, 이 스크립트 역시 빌드 시 서버 사이드에서 생성됩니다 (블로그는 Astro로 구축되어 모든 것이 정적입니다). 따라서 클라이언트 측에서 실행할 작업은 없습니다. 제가 직접 Astro에서 스태틱 빌드 시점에 JSON을 동적으로 생성하도록 구현했는데, 이렇게 서버에서 미리 처리해두는 방식이 성능과 크롤러 친화성 면에서 훨씬 유리하더군요.

## 피해야 할 흔한 문제점들

*   **목록에 없는 컴포넌트, 또는 버튼에 추가 키(`id`, `custom_id` 등)**: 문제가 되는 컴포넌트뿐만 아니라 **전체 페이로드를 무효화**합니다. 디버깅할 때 이 부분이 가장 까다로울 수 있습니다.
*   **OG 태그가 더 이상 필요 없다고 생각하여 제거하는 경우**: OG 태그는 여전히 필수적입니다. 임베드가 표시되지 않을 때마다 폴백 역할을 하기 때문이죠.
*   **30분 캐시 문제**: 테스트 중에는 URL 뒤에 `?v=2`를 추가하여 변경 사항이 적용되지 않아 10분 동안 헤맬 시간을 절약하세요.
*   **10초 시간 제한**: 이미지를 포함한 전체 가져오기 작업은 이 시간 내에 완료되어야 합니다. 여러 이미지를 로드하는 미디어 갤러리를 사용하면 단순 `og:image`보다 이 제한에 더 빨리 도달할 수 있습니다.

## 테스트 방법

디스코드 [임베드 디버거](https://discord.com/developers/embeds)는 크롤러가 URL을 어떻게 읽는지 정확히 보여줍니다. 어떤 태그를 찾았는지, 어떤 임베드 형식을 선택했는지 상세히 알 수 있습니다. 다른 곳에서 버그를 찾기 전에 이것부터 확인하는 것이 좋습니다.

## 마무리하며

이번 내용을 간단히 요약하자면 이렇습니다. 아무런 조치를 취하지 않아도 디스코드는 이미 `og:*` 태그를 기반으로 링크 카드를 표시합니다.

하지만 임베드 컴포넌트를 추가하는 것은 단순히 보여주는 것을 넘어, 사용자 경험을 한층 더 끌어올릴 수 있는 추가적인 옵션입니다. JSON 페이로드가 존재하고 유효할 때만 활성화되며, 그렇지 않은 경우 디스코드는 자동으로 기본 카드로 폴백합니다.

제 블로그에서는 기존의 제목, 설명, 이미지를 그대로 사용하면서도, 미디어 갤러리와 버튼을 통해 콘텐츠에 대한 직접적인 접근성을 높여 더욱 매력적인 미리보기를 제공하는 방향으로 활용했습니다. 작은 변화지만 사용자들에게는 더 풍부한 정보를 제공하고, 블로그 방문율을 높이는 데 기여할 수 있다고 생각합니다.
