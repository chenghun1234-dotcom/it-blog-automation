> 재사용 가능한 타입 가드가 AST 노드 타입뿐만 아니라, **좁혀진(narrowed) 자식 프로퍼티의 타입까지 보존**할 수 있을까?

## 🌲 컴파일러 API의 아주 흔한 패턴

우리가 `ts.Node`라는 광범위한 타입을 가지고 있다고 가정해 봅시다.

```ts
import * as ts from "typescript";

declare const node: ts.Node;
```

여기서 두 가지 사실을 알고 싶습니다.

-   이것이 `CallExpression`인가?
-   그 `expression` 프로퍼티가 `Identifier`인가?

인라인으로 작성하면 정말 쉽습니다.

```ts
if (ts.isCallExpression(node) && ts.isIdentifier(node.expression)) {
  // node: ts.CallExpression
  // node.expression: ts.Identifier
  node.expression.text;
}
```

타입스크립트는 제어 흐름을 완벽하게 이해합니다.

특별한 조치도 필요 없죠.

솔직히, 이 체크가 코드에서 단 한 번만 나타난다면, 저도 아마 이대로 둘 겁니다.

## 🤔 이런 형태를 재사용하고 싶다면?

이제 동일한 AST 형태가 여러 곳에서 나타난다고 가정해 봅시다.

-   방문자(visitor) 로직
-   `filter` 함수
-   `find` 함수
-   다른 변환 로직
-   다른 린트 규칙

이럴 때는 해당 체크 로직에 이름을 부여하는 것이 합리적입니다.

타입스크립트 v5.5부터는 간단한 함수가 타입 프레디케이트를 자동으로 추론하는 경우가 많습니다.

하지만 이 복합적인 '부모-자식' 체크는 좀 다릅니다.

```ts
const isCallWithIdentifierExpression = (node: ts.Node) =>
  ts.isCallExpression(node) && ts.isIdentifier(node.expression);
// 추론된 타입:
// (node: ts.Node) => boolean
```

따라서 추출된 프레디케이트가 두 가지 사실(부모 타입과 자식 타입 모두)을 보존하기를 원한다면, **좁혀진 타입을 명시적으로 기술**해야 합니다.

```ts
const isCallWithIdentifierExpression = (
  node: ts.Node,
): node is ts.CallExpression & {
  expression: ts.Identifier;
} => ts.isCallExpression(node) && ts.isIdentifier(node.expression);
```

이렇게 하면 잘 작동합니다. 그리고 재사용도 가능하죠.

```ts
declare const nodes: readonly ts.Node[];

const calls = nodes.filter(isCallWithIdentifierExpression);
// calls:
// Array<
//   ts.CallExpression & {
//     expression: ts.Identifier;
//   }
// >
```

> 그래서 뭐가 문제라는 거죠?

런타임상의 문제는 딱히 없습니다.

성가신 부분은 바로 이 부분을 수동으로 기술해야 했다는 겁니다 👇

```ts
ts.CallExpression & {
  expression: ts.Identifier;
}
```

하지만 우리는 이미 저 정확한 런타임 체크들을 수행했잖아요?

체크 로직을 조합하고 타입 추론이 이를 따르도록 할 수 있다면 정말 좋을 겁니다. 😸 이런 반복적인 수동 타입 정의는 개발 생산성을 저해할 뿐만 아니라, 휴먼 에러의 가능성도 높입니다. **제가 현업에서 복잡한 AST 변환 로직을 짤 때마다 이 부분이 항상 불편했는데, `is-kit`을 사용하며 훨씬 간결하고 안전하게 코드를 작성할 수 있었습니다.**

## 🧩 부모와 자식을 함께 타입 좁히기

바로 여기서 제가 `refineKey`를 사용하게 된 겁니다.

[`is-kit`](https://github.com/nyaomaru/is-kit)을 활용하면 이렇게 됩니다.

```ts
import * as ts from "typescript";
import { and, refineKey } from "is-kit";

const isCallWithIdentifierExpression = and(
  ts.isCallExpression,
  refineKey("expression", ts.isIdentifier),
);
```

이게 다입니다.

이제는

```ts
declare const node: ts.Node;

if (isCallWithIdentifierExpression(node)) {
  // node:
  // ts.CallExpression & {
  //   expression: ts.Identifier;
  // }
  node.expression.text;
}
```

흥미로운 점은 두 가지 체크 사이의 관계입니다.

```ts
ts.isCallExpression;
```

이것은 부모 타입을 좁힙니다.

그런 다음

```ts
refineKey("expression", ts.isIdentifier);
```

조합된 타입 좁히기 체인 내에서, 이미 `ts.isCallExpression`에 의해 좁혀진 부모의 한 프로퍼티를 체크하고, 체크된 자식 타입을 보존합니다.

그래서 핵심 아이디어는 이렇습니다.

> 런타임에 자식 노드를 한 번 체크하고, 그 사실을 부모 타입까지 가져오는 것.

## 😸 이것은 AST 문제가 아니었습니다

이것이 제가 리서치 과정에서 놀랐던 부분입니다.

처음에는 타입스크립트 컴파일러 API의 부족한 부분을 파고든다고 생각했습니다.

하지만 똑같은 형태가 일반 객체에서도 나타납니다.

개념적으로 이 패턴은 단지

```text
부모 타입
  ↓
프로퍼티 체크
  ↓
부모 타입 & {
  프로퍼티: 좁혀진_자식_타입
}
```

일 뿐입니다. 컴파일러 API는 단지 AST 코드가 이 패턴을 모든 곳에 포함하고 있기 때문에 이를 위한 정말 좋은 스트레스 테스트였던 거죠.

예를 들어,

```text
CallExpression
  → expression
  → Identifier
```

또는

```text
VariableDeclaration
  → initializer?
  → CallExpression
```

또는

```text
CallExpression
  → arguments[0]
  → StringLiteral
```

그래서 저는 `refineKey`를 컴파일러 API 헬퍼라고 생각하지 않습니다.

컴파일러 API는 그저 더 일반적인 조합 문제의 고급 예시일 뿐입니다. 이 깨달음을 얻었을 때, **제가 실무에서 겪었던 수많은 타입 정의의 복잡함과 씨름했던 순간들이 주마등처럼 스쳐 지나가더군요.** 결국 AST는 이 '프로퍼티 타입 좁히기' 문제를 가장 잘 보여주는 예시였던 셈입니다.

## 🔗 컴파일러 API 가드는 이미 잘 조합됩니다

제가 피하고 싶었던 또 다른 점은 타입스크립트의 기존 프레디케이트를 불필요하게 래핑하는 것이었습니다.

컴파일러 API는 이미 훌륭한 가드들을 제공하고 있습니다.

```ts
ts.isStringLiteral;
ts.isIdentifier;
ts.isCallExpression;
ts.isClassDeclaration;
```

우리는 이런 것들을 재사용해야 합니다.

예를 들어,

```ts
import * as ts from "typescript";
import { or } from "is-kit";

const isStringLike = or(ts.isStringLiteral, ts.isNoSubstitutionTemplateLiteral);

declare const nodes: readonly ts.Node[];

const strings = nodes.filter(isStringLike);
// strings:
// (
//   | ts.StringLiteral
//   | ts.NoSubstitutionTemplateLiteral
// )[]
```

`is-kit`이 자체적인

```ts
isTsStringLiteral();
isTsIdentifier();
isTsCallExpression();
```

등을 만들 이유가 전혀 없습니다. 그렇게 되면 컴파일러 API를 단순히 중복 구현하는 꼴이 될 뿐이죠.

진정으로 유용한 부분은 **조합(composition)**입니다.

## ♻️ `find`와 방문자 패턴에서 동일한 가드 재사용하기

이 정제된 형태가 여러 컨텍스트에서 나타날 때 이 방식은 더욱 유용해집니다.

예를 들어,

```ts
import * as ts from "typescript";
import { and, refineKey } from "is-kit";

const isIdentifierNamedJsxAttribute = and(
  ts.isJsxAttribute,
  refineKey("name", ts.isIdentifier),
);
```

이것을 `find`와 함께 사용할 수 있습니다.

```ts
declare const attributes: readonly ts.JsxAttributeLike[];

const attribute = attributes.find(isIdentifierNamedJsxAttribute);
// attribute:
// (
//   ts.JsxAttribute & {
//     name: ts.Identifier;
//   }
// ) | undefined
```

동일한 가드가 방문자(visitor) 패턴에서도 작동합니다.

```ts
function visit(node: ts.Node): void {
  if (isIdentifierNamedJsxAttribute(node)) {
    // node:
    // ts.JsxAttribute & {
    //   name: ts.Identifier;
    // }
    node.name.text;
  }
  ts.forEachChild(node, visit);
}
```

바로 이 지점에서 가드를 추출하는 것이 그 진가를 발휘하기 시작합니다.

런타임 규칙과 타입스크립트의 타입 좁히기가 함께 움직이는 거죠.

## 🫥 선택적 자식 노드는 다른 계약입니다

AST 노드에는 많은 선택적 프로퍼티가 포함되어 있습니다.

예를 들어, `VariableDeclaration`은 초기화 표현식(initializer)을 가질 수도 있고 안 가질 수도 있습니다.

```ts
declaration.initializer;
```

따라서 이는 필수 프로퍼티를 좁히는 것과는 약간 다릅니다.

우리는 단순히

> `initializer`를 좁히고 싶다.

는 것이 아니라,

> `initializer`가 **존재해야 하며**, 그 다음에 좁히고 싶다.

는 것을 원합니다.

이런 경우에는 `is-kit`에 `refineDefinedKey`가 있습니다.

```ts
import * as ts from "typescript";
import { refineDefinedKey } from "is-kit";

const hasCallInitializer = refineDefinedKey("initializer", ts.isCallExpression);
```

이제는

```ts
declare const declaration: ts.VariableDeclaration;

if (hasCallInitializer(declaration)) {
  // declaration.initializer: ts.CallExpression
  declaration.initializer.expression;
}
```

해당 `if` 블록 안에서는 `initializer`가 다음 두 가지를 모두 만족합니다.

-   존재한다 (present)
-   `ts.CallExpression` 타입이다

`initializer`가 없는 경우 `false`를 반환합니다.

명시적으로 `undefined`인 `initializer`도 `false`를 반환합니다.

저는 이 기능을 `refineKey`와 분리해 두는 것을 선호합니다. 왜냐하면 부재(absence)는 단순히 타입스크립트 어노테이션이 아니라, 런타임 동작이기 때문이죠.

## 📦 배열도 같은 문제가 있습니다

AST 배열은 또 다른 작은 문제를 야기합니다.

첫 번째 인자가 문자열 리터럴인 호출 표현식을 찾고 싶다고 가정해 봅시다.

`node.arguments[0];`은 단순해 보이지만, 런타임에는 배열이 비어있을 수도 있습니다.

그래서 우리는 두 가지를 증명하고 싶습니다.

-   인덱스 `0`이 존재한다.
-   해당 값이 `StringLiteral`이다.

이 또한 조합할 수 있습니다.

```ts
import * as ts from "typescript";
import { and, refineIndex, refineKey } from "is-kit";

const isCallWithStringFirstArgument = and(
  ts.isCallExpression,
  refineKey("arguments", refineIndex(0, ts.isStringLiteral)),
);
```

그럼

```ts
declare const node: ts.Node;

if (isCallWithStringFirstArgument(node)) {
  // node: ts.CallExpression
  // node.arguments[0]: ts.StringLiteral
  node.arguments[0].text;
}
```

이제 인덱스 `0`은 존재하며 `ts.StringLiteral`이라는 것이 확실해집니다.

다시 말하지만, 이것은 AST에만 국한된 아이디어가 아닙니다.

그냥

> 체크된 특정 위치를 좁히고 그 사실을 보존하는 것.

## 🪆 중첩된 체크도 조합 가능합니다

이러한 타입 좁히기는 중첩될 수도 있습니다.

다음 조건을 만족하는 함수형 선언(function-like declaration)을 찾고 싶다고 가정해 봅시다.

-   `body`가 존재한다.
-   `body`가 블록이다.
-   첫 번째 구문이 존재한다.
-   첫 번째 구문이 반환문(return statement)이다.

각 조각을 개별적으로 만들 수 있습니다.

```ts
import * as ts from "typescript";
import { and, refineDefinedKey, refineIndex, refineKey } from "is-kit";

const isBlockStartingWithReturn = and(
  ts.isBlock,
  refineKey("statements", refineIndex(0, ts.isReturnStatement)),
);

const hasBodyStartingWithReturn = refineDefinedKey(
  "body",
  isBlockStartingWithReturn,
);
```

그런 다음

```ts
declare const functionLike: ts.FunctionLikeDeclaration;

if (hasBodyStartingWithReturn(functionLike)) {
  // functionLike.body: ts.Block
  // functionLike.body.statements[0]: ts.ReturnStatement
  functionLike.body.statements[0].expression;
}
```

각 단계가 하나의 사실을 증명합니다.

`body.statements[0]`와 같은 경로 문자열도, 특별한 AST DSL도 필요 없습니다.

그냥 작은 가드들이 함께 조합된 것일 뿐입니다.

## 🔒 왜 하나의 구체적인 키나 인덱스만 다룰까요?

여기에는 중요한 제약 사항이 있습니다.

성공적인 조회는 하나의 구체적인 위치를 증명합니다.

만약 우리가 다음을 체크한다면

```ts
refineKey("expression", ...)
```

우리는 `parent.expression`에 대한 무언가를 증명한 것입니다.

특정 범위의 키 도메인에 있는 **모든 프로퍼티가 동일한 테스트를 통과했다고 증명한 것이 아닙니다.**

이것이 바로 `refinement` 헬퍼 함수들이 하나의 구체적인 키나 인덱스와 함께 작동하도록 의도된 이유입니다.

광범위한 키 유니언이나 이와 유사한 다중 위치 주장은 결과 타입을 쉽게 과장되게 만들 수 있습니다.

하나의 런타임 조회가 실제로 확인한 것보다 더 많은 것을 주장하게 하는 것보다, API를 조금 덜 마법처럼 만드는 것을 선호합니다.

## 🧪 타입스크립트 7에서는요?

이 연구는 타입스크립트 v7이 컴파일러 API 환경을 변화시켰기 때문에 특히 흥미로웠습니다.

이 섹션의 예시들은 타입스크립트 v7.0.2에서 검증되었습니다.

타입스크립트 v7.0.2 현재, AST 타입과 프레디케이트는 `typescript/unstable/ast`를 통해 노출됩니다.

따라서 동일한 조합 스타일을 여기서도 사용할 수 있습니다.

```ts
import * as ast from "typescript/unstable/ast";
import { and, refineKey } from "is-kit";

const isCallWithIdentifierExpression = and(
  ast.isCallExpression,
  refineKey("expression", ast.isIdentifier),
);
```

제가 특별히 조사했던 한 가지는 타입스크립트 v7이 `kind`를 통한 타입 좁히기를 통해 이런 `isX` 체크들을 불필요하게 만들지는 않았는지였습니다.

진정한 구별된 유니언(discriminated union)의 경우, 타입스크립트는 리터럴 식별자(discriminant)로부터 타입을 확실히 좁힐 수 있습니다.

하지만 타입스크립트 v7 AST 표면에서 현재 노출되는 광범위한 AST `Node`는 그런 종류의 '닫힌 구별된 유니언'이 아닙니다.

따라서 광범위한 AST 노드에서는 `isX` 프레디케이트가 여전히 중요합니다.

예를 들어,

```ts
import * as ast from "typescript/unstable/ast";

declare const node: ast.Node;

if (node.kind === ast.SyntaxKind.CallExpression) {
  // 여기서는 광범위한 ast.Node가 CallExpression의
  // 프로퍼티를 자동으로 노출하지 않습니다.
}
```

이러한 구별은 중요합니다.

구별된 유니언으로 모델링된 커스텀 AST 타입은 다르게 동작할 수 있습니다.

그렇다고 해서 타입스크립트 v7의 광범위한 `Node`가 현재 똑같이 동작한다는 의미는 아닙니다.

### 왜 `Node`를 닫힌 유니언으로 만들지 않았을까요?

이 내용을 올린 후, [Jake Bailey](https://bsky.app/profile/jakebailey.dev/post/3mwpa3wwmjs2d)가 아주 간결한 답변을 주었습니다.

> 느리기 때문입니다 😞

{% embed https://bsky.app/profile/jakebailey.dev/post/3mwpa3wwmjs2d %}

이것은 트레이드오프를 훨씬 더 쉽게 이해할 수 있게 해줍니다.

만약 `Node`가 모든 AST 노드 타입을 포함하는 하나의 닫힌 구별된 유니언이었다면, `kind`를 통해 잠재적으로 더 강력한 타입 좁히기 및 완전성 검사(exhaustive checks)를 얻을 수 있었을 겁니다.

예를 들어, 닫힌 유니언을 사용하면 익숙한 `never` 패턴을 활용할 수 있습니다.

```ts
switch (node.kind) {
  // 알려진 모든 kind 처리...

  default: {
    const exhaustive: never = node;
  }
}
```

새로운 변형이 추가될 때, 이 `never` 체크는 컴파일 타임에 실패하여 우리의 핸들링이 더 이상 완전하지 않다는 것을 알려줄 수 있습니다.

하지만 이러한 강력한 타입 레벨 모델은 공짜가 아닙니다.

그 대가는 타입 체킹 성능입니다. 매우 큰 닫힌 유니언은 타입 체커에게 더 많은 작업을 부여하니까요. 타입스크립트 개발팀의 이런 고민은 충분히 이해가 갑니다. **실제 대규모 프로젝트에서 타입 체킹 성능은 빌드 시간에 직결되어 개발 경험에 큰 영향을 미치기 때문이죠.**

따라서 `ast.Node`의 광범위한 형태는 단순히 타입 좁히기 기능이 누락된 것이 아닙니다.

여기에는 다음과 같은 실제적인 트레이드오프가 존재합니다.

> 강력한 컴파일 타임 완전성 vs. 타입 체킹 성능

그리고 이것이 `ast.isCallExpression()`과 같은 명시적인 프레디케이트가 여전히 중요한 역할을 하는 이유를 설명하는 데 도움이 됩니다.

타입스크립트 7과 관련된 한 가지 더 염두에 둘 만한 세부 사항이 있습니다.

`typescript/unstable/ast`의 `unstable` 부분도 중요합니다.

아직 진화 중인 API 표면에 대해 확고한 문서화 약속을 구축하고 싶지는 않습니다.

조합 패턴은 일반적입니다.

정확한 타입스크립트 v7 통합은 타입스크립트 자체와 함께 발전할 수 있습니다.

---

## ✋ 모든 AST 체크에 이 방식이 필요한 건 아닙니다

이 점 또한 중요합니다.

만약 하나의 로컬 조건이 있다면

```ts
if (ts.isReturnStatement(node) && node.expression) {
  // node: ts.ReturnStatement
  // node.expression: ts.Expression
  visit(node.expression);
}
```

저는 이걸 인라인으로 둘 겁니다.

정말입니다.

단지 가능하다고 해서

```ts
const isReturnWithExpression = ...
```

으로 바꾸는 것이 자동으로 코드를 더 좋게 만들지는 않습니다.

저는 유용한 분기점을 이렇게 생각합니다.

| 상황                           | 선호하는 방식                               |
| :----------------------------- | :--------------------------------------------- |
| 하나의 로컬 분기               | 네이티브 `ts.isX` 체크                       |
| 반복되는 AST 형태              | 이름 있는 재사용 가능 가드                   |
| 프로젝트에서 이미 `is-kit` 사용 | `refineKey`, `refineDefinedKey`, `refineIndex` |

목표는 다음이 아닙니다.

> 모든 `ts.isX` 조건을 `is-kit`으로 대체하는 것.

목표는 다음입니다.

> 런타임 사실이 재사용 가능한 어휘가 될 때, 타입 좁히기도 재사용 가능하게 유지하는 것.

---

## 🚫 이 방식이 목표로 하지 않는 것들

`is-kit`은 컴파일러 API 프레임워크가 되려고 하지 않습니다.

다음과 같은 것들을 하지 않습니다.

-   개별 컴파일러 API 함수를 래핑하는 것
-   완전한 AST 노드 형태를 검증하는 것
-   AST 순회를 제어하는 것
-   AST 사이클을 감지하는 것
-   타입스크립트 런타임 의존성을 추가하는 것
-   타입스크립트를 피어 의존성으로 요구하는 것
-   명확한 일회성 인라인 체크를 대체하는 것

컴파일러 API는 단순히 일반적인 프로퍼티 타입 좁히기의 까다로운 실제 사례일 뿐입니다.

이것이 제가 유지하고 싶은 경계입니다.

---

## 🎯 핵심은 이것입니다

저는 이 연구를 시작할 때

> 타입스크립트 컴파일러 API에 특별한 처리 방식이 필요할지도 모른다.

라고 생각했습니다.

제가 발견한 것은 더 일반적인 것이었습니다.

반복되는 문제는 다음과 같았습니다.

```text
부모 타입 좁히기
    ↓
자식 체크
    ↓
두 가지 사실 모두 보존
    ↓
프레디케이트 재사용
```

이것은 AST 노드에 유용하지만, AST 노드에 대한 것만은 아닙니다.

그래서 현재 제가 생각하는 방식은 이렇습니다.

-   실제 런타임 지식에는 네이티브 타입 가드를 사용합니다.
-   일회성 조건은 인라인으로 유지합니다.
-   동일하게 체크된 형태가 재사용 가능해지면 이름 있는 가드를 조합합니다.
-   교차 타입(intersection types)을 수동으로 다시 작성하는 대신, 부모에 대한 자식 타입 좁히기를 보존합니다.

컴파일러 API의 경우, 이런 모습일 수 있습니다.

```ts
const isCallWithIdentifierExpression = and(
  ts.isCallExpression,
  refineKey("expression", ts.isIdentifier),
);
```

작은 런타임 체크.
작은 재사용 가능한 조각들.
그리고 타입스크립트는 우리가 실제로 체크한 사실들을 계속해서 알고 있습니다. 😸

저는 필수 자식 노드, 선택적 자식 노드, 배열 인덱스, 중첩된 AST 형태, 그리고 타입스크립트 7에 대한 예시와 함께 더 자세한 가이드를 작성했습니다.
