# TypeScript 컴파일러 API, 당신의 타입 가드는 자식 노드까지 똑똑하게 기억하고 있나요? 🧠

안녕하세요! 10년 차 프런트엔드 엔지니어이자 테크 블로거, [@nyaomaru](https://github.com/nyaomaru)입니다. (요즘 `Jev`와 함께 새로운 가능성을 탐색 중인데, OpenAI의 "Decisions API"도 흥미롭게 지켜보고 있어요 😸)

> 재사용 가능한 타입 가드가 AST 노드 타입뿐만 아니라, **좁혀진(narrowed) 자식 속성까지도 함께 보존**할 수 있을까?

하지만 일반 TypeScript 객체를 가지고 똑같은 패턴을 재현해보니, 관점이 완전히 바뀌더군요.
진정으로 흥미로운 문제는 AST 자체가 아니었습니다.
바로 **속성 정제(property refinement)**였죠.

## 🌲 컴파일러 API에서 흔히 마주치는 패턴

우리가 아주 광범위한 `ts.Node`를 다루고 있다고 가정해봅시다.

```ts
import * as ts from "typescript";

declare const node: ts.Node;
```

이 `node`에 대해 두 가지 사실을 알고 싶습니다.

-   이것이 `CallExpression`인가?
-   그 `expression` 속성이 `Identifier`인가?

인라인으로 작성하면 정말 간단합니다.

```ts
if (ts.isCallExpression(node) && ts.isIdentifier(node.expression)) {
  // node: ts.CallExpression
  // node.expression: ts.Identifier
  node.expression.text;
}
```

TypeScript는 여기서 제어 흐름을 완벽하게 이해합니다.
특별히 다른 조치를 취할 필요가 없죠.
솔직히 이 정도의 체크가 한 번만 등장한다면, 저도 실무에서 굳이 추상화하지 않고 위 코드 그대로 사용하는 편입니다.

## 🤔 그 형태를 재사용하고 싶다면?

이제 똑같은 AST 형태가 여러 곳에 나타난다고 가정해봅시다.

-   방문자(visitor)
-   `filter` 함수
-   `find` 함수
-   다른 변환 로직
-   다른 린트(lint) 규칙

이런 경우, 해당 검사에 이름을 붙여 재사용하는 것이 합리적입니다.
TypeScript v5.5부터는 간단한 함수들이 종종 타입 프레디케이트(type predicate)를 자동으로 추론해주기도 합니다.
하지만 이렇게 부모와 자식의 복합적인 검사는 이야기가 다릅니다.

```ts
const isCallWithIdentifierExpression = (node: ts.Node) =>
  ts.isCallExpression(node) && ts.isIdentifier(node.expression);
// 추론된 타입:
// (node: ts.Node) => boolean
```

따라서 추출된 프레디케이트가 두 가지 사실(부모와 자식 타입)을 모두 보존하도록 하려면, **정제된 타입을 명시적으로 기술**해야 합니다.

```ts
const isCallWithIdentifierExpression = (
  node: ts.Node,
): node is ts.CallExpression & {
  expression: ts.Identifier;
} => ts.isCallExpression(node) && ts.isIdentifier(node.expression);
```

이렇게 하면 잘 동작합니다. 이제 이걸 재사용할 수 있죠.

```ts
declare const nodes: readonly ts.Node[];

const calls = nodes.filter(isCallWithIdentifierExpression);
// calls:
// Array<
//   ts.CallExpression & {
//     expression: ts.Identifier;
//   }
// >
```

> 그래서 문제가 뭐냐구요?

런타임상의 문제는 딱히 없습니다.
번거로운 부분은 바로 이 부분👇을 수동으로 일일이 작성해야 했다는 점입니다.

```ts
ts.CallExpression & {
  expression: ts.Identifier;
}
```

우리는 이미 런타임에 이 정확한 검사들을 수행했는데요.
체크 로직을 조합하고, 타입이 그 로직을 자연스럽게 따라오도록 할 수 있다면 정말 좋을 겁니다. 😸

## 🧩 부모와 자식을 함께 정제하기

제가 결국 `refineKey`를 사용하게 된 이유가 바로 여기 있습니다.

[`is-kit`](https://github.com/nyaomaru/is-kit) 라이브러리를 활용하면 다음과 같이 작성할 수 있습니다.

```ts
import * as ts from "typescript";
import { and, refineKey } from "is-kit";

const isCallWithIdentifierExpression = and(
  ts.isCallExpression,
  refineKey("expression", ts.isIdentifier),
);
```

이게 다입니다. 정말 간단하죠?

이제 이 코드를 사용하면:

```ts
declare const node: ts.Node;

if (isCallWithIdentifierExpression(node)) {
  // node:
  // ts.CallExpression & {
  //   expression: ts.Identifier;
  // }
  node.expression.text;
}
```

여기서 흥미로운 점은 두 검사 간의 관계입니다.

```ts
ts.isCallExpression;
```

이 부분은 부모 노드를 좁힙니다.
그다음,

```ts
refineKey("expression", ts.isIdentifier);
```

조합된 좁히기 체인(narrowing chain) 내에서, 이미 `ts.isCallExpression`에 의해 좁혀진 부모의 한 속성을 검사하고, 그 자식 타입까지 함께 보존하는 역할을 합니다.

결론적으로 아이디어는 다음과 같습니다.

> 런타임에 자식 요소를 한 번 검사하고, 그 사실을 부모 타입까지 끌어올려 반영한다.

## 😸 이 문제는 AST만의 문제가 아니었다

이 연구를 진행하면서 가장 놀랐던 부분이 바로 이겁니다.
저는 애초에 TypeScript 컴파일러 API의 간극을 파고들고 있다고 생각했죠.
하지만 똑같은 형태가 일반적인 객체에서도 나타납니다.

개념적으로 이 패턴은 단순히 이렇습니다.

```text
부모 (Parent)
  ↓
속성 검사 (check property)
  ↓
부모 (Parent) & {
  속성 (property): 정제된 자식 (RefinedChild)
}
```

컴파일러 API는 단지 이 패턴에 대한 아주 좋은 스트레스 테스트 환경일 뿐입니다. AST 코드는 어디에나 이 패턴이 숨어 있으니까요.

예를 들면 이런 식이죠.

```text
CallExpression
  → expression
  → Identifier
```

또는

```text
VariableDeclaration
  → initializer?
  → CallExpression
```

혹은

```text
CallExpression
  → arguments[0]
  → StringLiteral
```

그래서 저는 `refineKey`를 컴파일러 API 전용 헬퍼라고 생각하지 않습니다.
컴파일러 API는 그저 더 일반적인 조합(composition) 문제의 고급 예시일 뿐이죠. 처음엔 저도 컴파일러 API의 특정 제약이라고 생각했죠. 하지만 일반 객체에서도 같은 패턴이 나타나는 걸 보고 '아, 이건 더 넓은 문제구나' 하고 깨달았습니다.

## 🔗 컴파일러 API 가드는 이미 조합이 잘 된다

제가 피하고 싶었던 또 다른 점은 TypeScript의 기존 프레디케이트를 불필요하게 래핑(wrapping)하는 것이었습니다.
컴파일러 API는 이미 훌륭한 타입 가드들을 제공하고 있습니다.

```ts
ts.isStringLiteral;
ts.isIdentifier;
ts.isCallExpression;
ts.isClassDeclaration;
```

우리는 이들을 재사용해야 합니다.
예를 들어 `is-kit`의 `or` 함수를 사용하면 다음과 같이 활용할 수 있습니다.

```ts
import * as ts from "typescript";
import { or } from "is-kit";

const isStringLike = or(ts.isStringLiteral,　ts.isNoSubstitutionTemplateLiteral);

declare const nodes: readonly ts.Node[];

const strings = nodes.filter(isStringLike);
// strings:
// (
//   | ts.StringLiteral
//   | ts.NoSubstitutionTemplateLiteral
// )[]
```

`is-kit`이 자체적으로 다음과 같은 함수들을 만들 이유는 전혀 없습니다.

```ts
isTsStringLiteral();
isTsIdentifier();
isTsCallExpression();
```

그것은 컴파일러 API를 단순히 중복시키는 것에 불과합니다.
진정으로 유용한 부분은 바로 **조합(composition)**이죠.

## ♻️ `find`와 방문자(Visitor)에서 동일한 가드 재사용하기

정제된(refined) 형태가 여러 문맥에서 나타날 때, 이 기법은 더욱 유용해집니다.
예를 들어 봅시다.

```ts
import * as ts from "typescript";
import { and, refineKey } from "is-kit";

const isIdentifierNamedJsxAttribute = and(
  ts.isJsxAttribute,
  refineKey("name", ts.isIdentifier),
);
```

이 가드를 `find`와 함께 사용할 수 있습니다.

```ts
declare const attributes: readonly ts.JsxAttributeLike[];

const attribute = attributes.find(isIdentifierNamedJsxAttribute);
// attribute:
// (
//   ts.JsxAttribute & {
//     name: ts.Identifier;
//   }
// ) | undefined
```

동일한 가드가 방문자(visitor)에서도 작동합니다.

```ts
function visit(node: ts.Node): void {
  if (isIdentifierNamedJsxAttribute(node)) {
    // node:
    // ts.JsxAttribute & {
    //   name: ts.Identifier;
    // }
    node.name.text;
  }
  ts.forEachChild(node, visit);
}
```

런타임 규칙과 타입 추론이 함께 움직이는 것, 바로 이 지점부터 타입 가드를 별도로 추출하는 노력이 빛을 발하기 시작합니다.

## 🫥 옵셔널(Optional) 자식은 다른 계약이다

AST 노드에는 많은 옵셔널 속성들이 포함되어 있습니다.
예를 들어, `VariableDeclaration`은 초기화자(initializer)를 가질 수도, 가지지 않을 수도 있습니다.

```ts
declaration.initializer;
```

따라서 이것은 필수 속성을 정제하는 것과는 미묘하게 다릅니다.
우리는 단순히 "초기화자를 정제하라"는 것이 아니라,
"초기화자가 **존재해야 하며**, 그런 다음 그것을 정제하라"는 것을 원합니다.

이러한 경우를 위해 `is-kit`에는 `refineDefinedKey`가 있습니다.

```ts
import * as ts from "typescript";
import { refineDefinedKey } from "is-kit";

const hasCallInitializer = refineDefinedKey("initializer", ts.isCallExpression);
```

이제 이 코드를 사용하면:

```ts
declare const declaration: ts.VariableDeclaration;

if (hasCallInitializer(declaration)) {
  // declaration.initializer: ts.CallExpression
  declaration.initializer.expression;
}
```

해당 조건문 안에서 `initializer`는 다음 두 가지 사실을 모두 충족합니다.

-   존재한다 (present)
-   `ts.CallExpression` 타입이다

초기화자가 없는 경우(`undefined` 명시 포함)에는 `false`를 반환합니다.
저는 이 기능을 `refineKey`와 별도로 유지하는 것을 선호하는데, 그 이유는 '부재(absence)' 자체가 단순히 TypeScript 주석이 아니라 중요한 런타임 동작이기 때문입니다.

## 📦 배열도 똑같은 문제가 있다

AST 배열은 또 다른 작은 문제를 야기합니다.
첫 번째 인수가 문자열 리터럴인 호출을 찾고 싶다고 가정해봅시다.

이 코드 `node.arguments[0];`는 간단해 보이지만, 런타임에는 배열이 비어 있을 수 있습니다.
따라서 우리는 두 가지를 증명해야 합니다.

-   인덱스 `0`이 존재한다.
-   해당 값이 `StringLiteral`이다.

이 또한 조합할 수 있습니다.

```ts
import * as ts from "typescript";
import { and, refineIndex, refineKey } from "is-kit";

const isCallWithStringFirstArgument = and(
  ts.isCallExpression,
  refineKey("arguments", refineIndex(0, ts.isStringLiteral)),
);
```

그러면 다음과 같이 작동합니다.

```ts
declare const node: ts.Node;

if (isCallWithStringFirstArgument(node)) {
  // node: ts.CallExpression
  // node.arguments[0]: ts.StringLiteral
  node.arguments[0].text;
}
```

이제 인덱스 `0`은 존재하고 `ts.StringLiteral`이라는 것이 확실해졌습니다.
다시 말하지만, 이것은 AST에만 국한된 아이디어가 아닙니다.
단지 "특정 검사된 위치를 정제하고 그 사실을 그대로 보존한다"는 일반적인 원리일 뿐입니다.

## 🪆 중첩된 검사도 조합 가능하게 유지할 수 있다

이러한 정제 기능은 중첩해서 사용할 수도 있습니다.
다음과 같은 함수형 선언(function-like declaration)을 찾고 싶다고 가정해봅시다.

-   `body`가 존재하고
-   `body`가 블록이며
-   첫 번째 문(statement)이 존재하고
-   첫 번째 문이 `return` 문인 경우

우리는 이 구성 요소를 각각 분리해서 만들 수 있습니다.

```ts
import * as ts from "typescript";
import { and, refineDefinedKey, refineIndex, refineKey } from "is-kit";

const isBlockStartingWithReturn = and(
  ts.isBlock,
  refineKey("statements", refineIndex(0, ts.isReturnStatement)),
);

const hasBodyStartingWithReturn = refineDefinedKey(
  "body",
  isBlockStartingWithReturn,
);
```

그러면 다음과 같이 사용할 수 있습니다.

```ts
declare const functionLike: ts.FunctionLikeDeclaration;

if (hasBodyStartingWithReturn(functionLike)) {
  // functionLike.body: ts.Block
  // functionLike.body.statements[0]: ts.ReturnStatement
  functionLike.body.statements[0].expression;
}
```

각 단계는 하나의 사실을 증명합니다.
`body.statements[0]` 같은 긴 경로 문자열도, 특별한 AST DSL도 필요 없습니다.
그저 작은 가드들이 서로 조합될 뿐이죠. 이렇게 작은 조각들로 복잡한 조건을 조합할 수 있다는 점은 실제 대규모 프로젝트에서 AST를 다룰 때 코드의 가독성과 유지보수성을 크게 높여줬습니다. 제가 직접 경험해본 바입니다.

## 🔒 왜 하나의 구체적인 키(Key) 또는 인덱스(Index)만 가능한가?

여기에는 중요한 제약 사항이 있습니다.
성공적인 조회는 하나의 구체적인 위치를 증명합니다.
만약 우리가 `refineKey("expression", ...)`을 검사했다면,
`parent.expression`에 대해 뭔가 증명한 것입니다.
어떤 더 넓은 키 도메인의 모든 속성이 동일한 테스트를 통과했다고 증명한 것은 **아닙니다**.

이것이 바로 정제 헬퍼(refinement helpers)가 의도적으로 하나의 구체적인 키나 인덱스와 함께 작동하는 이유입니다.
광범위한 키 유니온(union)이나 유사한 다중 위치 주장들은 결과 타입이 실제보다 과장되기 훨씬 쉽게 만들 것입니다.
저는 단 한 번의 런타임 조회로 실제 검사한 것 이상의 것을 주장하게 하는 것보다는, API가 약간 덜 마법처럼 보이더라도 안정성을 유지하는 것을 선호합니다.

## 🧪 TypeScript 7에서는 어떨까?

TypeScript v7이 컴파일러 API 환경을 변화시키면서 이 연구는 특히 흥미로워졌습니다.
이 섹션의 예제들은 TypeScript v7.0.2를 기준으로 검증되었습니다.
TypeScript v7.0.2 현재, AST 타입과 프레디케이트는 `typescript/unstable/ast`를 통해 노출됩니다.
따라서 동일한 조합 스타일을 여기서도 사용할 수 있습니다.

```ts
import * as ast from "typescript/unstable/ast";
import { and, refineKey } from "is-kit";

const isCallWithIdentifierExpression = and(
  ast.isCallExpression,
  refineKey("expression", ast.isIdentifier),
);
```

제가 특별히 조사했던 한 가지는 TypeScript v7이 `kind` 속성을 통한 좁히기(narrowing) 덕분에 이러한 `isX` 검사가 불필요해지는지 여부였습니다.
진정한 판별된 유니온(discriminated union)의 경우, TypeScript는 리터럴 판별자(discriminant)를 통해 타입을 확실히 좁힐 수 있습니다.
하지만 TypeScript v7 AST 표면에서 현재 노출되는 광범위한 `Node` 타입은 그런 종류의 닫힌(closed) 판별된 유니온이 아닙니다.
따라서 광범위한 AST 노드를 다룰 때는 `isX` 프레디케이트들이 여전히 중요합니다.

예를 들어:

```ts
import * as ast from "typescript/unstable/ast";

declare const node: ast.Node;

if (node.kind === ast.SyntaxKind.CallExpression) {
  // 광범위한 ast.Node는 여기서 CallExpression의 속성을
  // 자동으로 노출하지 않습니다.
}
```

이러한 차이는 중요합니다.
판별된 유니온으로 모델링된 커스텀 AST 타입은 다르게 동작할 수 있습니다.
그렇다고 해서 TypeScript v7의 광범위한 `Node`가 현재 동일하게 동작한다는 의미는 아닙니다.

### 왜 `Node`를 닫힌 유니온으로 만들지 않았을까?

제가 이 주제에 대해 글을 올린 후, [Jake Bailey](https://bsky.app/profile/jakebailey.dev/post/3mwpa3wwmjs2d)가 정말 간결한 답변을 주었습니다.

> "느리기 때문입니다 😞"

{% embed https://bsky.app/profile/jakebailey.dev/post/3mwpa3wwmjs2d %}

이것은 트레이드오프(trade-off)를 훨씬 쉽게 이해하게 해줍니다.
만약 `Node`가 모든 AST 노드 타입을 포함하는 하나의 닫힌 판별된 유니온이었다면, `kind`는 잠재적으로 더 강력한 좁히기(narrowing)와 완전성(exhaustive) 검사를 제공했을 것입니다.

예를 들어, 닫힌 유니온에서는 익숙한 `never` 패턴을 사용할 수 있습니다.

```ts
switch (node.kind) {
  // 모든 알려진 종류를 처리...

  default: {
    const exhaustive: never = node;
  }
}
```

새로운 종류가 추가되면, 이 `never` 검사는 컴파일 시점에 실패하여 우리의 처리가 더 이상 완전하지 않음을 알려줄 수 있습니다.
하지만 이 강력한 타입 레벨 모델은 공짜가 아닙니다.
그 비용은 바로 타입 검사 성능입니다. 매우 큰 닫힌 유니온은 타입 검사기에게 더 많은 작업을 부여하기 때문입니다.

따라서 `ast.Node`의 광범위한 형태는 단순히 빠진 좁히기 기능이 아닙니다.
여기에는 "더 강력한 컴파일 타임 완전성 vs. 타입 검사 성능"이라는 실제적인 트레이드오프가 존재합니다.
그리고 이것은 `ast.isCallExpression()`과 같은 명시적인 프레디케이트들이 여전히 중요한 역할을 하는 이유를 설명하는 데 도움이 됩니다.

TypeScript 7 관련해서 염두에 두어야 할 한 가지 더 중요한 세부 사항이 있습니다.
`typescript/unstable/ast`의 `unstable`이라는 부분도 중요합니다.
아직 진화 중인 API 표면에 대해 확정적인 문서화 약속을 구축해서는 안 될 것입니다.
그러나 조합 패턴은 일반적입니다.
정확한 TypeScript v7 통합은 TypeScript 자체의 발전과 함께 진화할 수 있습니다.

---

## ✋ 모든 AST 검사에 이 방법이 필요한 건 아니다

이 점도 중요합니다.
만약 제가 다음과 같은 하나의 로컬 조건만 있다면,

```ts
if (ts.isReturnStatement(node) && node.expression) {
  // node: ts.ReturnStatement
  // node.expression: ts.Expression
  visit(node.expression);
}
```

저는 이 코드를 인라인으로 그대로 둘 것입니다. 정말로요.
단지 "할 수 있다"는 이유만으로 이것을 `const isReturnWithExpression = ...` 형태로 바꾸는 것이 자동으로 코드를 더 좋게 만들지는 않습니다.

유용한 분기점은 다음과 같다고 생각합니다.

| 상황                            | 선호하는 방식                      |
| :------------------------------ | :--------------------------------- |
| 하나의 로컬 분기               | 네이티브 `ts.isX` 검사             |
| 반복되는 AST 형태               | 이름 붙인 재사용 가능한 가드       |
| 프로젝트에서 이미 `is-kit` 사용 | `refineKey`, `refineDefinedKey`, `refineIndex` |

목표는 "모든 `ts.isX` 조건을 `is-kit`으로 대체하자"가 아닙니다.
목표는 "런타임 사실이 재사용 가능한 '어휘'가 될 때, 타입 추론도 함께 재사용 가능하게 만드는 것"입니다.

---

## 🚫 `is-kit`이 시도하지 않는 것들

`is-kit`은 컴파일러 API 프레임워크가 되려고 하지 않습니다.
이 라이브러리는 다음을 하지 않습니다.

-   개별 컴파일러 API 함수들을 래핑하지 않습니다.
-   완전한 AST 노드 형태를 검증하지 않습니다.
-   AST 순회(traversal)를 제어하지 않습니다.
-   AST 사이클을 감지하지 않습니다.
-   TypeScript 런타임 의존성을 추가하지 않습니다.
-   TypeScript를 피어 의존성(peer dependency)으로 요구하지 않습니다.
-   명확하고 한 번만 사용되는 인라인 검사를 대체하지 않습니다.

컴파일러 API는 단지 일반적인 속성 정제(generic property refinement)의 까다로운 실제 예시일 뿐입니다.
제가 지키고 싶은 경계가 바로 이것입니다.

## 🎯 가장 중요한 핵심

저는 이 연구를 시작할 때 "TypeScript 컴파일러 API에 뭔가 특별한 처리가 필요할지도 몰라"라고 생각했습니다.
하지만 제가 찾은 것은 훨씬 더 일반적인 문제였습니다.
반복적으로 나타나는 문제는 바로 이것이었습니다.

```text
부모 좁히기 (narrow parent)
    ↓
자식 검사 (check child)
    ↓
두 가지 사실 모두 보존 (preserve both facts)
    ↓
프레디케이트 재사용 (reuse the predicate)
```

이것은 AST 노드에 유용하지만, 사실 AST 노드에만 국한된 이야기는 아닙니다.
따라서 제 현재 정신 모델은 이렇습니다.

-   실제 런타임 지식에는 네이티브 타입 가드를 사용하세요.
-   한 번만 사용되는 조건은 인라인으로 두세요.
-   동일한 검사 형태가 재사용 가능한 '어휘'가 될 때, 이름 붙인 가드를 조합하세요.
-   교차 타입(intersection types)을 수동으로 다시 작성하는 대신, 부모에 자식 정제 정보를 보존하세요.

컴파일러 API의 경우, 이런 모습이 될 수 있겠죠.

```ts
const isCallWithIdentifierExpression = and(
  ts.isCallExpression,
  refineKey("expression", ts.isIdentifier),
);
```

작은 런타임 검사들.
작고 재사용 가능한 조각들.
그리고 TypeScript는 우리가 실제로 검사한 사실들을 기억합니다. 😸
