# { } + [ ] = 0, 이게 말이 돼?! 10년차 개발자가 파헤치는 자바스크립트의 '마법 같은' 비밀

자바스크립트(JavaScript)는 그야말로 전설적인 프로그래밍 언어입니다. 1990년대 중반, 불과 10일 만에 뚝딱 만들어졌으니 말이죠. 당시 넷스케이프가 마이크로소프트에 치명타를 날리려던 브라우저 전쟁 한복판에서 태어났습니다. 결과는 다들 아시겠지만, 원래 계획대로 흘러가진 않았죠. 오늘날 자바스크립트를 사랑하는 사람도, 혐오하는 사람도, 그저 놀림거리로 삼는 사람도 있지만, 한 가지 진실은 변치 않습니다. **현대 웹은 자바스크립트 없이는 절대 존재할 수 없다는 겁니다!**

수십 년간 자바스크립트는 셀 수 없이 많은 혁신을 거듭해 왔습니다. 지금의 기능은 1990년대의 언어 능력과는 비교할 수 없을 정도죠. 그런데 여기 아주 작은 문제가 하나 있습니다. 언어에 어떤 변화를 주든, 아직도 수많은 웹사이트가 오래된 자바스크립트 동작 방식에 의존하고 있다는 사실을 고려해야 한다는 점입니다. 그리고 그중 일부 웹사이트는 아마 영원히 그 코드를 실행하고 있을지도 모릅니다.

그러니 뭐, **자바스크립트의 '기묘함'은 아마 영원히 우리 곁에 머무를 겁니다!** 😂

오랜만에 제 블로그에서 한때 인기가 많았던 **JS WTF** 시리즈를 다시 꺼내 들기로 했습니다. 이유는 아주 간단합니다. iJS 뮌헨 일정을 마치고 프랑크푸르트 공항에서 비행기를 기다리며 두 시간을 때워야 하거든요(자세한 건 묻지 마세요). 획기적이고 심도 깊은 기술 글을 쓰기엔 충분치 않은 시간이고, 그렇다고 그냥 벽만 쳐다보고 있을 순 없잖아요?

자, 그럼 제가 좋아하는 자바스크립트 구문 중 하나를 한번 살펴보죠.

```javascript
{} + [] // 0
```

네, 제대로 보셨습니다. 특정 상황에서, 자바스크립트에서 빈 객체에 빈 배열을 더하면 0이 됩니다. **그리고 이건 완벽하게 이치에 맞습니다!** 🤡

## 잠깐, 뭐라고요? 왜 이런 일이 일어나는 거죠?

가장 먼저 아셔야 할 것은 **자바스크립트가 이 상황에서 `{}`를 '객체'로 해석하지 않을 수도 있다는 점입니다!** 맥락에 따라 자바스크립트 파서(parser)는 해당 표현식을 완전히 별개의 두 가지로 처리할 수 있습니다.

클래식 자바스크립트 스크립트에서 문(statement)의 시작 부분에 다음과 같은 코드가 있다고 가정해 봅시다.

```javascript
{} + []
```

자바스크립트는 이것을 이렇게 해석할 수 있습니다.

```javascript
{}    // 비어있는 코드 블록
+[]   // 빈 배열에 적용된 단항 덧셈 연산자(Unary plus) (대체 뭐가 문제겠어?)
```

맞습니다. 첫 번째 `{}`는 객체 리터럴이 아닙니다. 단순히 아무것도 하지 않는 빈 코드 블록일 뿐이죠. 그럼 두 번째 부분은요? 음, 여기서부터 재미가 시작됩니다.

## 타입 강제 변환의 마법 ✨

다음 표현식은:

```javascript
+[]
```

우리 멋진 언어 자바스크립트가 자랑하는 것 중 하나인 **타입 강제 변환(Type Coercion)**의 전형적인 예시입니다.

아마 다들 아시겠지만, 자바스크립트는 동적(dynamic)이며 약하게 타입이 지정된(weakly typed) 언어입니다.

동적 타이핑(Dynamic typing)은 변수가 특정 타입에 영구적으로 묶여 있지 않다는 것을 의미합니다. 변수에 숫자를 할당했다가 나중에 문자열로 바꿔도 자바스크립트는 아무런 불평을 하지 않습니다.

하지만 더 있습니다! 자바스크립트는 암시적 타입 변환도 수행하는데, 이것이 자바스크립트가 종종 '약타입'으로 묘사되는 이유 중 하나입니다. 그리고 때로는 이러한 변환이 다소… 창의적인 결과를 만들어내죠.

우리의 단항 덧셈 연산자(unary plus operator)를 보시죠.

```javascript
+[]
```

숫자를 더하거나 문자열을 연결하는 데 사용되는 이항 `+` 연산자와 달리, **단항 덧셈 연산자는 피연산자를 숫자 값으로 변환하려고 시도합니다.** 이 경우, 기본적으로 다음과 같이 작동합니다.

```javascript
Number([])
```

네, 우리는 배열을 숫자로 변환하려고 합니다. 왜 안 되겠어요?

하지만 자바스크립트가 이 작업을 완료하려면 또 다른 변환을 수행해야 합니다. 배열은 객체이며, 자바스크립트는 먼저 배열로부터 원시 값(primitive value)을 얻어야 합니다. 일반적인 빈 배열의 경우, 그 과정에서 `toString()` 메서드를 호출하게 됩니다.

그리고 아시겠나요?

```javascript
[].toString(); // ""
```

빈 배열은 빈 문자열이 됩니다.

그래서 우리의 변환은 사실상 다음과 같이 보입니다.

```javascript
Number([]);

// 첫째, 배열은 원시 문자열이 됩니다:
Number("");

// 그 다음, 빈 문자열은:
0
```

왜냐하면:

```javascript
Number("") // 0
```

따라서:

```javascript
+[] // 0
```

이는 우리의 원래 구문:

```javascript
{} + []
```

이 빈 블록과 단항 덧셈 연산자로 파싱될 때, 사실상 다음과 같이 된다는 의미입니다.

```javascript
{} // 아무것도 하지 않는다

+[] // 0
```

**그리고 이것이 우리가 0을 얻는 방법입니다!** 정말 간단하고 명확하죠, 안 그래요? 🤡

솔직히 말해, 정확히 이런 구문이 이렇게 완벽하게 정상적인 결과를 만들어내는 다른 언어는 떠오르지 않습니다. 심지어 우리가 사랑하는 PHP도 이런 경우라면 치명적인 에러(fatal error)를 뿜어낼 겁니다. 물론 PHP도 자체적인 흥미로운 놀라움이 많으니 너무 가혹하게 판단해서는 안 되겠죠.

여기서 한 가지 중요한 세부 사항이 있습니다. **이 동작은 코드가 어떻게 파싱되는지에 따라 달라집니다.** 예를 들어 보겠습니다.

```javascript
// 클래식 스크립트에서, 독립적인 문(statement)으로 사용될 때:
{} + [] // 0

// 자바스크립트가 {}를 객체로 해석하도록 강제할 때:
({} + []) // "[object Object]"

// 함수 호출 내부에 있을 때:
console.log({} + []); // "[object Object]"
```

## 좋아요, 그럼 `[] + []`는 어떻죠?

이제 타입 강제 변환을 이해했으니, 이건 명확할 겁니다.

```javascript
[] + [] // ""
```

여기서는 이항 `+` 연산자를 다루고 있습니다. 자바스크립트는 두 배열을 모두 원시 값으로 변환합니다. 뭐, 두 개의 빈 문자열을 더할 때 뭘 기대하셨겠어요? 😀 아무것도 더하기 아무것도 는 아무것도! 아름답습니다.

## 그런데 이제 덧셈의 교환 법칙조차 선택 사항인가요 😂

같은 논리를 따라, 다른 표현식도 시도해 봅시다.

```javascript
[] + {} // "[object Object]"
```

잠깐만요.

방금 우리가 **`{} + []`는 0**이라고 확인하지 않았나요?

그런데 피연산자의 순서를 바꾸자 완전히 다른 결과가 나온다고요? 덧셈의 교환 법칙조차 자바스크립트에서는 선택 사항인 모양입니다. xD

글쎄요, 엄밀히 말하면 여기서 항상 수학적인 덧셈을 하는 것은 아니고, 파서가 이 표현식들을 다르게 처리합니다. 하지만 좋은 농담을 기술적인 세부 사항으로 망치진 맙시다. 실제로 일어나는 일은 이렇습니다.

```javascript
[] + {}
```

이 표현식에서 빈 배열은 빈 문자열이 됩니다.

```javascript
[].toString() // ""
```

그럼 빈 객체는요? 음, 일반 자바스크립트 객체는 자체적으로 멋진 문자열 표현을 가지고 있습니다.

```javascript
({}).toString() // "[object Object]"
```

그래서 자바스크립트는 사실상 다음을 수행합니다.

```javascript
"" + "[object Object]"
```

그리고 이는 우리에게 다음을 제공합니다.

```javascript
"[object Object]"
```

이게 다입니다! **도리깨를 만드는 것만큼 쉽죠.** 이게 폴란드 속담인데, '말도 안 되게 쉽다'는 뜻이거든요. 제가 실무에서 이런 종류의 미묘한 동작 때문에 예상치 못한 버그를 잡을 때마다, 자바스크립트의 유연함이 때로는 양날의 검 같다는 생각을 하곤 합니다. 특히 API 응답 데이터를 다룰 때 `typeof`나 강제 변환에 대한 이해가 부족하면 데이터를 엉뚱한 타입으로 처리해서 엉뚱한 결과를 뱉어내기도 하죠. 자바스크립트와 딱 맞는 표현 같아요. 😂

## 마지막으로

자바스크립트의 기묘한 세계로 떠나는 작은 여정이 즐거웠기를 바랍니다. 그리고 이 글을 읽고 나서 이 훌륭한 언어의 아름다움과 독창성을 더욱 높이 평가해 주셨으면 좋겠습니다.

결국 자바스크립트는 30년 넘게 우리를 즐겁게 해주고 있으며, 앞으로도 수많은 놀라움을 선사할 것이라고 강력히 의심합니다.

그리고 가장 좋은 점은? **위의 예시 중 어느 것도 버그가 아니라는 겁니다.** 이 모든 현상은 자바스크립트의 파싱 규칙, 타입 강제 변환, 그리고 언어의 오랜 하위 호환성 역사에서 비롯된 결과입니다. 그러니 다음번에 누군가가 `{} + []`가 0이 될 수 있다고 자바스크립트가 고장 났다고 말하면, 자랑스럽게 왜 그것이 완벽하게 이치에 맞는지 설명해 줄 수 있을 겁니다.

다음번에는 `{} + {} = NaN`인 이유를 알려드릴게요… 하지만 즐거운 시간은 빨리 흐르는 법, 곧 비행기 탈 준비를 해야겠네요!
