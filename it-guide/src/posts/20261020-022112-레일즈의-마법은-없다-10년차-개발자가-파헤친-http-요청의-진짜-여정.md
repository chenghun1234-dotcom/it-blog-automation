# 레일즈의 '마법'은 없다: 10년차 개발자가 파헤친 HTTP 요청의 진짜 여정

모던 웹 프레임워크를 다뤄본 개발자에게 Ruby on Rails에 대해 어떻게 생각하는지 물어보면, 십중팔구 30초 안에 같은 단어를 듣게 될 겁니다.

*"마법 같아요!"*

제너레이터(Generator)를 실행하면, 순식간에 데이터베이스 테이블이 생겨납니다. 텅 빈 모델 클래스만 작성해도, 단 하나의 속성 선언 없이 스키마의 모든 컬럼을 즉시 알아챕니다. 컨트롤러 액션 내부에 인스턴스 변수를 정의했는데, 마치 객체 경계가 사라진 듯 전혀 다른 뷰 템플릿 안에서 나타나죠. `require` 한 번 하지 않았는데도 클래스를 참조하면 루비가 알아서 찾아줍니다.

초보 개발자들에게는 분명 마술처럼 느껴질 겁니다. 회의론자들에게는 문제가 발생했을 때 추론하거나 디버깅할 수 없는 위험한 블랙박스처럼 보이기도 하죠.

하지만 레일즈에는 마법 따위는 없습니다.

레일즈의 모든 컨벤션은 평범한 루비 메타프로그래밍, 표준 객체 지향 디자인 패턴, 그리고 20년 이상 웹의 가장 큰 애플리케이션들을 조용히 움직여온 우아한 파이프라인 아키텍처로 이루어져 있습니다. 문법적 편의성이라는 껍질을 벗겨내면, 레일즈는 이해하기 힘든 블랙박스가 아니라 시스템 아키텍처의 걸작으로 그 진면목을 드러냅니다.

레일즈를 완벽하게 마스터하고 어떤 문제든 자신 있게 디버깅하려면, HTTP 요청이 서버 소켓에 도달하는 순간부터 미들웨어 양파층, 라우터, 모델 리플렉션 엔진을 거쳐 뷰 렌더러로 빠져나오는 전 과정을 따라가 볼 필요가 있습니다.

지금부터 그 막후에서 무슨 일이 벌어지고 있는지 자세히 파헤쳐 보겠습니다.

## 요청 양파: Puma부터 ActionDispatch까지

레일즈가 여러분의 코드를 건드리기도 전에, 요청은 소프트웨어 아키텍트들이 **'요청 양파(Request Onion)'**라고 부르는 계층을 통과해야 합니다.

가장 바깥쪽에는 웹 서버(주로 Puma)가 앉아 있습니다. Puma는 원시 TCP 소켓을 수신하고, 들어오는 HTTP 요청을 받아 원시 헤더와 바디를 파싱합니다. 그리고 이 데이터를 **Rack 환경(Rack environment, `env`)**이라는 일반 루비 해시로 감싸죠.

그다음 Puma는 루비 웹 세계의 보편적인 약속인 **Rack 인터페이스**를 사용해 이 해시를 레일즈에 전달합니다.

```plaintext
[HTTP Request] ──> Puma Web Server ──> call(env) ──> [Rack Middleware Stack] ──> [ActionDispatch Router]
```

Rack 애플리케이션은 놀랍도록 단순합니다. `call(env)`에 응답하고 다음 세 요소를 포함하는 3요소 배열을 반환하는 모든 루비 객체입니다.
1.  정수 HTTP 상태 코드(예: `200`)
2.  HTTP 응답 헤더 해시
3.  열거 가능한 바디 스트림

![The Anatomy of a Rails Request: Puma, Rack Middlewares, ActionDispatch Router, Controller, and View](https://iili.io/nMKGGCF.png)

Puma가 `Rails.application.call(env)`를 호출할 때, 요청은 여러분의 컨트롤러로 곧바로 들어가지 않습니다. 대신, 20개가 넘는 내장 **Rack 미들웨어** 스택을 통해 단계별로 전달됩니다.

각 미들웨어는 마치 양파 껍질처럼 다음 미들웨어를 감싸는 구조로 동작하죠.

1.  **`ActionDispatch::HostAuthorization`**: 허용된 호스트 이름과 `Host` 헤더를 비교하여 DNS 재바인딩 공격을 방어합니다.
2.  **`ActionDispatch::SSL`**: HTTPS 리다이렉션을 강제하고 Strict-Transport-Security 헤더를 설정합니다.
3.  **`Rack::Sendfile`**: Nginx와 같은 리버스 프록시로 정적 파일 서빙을 오프로드합니다.
4.  **`ActionDispatch::Cookies` 및 `CookieStore`**: 서명된 세션 쿠키를 복호화하고, 변조 방지를 위해 HMAC 서명을 검증하며, 세션 페이로드를 메모리로 역직렬화합니다.
5.  **`ActionDispatch::ShowExceptions`**: 애플리케이션 깊은 곳에서 발생한 처리되지 않은 오류를 잡아내어, 친숙한 HTML 오류 페이지 또는 JSON 진단으로 변환합니다.

이러한 보호 장치들을 모두 통과한 후에야 요청은 레일즈 라우팅 엔진인 **ActionDispatch::Journey**에 도달합니다. 제가 실무에서 CORS 문제나 세션 관련 오류를 만났을 때, 이 미들웨어 스택을 제대로 이해하고 있어야 빠르게 원인을 찾아내고 적절한 미들웨어 설정을 통해 해결할 수 있었습니다. 특히 보안 관련 미들웨어는 프레임워크 단에서 대부분 처리해주지만, 문제가 발생하면 결국 이 "양파" 속을 들여다봐야 해요.

Journey는 부팅 시 `config/routes.rb` 파일을 파싱하여 결정론적인 라우팅 트리를 컴파일합니다. 그리고 HTTP 동사(`GET`)와 경로(`/articles/42`)를 매칭하고, 파라미터(`id: "42"`)를 추출하며, `ArticlesController#show`가 이 요청을 처리해야 한다고 판단한 뒤 호출을 디스패치합니다.

## 보이지 않는 컬럼의 미스터리: ActiveRecord 스키마 리플렉션

컨트롤러 안으로 들어오면 데이터베이스 쿼리를 실행합니다.

```ruby
class ArticlesController < ApplicationController
  def show
    @article = Article.find(params[:id])
  end
end
```

이제 여러분의 모델 파일 `app/models/article.rb`를 살펴보세요.

```ruby
class Article < ApplicationRecord
end
```

이 클래스 정의를 자세히 보면 **어떤 컬럼 선언도 없습니다.**

`attr_accessor :title`도, `property :body, String`도 없습니다. 모델 디렉토리 안에 스키마 정의 파일도 없죠.

그런데도 여러분은 `article.title`, `article.body`, `article.published?`와 같이 작성할 수 있고, 루비는 이를 완벽하게 실행합니다.

순수한 루비 객체가 한 번도 선언하지 않은 속성의 이름과 타입을 어떻게 알 수 있을까요?

그 해답은 바로 **동적 스키마 리플렉션(Dynamic Schema Reflection)**에 있습니다.

![Why ActiveRecord Never Declares Columns: Schema introspection and GeneratedAttributeMethods module](https://iili.io/nMKGMEg.png)

레일즈 애플리케이션이 부팅되거나, 코드에서 `Article`가 처음 참조될 때 ActiveRecord는 아주 영리한 작업을 수행합니다.

1.  **데이터베이스 카탈로그 조사 (Introspection):** ActiveRecord는 데이터베이스 어댑터에 연결하여 데이터베이스 카탈로그를 쿼리합니다. (PostgreSQL에서는 `information_schema.columns`를 쿼리하고, SQLite에서는 `PRAGMA table_info(articles)`를 실행합니다.)
2.  **스키마 수집:** 데이터베이스 엔진으로부터 컬럼 이름, 데이터 타입, NULL 허용 제약 조건, 기본값 등을 정확하게 가져옵니다.
3.  **동적 모듈 생성:** `Article` 클래스에 직접 메서드를 정의하는 대신, ActiveRecord는 `GeneratedAttributeMethods`라는 숨겨진 내부 모듈을 생성합니다.
4.  **게터/세터 메타프로그래밍:** 데이터베이스 카탈로그에서 반환된 모든 컬럼에 대해 ActiveRecord는 이 모듈 내부에 메서드 정의를 평가합니다.

```ruby
# ActiveRecord가 내부적으로 생성하는 개념적인 표현:
module GeneratedAttributeMethods
  def title
    _read_attribute('title')
  end

  def title=(value)
    _write_attribute('title', value)
  end

  def title?
    _query_attribute('title')
  end
end
```

5.  **모듈 포함(Inclusion):** ActiveRecord는 `GeneratedAttributeMethods`를 `Article` 클래스에 포함시킵니다.

메서드들이 `Article` 클래스 자체보다는 포함된 모듈 안에 존재하기 때문에, 여러분은 자신의 모델에서 `def title`을 쉽게 오버라이드하고 `super`를 호출하며, ActiveRecord의 내부 스토리지 엔진을 망가뜨리지 않고도 사용자 정의 포맷을 추가할 수 있습니다!

데이터베이스는 여러분의 데이터 모델에 대한 유일한 진실의 원천으로 남습니다. 레일즈는 그 진실을 루비의 메서드 테이블에 동적으로 반영하여, 수동 클래스 선언과 데이터베이스 마이그레이션을 동기화할 필요를 없애줍니다. 저는 ActiveRecord가 이런 식으로 유연하게 동작한다는 걸 알고 나서 모델 디자인에 대한 시야가 훨씬 넓어졌어요. 예를 들어, `title_with_prefix` 같은 가상 속성을 만들 때도 이 원리를 활용해 충돌 없이 커스텀 로직을 추가할 수 있습니다.

## 객체 경계를 넘나드는 컨트롤러 상태의 뷰 전달 방식

다음은 다른 언어에서 넘어온 프로그래머들에게 가장 당혹스러운 행동 중 하나입니다.

```ruby
# app/controllers/articles_controller.rb
class ArticlesController < ApplicationController
  def show
    @article = Article.find(params[:id])
    @comments = @article.comments
  end
end
```

그리고 뷰 템플릿에서는 이렇게 사용합니다.

```erb
<!-- app/views/articles/show.html.erb -->
<h1><%= @article.title %></h1>
<p><%= @article.body %></p>
```

표준 객체 지향 프로그래밍에서 인스턴스 변수(`@article`, `@comments`)는 그것을 생성한 특정 객체 인스턴스에 엄격하게 비공개입니다. `ArticlesController`의 인스턴스가 자신의 비공개 `@variables`를 `ActionView::Base`의 인스턴스에 노출할 수 없다는 뜻이죠.

컨트롤러와 뷰는 전혀 다른 시점에 인스턴스화되는 완전히 별개의 클래스입니다.

그렇다면 `@article`은 어떻게 두 개의 완전히 분리된 객체 간의 경계를 넘나들까요?

그 연결 고리는 바로 **`view_assigns`**라는 메서드입니다.

![The Magic of @instance_variables in Views: The view_assigns extraction and injection bridge](https://iili.io/nMKGV4a.png)

컨트롤러 액션 실행이 끝나면, 레일즈는 렌더링 시퀀스를 시작합니다.

1.  **인스턴스 상태 추출:** 컨트롤러는 `view_assigns`를 호출합니다. 이 메서드는 컨트롤러 객체의 모든 인스턴스 변수를 검사하고, 내부 레일즈 변수(예: `@_response`, `@_request`)를 제외한 후, 남은 사용자 변수들을 일반 루비 해시로 변환합니다.

```ruby
# view_assigns가 반환하는 것:
{
  "article" => #<Article id: 42, title: "Rails Internals">,
  "comments" => [#<Comment id: 1>, #<Comment id: 2>]
}
```

2.  **뷰 컨텍스트 인스턴스화:** 레일즈는 템플릿 렌더링을 담당할 새로운 `ActionView::Base` 객체를 인스턴스화합니다.
3.  **데이터 전달 메타프로그래밍:** 레일즈는 assigns 해시를 반복하며 루비의 리플렉션 메서드를 사용하여 각 키와 값을 새 뷰 인스턴스에 직접 주입합니다.

```ruby
assigns.each do |key, value|
  view.instance_variable_set("@#{key}", value)
end
```

4.  **ERB 템플릿 컴파일:** 레일즈는 ERB 템플릿을 가져와 HTML과 내장된 루비 태그를 순수한 루비 메서드로 컴파일한 다음, 뷰 인스턴스의 컨텍스트에서 해당 메서드를 실행합니다.

이제 뷰 인스턴스가 `@article`과 `@comments`와 동일한 인스턴스 변수를 가지게 되었으므로, 템플릿은 이를 원활하게 읽어들입니다. 객체 경계를 무시하는 마법처럼 보였던 것은 `instance_variable_set`을 통해 실행되는 자동화된 딕셔너리 전달 방식이었을 뿐이죠. 제가 신입 때 자바 스프링으로 백엔드를 하다가 레일즈로 넘어왔을 때, 이 부분이 가장 신기하면서도 '어떻게 된 일이지?' 의아했던 지점이었죠. 결국 원리를 알고 나니 다른 프레임워크의 모델/뷰 간 데이터 전달 방식보다 훨씬 직관적이라는 생각이 들었습니다.

## Zeitwerk: `require`를 쓰지 않는 이유

표준 루비에서는 다른 파일에 정의된 클래스를 사용하기 전에 명시적으로 로드해야 합니다.

```ruby
require_relative "../services/payment_processor"
```

하지만 레일즈에서는 코드베이스 어디에서든 `PaymentProcessor.charge(user)`라고만 작성하면 제대로 작동합니다. `require` 문을 거의 작성할 필요가 없죠.

수년 동안 레일즈는 루비의 `const_missing` 콜백에 연결된 사용자 정의 메커니즘을 사용하여 이 기능을 구현했습니다. 그러나 `const_missing`은 순환 종속성 교착 상태, 스레드 안전성 문제, 혼란스러운 로드 순서 버그 등 악명 높은 엣지 케이스로 고통받았습니다.

최신 레일즈는 루비를 위해 특별히 작성된 오토로딩 엔진인 **Zeitwerk**를 채택하여 이 문제를 해결했습니다.

![Zeitwerk Autoloading: Development on-demand reloading vs Production eager loading](https://iili.io/nMKGhYv.png)

Zeitwerk는 깔끔한 컨벤션을 강제합니다. **파일 경로는 상수 이름을 엄격하게 반영해야 합니다.**

*   상수 `User`는 `app/models/user.rb`에 매핑됩니다.
*   상수 `Users::AccountNotifier`는 `app/services/users/account_notifier.rb`에 매핑됩니다.

Zeitwerk는 이를 다양한 환경에서 어떻게 처리할까요?

### 개발 환경: 재시작 없는 즉각적인 리로드

개발 환경에서는 서버 부팅 시 애플리케이션 파일이 거의 메모리에 로드되지 않습니다. 코드에서 `User`와 같이 참조되지 않은 상수를 처음 만나면, Zeitwerk가 이 검색을 가로채고 이름을 `app/models/user.rb`로 변환하여 필요할 때 파일을 로드합니다.

더 중요한 것은, Zeitwerk가 파일 시스템 감시자와 통합되어 있다는 점입니다. 텍스트 편집기에서 파일을 수정하면, Zeitwerk는 루비의 메모리 공간에서 해당 상수를 언로드합니다.

다음 브라우저 새로고침 시, 레일즈는 디스크에서 파일을 신선하게 다시 평가합니다. Puma를 재시작하거나 컴파일 단계를 기다릴 필요 없이 즉각적인 업데이트를 얻을 수 있죠. Zeitwerk 덕분에 개발 생산성이 정말 비약적으로 상승했다고 생각합니다. 특히 수십 개의 모델 파일이 있는 대규모 프로젝트에서는 개발 서버 재시작 없이 바로 변경 사항이 반영되는 이 기능이 정말 소중하죠.

### 프로덕션 환경: Eager 로딩과 Copy-on-Write

프로덕션 환경에서는 온디맨드 오토로딩이 완전히 비활성화됩니다.

대신, 애플리케이션 부팅 중에 Zeitwerk는 **이거 로드(Eager Load)**를 실행합니다. `app/` 내부의 모든 디렉토리를 크롤링하여 Puma가 워커 프로세스를 생성하기 전에 모든 클래스, 모듈, 템플릿을 루비의 메모리 공간으로 로드합니다.

이는 두 가지 중요한 프로덕션 이점을 제공합니다.

1.  **런타임 디스크 I/O 없음:** 들어오는 사용자 요청은 디스크에서 파일을 찾거나 로드하는 데 CPU 사이클을 소비하지 않습니다.
2.  **Copy-on-Write (CoW) 메모리 최적화:** 모든 클래스가 Puma가 자식 워커를 포크하기 전에 마스터 프로세스에 할당되기 때문에, 모든 워커 프로세스는 정확히 동일한 물리적 RAM 페이지를 공유합니다. 5개의 워커 프로세스를 가진 레일즈 애플리케이션은 5개의 개별 인스턴스가 독립적으로 시작된 경우보다 훨씬 적은 메모리를 소비합니다.

## 스레드 고속도로: ActiveRecord 커넥션 풀링

애플리케이션이 수십 개의 동시 요청을 받을 때, 레일즈는 여러 스레드가 데이터베이스 연결을 손상시키지 않도록 어떻게 보장할까요?

Puma는 멀티 스레드 웹 서버입니다. 각 Puma 워커 프로세스는 스레드 풀(일반적으로 워커당 3~5개의 스레드)을 실행합니다. 각 스레드는 독립적인 HTTP 요청을 동시에 처리합니다.

만약 두 스레드가 동일한 TCP 연결을 통해 PostgreSQL에 원시 SQL 명령을 동시에 작성하려고 시도한다면, 프로토콜 스트림이 뒤섞여 소켓이 충돌할 것입니다.

이것을 안전하게 관리하기 위해 ActiveRecord는 **커넥션 풀(Connection Pool)**을 사용합니다.

![ActiveRecord Connection Pool Architecture: Puma Worker Threads checking out connections from ConnectionPool](https://iili.io/nMKGjvR.png)

커넥션 풀은 스레드 안전한 '리스 오피스'처럼 작동합니다.

1.  **커넥션 체크아웃:** 스레드 1이 `Article.find(42)`를 실행할 때, `ConnectionPool`에 데이터베이스 커넥션을 요청합니다.
2.  **스레드 어피니티:** 풀은 사용 가능한 커넥션을 스레드 1에 할당하고, 그 커넥션을 스레드의 로컬 스토리지와 연결합니다.
3.  **쿼리 실행:** 스레드 1은 전용 커넥션을 통해 안전하게 SQL 문을 실행합니다.
4.  **커넥션 체크인:** HTTP 요청이 완료되고 Rack 응답이 컨트롤러를 벗어나면, 외부 Rack 미들웨어(`ActiveRecord::Rack::ConnectionManagement` 또는 executor 훅)가 커넥션을 풀에 다시 체크인하여 다른 대기 스레드에서 사용할 수 있도록 합니다.

### 풀 크기 방정식

커넥션 풀을 이해하는 것은 레일즈에서 가장 흔한 프로덕션 재앙 중 하나인 `ActiveRecord::ConnectionTimeoutError`를 예방하는 데 도움이 됩니다.

`config/database.yml` 파일은 풀 크기를 정의합니다.

```yaml
production:
  adapter: postgresql
  pool: <%= ENV.fetch("RAILS_MAX_THREADS") { 5 } %>
```

만약 Puma가 10개의 스레드를 실행하도록 구성되어 있지만, 데이터베이스 풀 크기가 5로 설정되어 있다면, 6번째 동시 스레드는 활동 중인 커넥션이 사용 가능해질 때까지 최대 5초 동안 대기하다가 치명적인 타임아웃 오류를 발생시킬 것입니다.

데이터베이스 풀 크기를 Puma의 `max_threads`와 같거나 약간 크게 유지하면, 모든 활성 워커 스레드가 경쟁 없이 쿼리를 실행할 수 있습니다. 프로덕션 환경에서 `ActiveRecord::ConnectionTimeoutError`를 만났을 때, 대부분은 이 스레드와 커넥션 풀 설정을 제대로 이해하지 못해서 벌어지는 일입니다. 제가 이걸 모르고 초기에 몇 번 밤샘 디버깅을 했던 아픈 기억이 있죠. 이제는 항상 `pool >= max_threads` 공식을 잊지 않고 적용합니다.

## 대량 할당의 문을 지키는 문지기: Strong Parameters

레일즈 역사상 가장 중대한 보안 혁신 중 하나는 **Strong Parameters**입니다.

레일즈 초기 버전에서는 개발자들이 이렇게 작성했습니다.

```ruby
# ❌ 예전의 위험한 방식:
def create
  @user = User.create(params[:user])
end
```

이 방식은 **대량 할당 공격(Mass Assignment Attack)**이라는 치명적인 취약점을 만들었습니다. 악의적인 사용자는 의도치 않은 속성을 포함한 POST 요청을 보낼 수 있었습니다.

```json
{
  "user": {
    "name": "Attacker",
    "email": "attacker@evil.com",
    "admin": true
  }
}
```

ActiveRecord가 모든 해시 키를 데이터베이스 컬럼에 직접 매핑했기 때문에, 공격자는 단순히 `"admin": true`를 폼 페이로드에 추가하는 것만으로 관리자 권한을 획득할 수 있었습니다.

최신 레일즈는 모든 들어오는 요청 파라미터를 `ActionController::Parameters`로 감싸서 이를 방지합니다.

![Strong Parameters Pipeline: Raw untrusted payload filtered through require and permit before database insertion](https://iili.io/nMKGwpp.png)

기본적으로 `ActionController::Parameters` 인스턴스는 `permitted: false`라는 내부 플래그로 표시됩니다.

만약 허용되지 않은 파라미터 객체를 `User.create(params[:user])`와 같은 ActiveRecord 쓰기 메서드에 직접 전달하려고 시도하면, ActiveRecord는 호출을 가로채고 즉시 `ActiveModel::ForbiddenAttributesError`를 발생시킵니다.

데이터를 저장하려면, 속성 화이트리스트를 명시적으로 선언해야 합니다.

```ruby
private

def user_params
  params.require(:user).permit(:name, :email)
end
```

이 파이프라인은 두 단계로 작동합니다.
1.  **`require(:user)`**: 페이로드에 `:user` 키가 존재하는지 확인하고, 없으면 `ActionController::ParameterMissing` (자동으로 400 Bad Request를 렌더링)을 발생시킵니다.
2.  **`permit(:name, :email)`**: 키들을 순회하며 승인되지 않은 속성(예: `:admin` 또는 `:account_balance`)을 제거하고, `permitted: true`로 표시된 새로운 Parameters 인스턴스를 반환합니다.

이렇게 소독되고 명시적으로 승인된 데이터만이 데이터베이스 계층에 도달합니다. 저는 이 Strong Parameters가 Rails의 가장 중요한 보안 기능 중 하나라고 생각합니다. 예전 프로젝트에서 사용자 정보 업데이트 로직을 검토하다가 `permit`을 빼먹고 배포할 뻔했던 아찔한 경험이 있는데, 그때마다 '휴, 이거 없었으면 큰일 날 뻔했다' 싶죠.

## 패러다임의 전환: 마법에서 숙련으로

개발자들이 "레일즈 마법"에 대해 불평할 때, 그들은 대개 레일즈가 상용구 코드(boilerplate code)를 너무 효과적으로 숨겨서 기본 메커니즘이 보이지 않게 되는 사실에 반응하는 것입니다.

하지만 이 행동들 중 어느 것도 신비롭지 않습니다.

1.  **요청 양파(The Request Onion)**는 보편적인 루비 인터페이스를 따르는 Rack 미들웨어 래퍼들의 모듈식 체인입니다.
2.  **ActiveRecord 스키마 리플렉션(Schema Reflection)**은 런타임 모듈 포함과 결합된 동적 데이터베이스 카탈로그 조사입니다.
3.  **뷰 핸드오프(The View Handoff)**는 `view_assigns`를 통한 자동화된 딕셔너리 할당입니다.
4.  **Zeitwerk 오토로딩(Autoloading)**은 프로덕션 이저 로딩으로 최적화된 엄격한 상수-경로 변환입니다.
5.  **커넥션 풀링(Connection Pooling)**은 Puma의 동시성 모델에 맞춰진 스레드 안전한 커넥션 리스 방식입니다.
6.  **Strong Parameters**는 대량 할당 공격으로부터 모델을 보호하는 엄격한 파라미터 필터링입니다.

이러한 컨벤션을 구동하는 메커니즘을 이해하면, 레일즈는 예측 불가능한 속임수처럼 느껴지지 않습니다. 대신 항상 그러했듯이, 저수준의 복잡한 작업에 얽매이지 않고 기능 구현에 집중할 수 있게 해주는 탁월하게 잘 설계된 생산적인 프레임워크가 됩니다.

여러분은 레일즈를 처음 접했을 때, 이 "마법 같은" 행동들 중 어떤 것이 가장 혼란스러웠나요? 그리고 어떤 내부 작동 원리를 발견하고 나서 코드를 작성하고 디버깅하는 방식에 가장 큰 변화가 있었나요? 댓글로 여러분의 경험을 공유해주세요!
