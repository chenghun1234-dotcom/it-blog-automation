# 타입스크립트 AST를 탐험하는 당신에게: 재사용 가능한 타입 가드에서 자식 노드 타입 좁히기 마스터하기 🚀

안녕하세요! 10년 차 프런트엔드 개발자이자 테크 블로거 @nyaomaru입니다. 👋 요즘 `Jev` 프로젝트를 진행하며 새로운 가능성들을 탐색 중이고, OpenAI의 "Decisions API"에도 무척 흥미를 느끼고 있습니다.

최근 타입스크립트 컴파일러 API를 깊이 들여다보면서 한 가지 꽤 구체적인 질문에 부딪혔습니다.

> 재사용 가능한 타입 가드가 AST 노드 타입뿐만 아니라, **하위 속성(child property)의 좁혀진 타입까지 유지할 수 있을까?**

처음에는 이 문제가 컴파일러 API에만 국한된 특수한 상황이라고 생각했습니다. 하지만 동일한 패턴을 일반적인 타입스크립트 객체를 가지고 재현해보고 나서야 제 관점이 완전히 바뀌었죠. 결국, 흥미로웠던 본질적인 문제는 AST 자체가 아니었습니다. 그것은 바로 **속성 정제(property refinement)**였던 거죠.

자, 함께 자세히 들여다보겠습니다! 👀

## 🌲 아주 흔한 컴파일러 API 패턴

우선, 넓은 범위의 `ts.Node`가 있다고 가정해 봅시다.

```ts
import * as ts from "typescript";

declare const node: ts.Node;
```

여기서 우리는 두 가지를 알고 싶습니다.

*   이것이 `CallExpression`인가?
*   그 `expression` 속성이 `Identifier`인가?

인라인으로 작성하면 정말 쉽습니다.

```ts
if (ts.isCallExpression(node) && ts.isIdentifier(node.expression)) {
  // node: ts.CallExpression
  // node.expression: ts.Identifier
  node.expression.text; // 'expression'이 'Identifier'이므로 'text' 속성 접근 가능
}
```

타입스크립트는 컨트롤 플로우를 완벽하게 이해하고 있습니다. 특별한 트릭이 필요하지 않죠. 실제로 제가 팀 프로젝트에서 AST 변환 작업을 할 때, 이렇게 직관적인 조건문은 가독성을 크게 해치지 않는다면 그대로 두는 편입니다. 굳이 추상화해서 복잡도를 높일 필요는 없으니까요.

## 🤔 만약 이 구조를 재사용하고 싶다면?

이제 동일한 AST 구조가 여러 곳에 나타나는 상황을 상상해 보세요. 예를 들어,

*   방문자(visitor) 패턴
*   `filter` 메서드
*   `find` 메서드
*   다른 변환 로직
*   다른 린트(lint) 규칙

이런 경우, 해당 검사를 함수로 만들어 이름을 붙이는 것이 합리적입니다.

타입스크립트 v5.5부터는 간단한 함수들이 타입 프레디케이트(type predicate)를 자동으로 추론하는 경우가 많습니다. 하지만 이렇게 부모-자식 관계가 얽힌 복합적인 검사는 좀 다릅니다.

```ts
const isCallWithIdentifierExpression = (node: ts.Node) =>
  ts.isCallExpression(node) && ts.isIdentifier(node.expression);
// 추론된 타입:
// (node: ts.Node) => boolean
```

보시다시피, 단순히 `boolean`만 반환할 뿐입니다. 추출된 프레디케이트가 두 가지 사실(부모가 `CallExpression`이고 자식이 `Identifier`라는 사실)을 모두 유지하게 하려면, 우리는 **정제된 타입을 명시적으로** 기술해야 합니다.

```ts
const isCallWithIdentifierExpression = (
  node: ts.Node,
): node is ts.CallExpression & {
  expression: ts.Identifier;
} => ts.isCallExpression(node) && ts.isIdentifier(node.expression);
```

이렇게 하면 잘 작동합니다. 이제 이 함수를 재사용할 수 있죠.

```ts
declare const nodes: readonly ts.Node[];

const calls = nodes.filter(isCallWithIdentifierExpression);
// calls:
// Array<
//   ts.CallExpression & {
//     expression: ts.Identifier;
//   }
// >
```

> 그래서 문제가 뭐냐고요?

사실 런타임에는 전혀 문제가 없습니다. 귀찮은 부분은 우리가 이 부분을 수동으로 기술해야 했다는 거죠 👇

```ts
ts.CallExpression & {
  expression: ts.Identifier;
}
```

하지만 우리는 이미 해당 런타임 검사를 정확히 수행했습니다. 이 검사들을 조합하고 타입이 자연스럽게 따라오도록 할 수 있다면 얼마나 좋을까요? 😸

## 🧩 부모와 자식을 함께 정제하기

이 지점에서 제가 `refineKey`를 사용하게 되었습니다.

[`is-kit`](https://github.com/nyaomaru/is-kit) 라이브러리를 사용하면 다음과 같이 간단해집니다.

```ts
import * as ts from "typescript";
import { and, refineKey } from "is-kit";

const isCallWithIdentifierExpression = and(
  ts.isCallExpression,
  refineKey("expression", ts.isIdentifier),
);
```

정말 간단하죠? 이제 이렇게 활용할 수 있습니다.

```ts
declare const node: ts.Node;

if (isCallWithIdentifierExpression(node)) {
  // node:
  // ts.CallExpression & {
  //   expression: ts.Identifier;
  // }
  node.expression.text; // 'expression' 속성에 안전하게 접근 가능
}
```

여기서 흥미로운 점은 두 검사 사이의 관계입니다.

```ts
ts.isCallExpression;
```

이것은 부모 노드의 타입을 좁힙니다.

그리고

```ts
refineKey("expression", ts.isIdentifier);
```

이 조합된 좁히기 체인(narrowing chain) 내에서, 이미 `ts.isCallExpression`에 의해 좁혀진 부모의 특정 속성을 검사하고, 해당 자식 속성의 타입을 보존합니다.

그래서 핵심 아이디어는 이겁니다.

> 런타임에 자식을 한 번 검사한 다음, 그 동일한 사실을 부모 타입으로 다시 가져와 보존하는 거죠.

## 😸 이건 AST 문제가 아니었습니다

이 연구를 진행하면서 가장 놀랐던 부분이 바로 여기였습니다. 저는 원래 타입스크립트 컴파일러 API의 특정 "빈틈"을 파헤치고 있다고 생각했죠.

하지만 동일한 형태의 문제는 일반적인 객체에서도 나타납니다. 개념적으로 이 패턴은 그저

```text
Parent
  ↓
속성 검사
  ↓
Parent & {
  property: RefinedChild
}
```

일 뿐입니다. 컴파일러 API는 단지 AST 코드가 이 패턴을 모든 곳에서 사용하기 때문에, 이 패턴에 대한 아주 좋은 스트레스 테스트 환경을 제공할 뿐이었죠.

예를 들어,

```text
CallExpression
  → expression
  → Identifier
```

또는

```text
VariableDeclaration
  → initializer?
  → CallExpression
```

또는

```text
CallExpression
  → arguments[0]
  → StringLiteral
```

그래서 저는 `refineKey`를 컴파일러 API 헬퍼라고 생각하지 않습니다. 컴파일러 API는 단지 더 일반적인 조합 문제에 대한 고급 예시일 뿐이죠.

## 🔗 컴파일러 API 가드는 이미 잘 조합됩니다

제가 피하고 싶었던 또 다른 점은 타입스크립트의 기존 프레디케이트를 불필요하게 래핑하는 것이었습니다. 컴파일러 API는 이미 훌륭한 가드들을 제공하고 있죠.

```ts
ts.isStringLiteral;
ts.isIdentifier;
ts.isCallExpression;
ts.isClassDeclaration;
```

우리는 이들을 재사용해야 합니다.

예를 들어,

```ts
import * as ts from "typescript";
import { or } from "is-kit";

const isStringLike = or(ts.isStringLiteral,　ts.isNoSubstitutionTemplateLiteral);

declare const nodes: readonly ts.Node[];

const strings = nodes.filter(isStringLike);
// strings:
// (
//   | ts.StringLiteral
//   | ts.isNoSubstitutionTemplateLiteral
// )[]
```

`is-kit`이 자체적인

```ts
isTsStringLiteral();
isTsIdentifier();
isTsCallExpression();
```

같은 함수를 만들 이유가 전혀 없습니다. 그것은 단지 컴파일러 API를 복제하는 것에 불과할 테니까요. 여기서 정말 유용한 부분은 바로 **조합(composition)**입니다.

## ♻️ `find`와 방문자(Visitor)에서 동일한 가드 재사용하기

이렇게 정제된 형태가 여러 컨텍스트에서 나타날 때, 이 기법은 더욱 유용해집니다.

예를 들어,

```ts
import * as ts from "typescript";
import { and, refineKey } from "is-kit";

const isIdentifierNamedJsxAttribute = and(
  ts.isJsxAttribute,
  refineKey("name", ts.isIdentifier),
);
```

이를 `find` 메서드와 함께 사용할 수 있습니다.

```ts
declare const attributes: readonly ts.JsxAttributeLike[];

const attribute = attributes.find(isIdentifierNamedJsxAttribute);
// attribute:
// (
//   ts.JsxAttribute & {
//     name: ts.Identifier;
//   }
// ) | undefined
```

동일한 가드가 방문자 패턴에서도 작동합니다.

```ts
function visit(node: ts.Node): void {
  if (isIdentifierNamedJsxAttribute(node)) {
    // node:
    // ts.JsxAttribute & {
    //   name: ts.Identifier;
    // }
    node.name.text; // 'name'이 Identifier임을 보장받아 안전하게 접근
  }
  ts.forEachChild(node, visit);
}
```

바로 이 시점에서 가드를 추출하는 것이 진가를 발휘하기 시작합니다. 런타임 규칙과 타입스크립트의 타입 좁히기가 함께 움직이는 거죠. 이런 패턴은 특히 Lint 룰이나 코드 변환기를 만들 때 빛을 발하는데요. 저도 예전에 복잡한 코드 리팩토링 툴을 개발하면서 비슷한 로직을 여러 곳에 반복해서 적용해야 했던 경험이 있습니다. 그때마다 이처럼 명확하게 정의된 가드를 사용하니 코드의 일관성과 유지보수성이 크게 향상되더군요.

## 🫥 선택적 자식(Optional Children)은 다른 계약입니다

AST 노드에는 많은 선택적 속성(optional properties)이 포함되어 있습니다.

예를 들어, `VariableDeclaration`은 `initializer`를 가질 수도 있고, 가지지 않을 수도 있습니다.

```ts
declaration.initializer; // undefined일 수도 있음
```

따라서 이것은 필수 속성을 정제하는 것과는 약간 다릅니다. 우리는 단순히

> `initializer`를 정제하라.

가 아니라,

> `initializer`가 **존재해야 하며**, 그 다음에 정제하라.

를 원합니다. 이 경우 `is-kit`에는 `refineDefinedKey`가 있습니다.

```ts
import * as ts from "typescript";
import { refineDefinedKey } from "is-kit";

const hasCallInitializer = refineDefinedKey("initializer", ts.isCallExpression);
```

이제 이렇게 활용할 수 있습니다.

```ts
declare const declaration: ts.VariableDeclaration;

if (hasCallInitializer(declaration)) {
  // declaration.initializer: ts.CallExpression
  declaration.initializer.expression; // 'initializer'가 존재하고 'CallExpression'임을 보장
}
```

해당 분기 안에서 `initializer`는 두 가지 모두입니다.

*   존재하며 (`undefined`가 아님)
*   `ts.CallExpression`입니다.

`initializer`가 없는 경우 `false`를 반환합니다. 명시적으로 `undefined`인 `initializer`도 `false`를 반환하죠. 저는 이 `refineDefinedKey`를 `refineKey`와 분리해두는 것이 좋다고 생각합니다. 왜냐하면 부재(absence)는 단순한 타입스크립트 주석이 아니라 런타임 동작이기 때문입니다.

## 📦 배열도 같은 문제를 가집니다

AST 배열은 또 다른 작은 문제를 야기합니다.

첫 번째 인자가 문자열 리터럴인 호출(call)을 찾고 싶다고 가정해 봅시다.

```ts
node.arguments[0];
```

이것은 간단해 보이지만, 런타임에는 배열이 비어있을 수도 있습니다.

따라서 우리는 두 가지를 증명하고 싶습니다.

*   인덱스 `0`이 존재한다.
*   그 값이 `StringLiteral`이다.

이 또한 조합할 수 있습니다.

```ts
import * as ts from "typescript";
import { and, refineIndex, refineKey } from "is-kit";

const isCallWithStringFirstArgument = and(
  ts.isCallExpression,
  refineKey("arguments", refineIndex(0, ts.isStringLiteral)),
);
```

그러면 다음과 같이 활용할 수 있죠.

```ts
declare const node: ts.Node;

if (isCallWithStringFirstArgument(node)) {
  // node: ts.CallExpression
  // node.arguments[0]: ts.StringLiteral
  node.arguments[0].text; // 'arguments[0]'이 존재하고 'StringLiteral'임을 보장
}
```

이제 인덱스 `0`은 존재하고 `ts.StringLiteral`임이 확실해집니다. 다시 말하지만, 이것은 AST에만 국한된 아이디어가 아닙니다. 단순히

> 한 번 검사된 위치를 정제하고, 그 사실을 보존하는 것.

이죠.

## 🪆 중첩된 검사도 조합 가능합니다

이러한 정제는 중첩될 수도 있습니다.

다음과 같은 함수형 선언(function-like declaration)을 찾고 싶다고 가정해 봅시다.

*   `body`가 존재한다.
*   `body`는 블록(block)이다.
*   첫 번째 문(statement)이 존재한다.
*   첫 번째 문이 `return` 문이다.

이러한 조각들을 개별적으로 만들 수 있습니다.

```ts
import * as ts from "typescript";
import { and, refineDefinedKey, refineIndex, refineKey } from "is-kit";

const isBlockStartingWithReturn = and(
  ts.isBlock,
  refineKey("statements", refineIndex(0, ts.isReturnStatement)),
);

const hasBodyStartingWithReturn = refineDefinedKey(
  "body",
  isBlockStartingWithReturn,
);
```

그러면 이렇게 활용할 수 있습니다.

```ts
declare const functionLike: ts.FunctionLikeDeclaration;

if (hasBodyStartingWithReturn(functionLike)) {
  // functionLike.body: ts.Block
  // functionLike.body.statements[0]: ts.ReturnStatement
  functionLike.body.statements[0].expression; // 안전하게 접근
}
```

각 단계는 한 가지 사실을 증명합니다.

`body.statements[0]`와 같은 "경로 문자열"도, 특별한 AST DSL도 없습니다. 그저 작은 가드들이 함께 조합될 뿐이죠.

## 🔒 왜 하나의 구체적인 키나 인덱스만 가능한가?

여기에는 중요한 제약 사항이 있습니다.

성공적인 조회는 하나의 구체적인 위치를 증명합니다.

만약 우리가

```ts
refineKey("expression", ...)
```

을 검사했다면, 우리는

```ts
parent.expression;
```

에 대해 무언가를 증명한 것입니다. 우리는 더 넓은 키 도메인의 모든 속성이 동일한 테스트를 통과했다고 **증명한 것이 아닙니다**.

그렇기 때문에 이 정제 헬퍼들은 의도적으로 하나의 구체적인 키나 인덱스에 대해 작동합니다. 넓은 키 유니온이나 이와 유사한 다중 위치 주장은 결과 타입을 과장하기 쉽게 만들 수 있습니다.

저는 하나의 런타임 조회가 실제로 검사한 것보다 더 많은 것을 주장하게 하는 것보다, API를 약간 덜 마법처럼 만드는 편이 낫다고 생각합니다.

## 🧪 TypeScript 7은 어떨까요?

타입스크립트 v7이 컴파일러 API의 지형을 변화시키면서, 이 연구는 특히 흥미로워졌습니다.

이 섹션의 예제들은 타입스크립트 v7.0.2를 기준으로 검증되었습니다.

타입스크립트 v7.0.2 현재, AST 타입과 프레디케이트는 다음 경로를 통해 노출됩니다.

```text
typescript/unstable/ast
```

따라서 동일한 조합 스타일을 여기에서도 사용할 수 있습니다.

```ts
import * as ast from "typescript/unstable/ast";
import { and, refineKey } from "is-kit";

const isCallWithIdentifierExpression = and(
  ast.isCallExpression,
  refineKey("expression", ast.isIdentifier),
);
```

제가 특별히 조사했던 한 가지는 타입스크립트 v7이 `kind`를 통한 좁히기(narrowing)를 통해 이러한 `isX` 검사를 불필요하게 만들지는 않았는지였습니다.

진정한 판별 유니온(discriminated union)의 경우, 타입스크립트는 리터럴 판별자를 통해 타입을 확실히 좁힐 수 있습니다. 하지만 타입스크립트 v7 AST 표면에서 현재 노출되는 광범위한 AST `Node`는 그런 종류의 닫힌 판별 유니온이 아닙니다.

따라서 광범위한 AST 노드와 함께라면, `isX` 프레디케이트는 여전히 중요합니다.

예를 들어,

```ts
import * as ast from "typescript/unstable/ast";

declare const node: ast.Node;

if (node.kind === ast.SyntaxKind.CallExpression) {
  // 광범위한 ast.Node는 여기서 CallExpression 속성들을 자동으로 노출하지 않습니다.
}
```

이러한 차이점은 중요합니다. 판별 유니온으로 모델링된 사용자 정의 AST 타입은 다르게 작동할 수 있습니다. 그렇다고 해서 타입스크립트 v7의 광범위한 `Node`가 현재 같은 방식으로 작동한다는 의미는 아닙니다.

### 왜 `Node`를 닫힌 유니온으로 만들지 않는가?

제가 이 문제에 대해 글을 올린 후, [Jake Bailey](https://bsky.app/profile/jakebailey.dev/post/3mwpa3wwmjs2d)가 아주 간결한 답변을 주었습니다.

> "느려지니까요 😞"

{% embed https://bsky.app/profile/jakebailey.dev/post/3mwpa3wwmjs2d %}

이로써 트레이드오프(trade-off)를 훨씬 쉽게 이해할 수 있게 되었습니다.

만약 `Node`가 모든 AST 노드 타입을 포함하는 하나의 닫힌 판별 유니온이었다면, `kind`는 잠재적으로 더 강력한 좁히기와 완전성 검사를 제공했을 것입니다.

예를 들어, 닫힌 유니온을 사용하면 익숙한 `never` 패턴을 활용할 수 있습니다.

```ts
switch (node.kind) {
  // 알려진 모든 종류 처리...

  default: {
    const exhaustive: never = node; // 새로운 변형이 추가되면 여기서 컴파일 에러 발생
  }
}
```

새로운 변형이 추가되면, 이 `never` 검사가 컴파일 시점에 실패하여 우리의 처리 로직이 더 이상 완전하지 않다는 것을 알려줄 수 있습니다.

하지만 이처럼 강력한 타입 레벨 모델은 공짜가 아닙니다. 그 대가는 바로 타입 검사 성능입니다. 매우 큰 닫힌 유니온은 타입 검사기에게 더 많은 작업을 부여하죠.

따라서 `ast.Node`의 넓은 형태는 단순히 좁히기 기능이 누락된 것이 아닙니다. 여기에는 실제적인 트레이드오프가 존재합니다.

> 더 강력한 컴파일 시점의 완전성 vs. 타입 검사 성능

그리고 이것은 `ast.isCallExpression()`과 같은 명시적인 프레디케이트가 여전히 중요한 역할을 하는 이유를 설명하는 데도 도움이 됩니다.

한 가지 더 타입스크립트 7에 특화된 세부 사항을 염두에 두어야 합니다.

`typescript/unstable/ast`의 `unstable` 부분도 중요합니다. 아직 진화 중인 API 표면에 맞춰 문서화 약속을 빌드하는 것은 지양해야 합니다. 조합 패턴은 일반적이지만, 정확한 타입스크립트 v7 통합은 타입스크립트 자체의 발전과 함께 진화할 수 있습니다.

## ✋ 모든 AST 검사에 이 방법이 필요한 것은 아닙니다

이 점 또한 중요합니다.

만약 제가 하나의 로컬 조건만 있다면,

```ts
if (ts.isReturnStatement(node) && node.expression) {
  // node: ts.ReturnStatement
  // node.expression: ts.Expression
  visit(node.expression);
}
```

저는 이 코드를 인라인으로 둘 것입니다. 정말로요.

단지 가능하다고 해서 이것을

```ts
const isReturnWithExpression = ...
```

으로 바꾸는 것이 자동으로 코드를 더 좋게 만드는 것은 아닙니다.

저는 유용한 분기점을 다음과 같이 생각합니다.

| 상황                         | 선호하는 방식                                         |
| :--------------------------- | :--------------------------------------------- |
| 하나의 로컬 분기               | 네이티브 `ts.isX` 검사                         |
| 반복되는 AST 형태             | 이름 있는 재사용 가능한 가드                           |
| 프로젝트에서 이미 `is-kit`을 사용 중 | `refineKey`, `refineDefinedKey`, `refineIndex` |

목표는

> 모든 `ts.isX` 조건을 `is-kit`으로 대체하는 것

이 아닙니다. 목표는

> 런타임의 사실이 재사용 가능한 "어휘(vocabulary)"가 될 때, 타입 좁히기도 재사용 가능하도록 유지하는 것

입니다.

---

## 🚫 `is-kit`이 시도하지 않는 것들

`is-kit`은 컴파일러 API 프레임워크가 되려고 하지 않습니다.

다음과 같은 것들을 하지 않습니다.

*   개별 컴파일러 API 함수들을 래핑하는 것
*   완전한 AST 노드 형태를 검증하는 것
*   AST 순회(traversal)를 제어하는 것
*   AST 사이클을 감지하는 것
*   타입스크립트 런타임 의존성을 추가하는 것
*   타입스크립트를 피어 의존성으로 요구하는 것
*   명확한 일회성 인라인 검사를 대체하는 것

컴파일러 API는 단지 일반적인 속성 정제에 대한 까다로운 실제 사례일 뿐입니다. 제가 지키고 싶은 경계는 바로 이 지점이죠.

## 🎯 가장 중요한 부분

이 연구를 시작할 때는 "아마 타입스크립트 컴파일러 API에 어떤 특별한 처리가 필요할 거야"라고 생각했습니다.

제가 발견한 것은 훨씬 더 일반적인 문제였습니다.

반복되는 문제는 다음과 같았죠.

```text
부모 좁히기
    ↓
자식 검사하기
    ↓
두 가지 사실 모두 보존하기
    ↓
프레디케이트 재사용하기
```

이는 AST 노드에 유용하지만, 본질적으로 AST 노드에만 국한된 이야기는 아니었습니다.

따라서 현재 저의 사고 모델은 다음과 같습니다.

*   실제 런타임 지식을 위해서는 네이티브 타입 가드를 사용합니다.
*   일회성 조건은 인라인으로 유지합니다.
*   동일한 검사된 형태가 재사용 가능한 "어휘"가 될 때, 이름 있는 가드를 조합합니다.
*   교차 타입을 수동으로 다시 작성하는 대신, 부모에서 자식 정제를 보존합니다.

컴파일러 API의 경우, 이런 모습이 될 수 있습니다.

```ts
const isCallWithIdentifierExpression = and(
  ts.isCallExpression,
  refineKey("expression", ts.isIdentifier),
);
```

작은 런타임 검사들.
작은 재사용 가능한 조각들.
그리고 타입스크립트는 우리가 실제로 검사한 사실들을 그대로 유지시켜 줍니다. 😸
