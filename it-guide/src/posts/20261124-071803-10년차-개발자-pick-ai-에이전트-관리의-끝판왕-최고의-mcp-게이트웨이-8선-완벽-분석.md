# [10년차 개발자 PICK] AI 에이전트 관리의 끝판왕! 최고의 MCP 게이트웨이 8선 완벽 분석

AI 에이전트가 비즈니스 전반에 깊숙이 침투하면서, 단순한 기능 호출을 넘어 '관리'와 '제어'의 중요성이 부각되고 있습니다. 하나의 에이전트가 하나의 MCP(Multi-Modal Collaboration Protocol) 서버에 연결하는 건 사실 어렵지 않습니다. 그저 URL을 붙여넣고, 프롬프트 승인만 하면 에이전트가 알아서 도구를 사용하기 시작하죠.

하지만 문제는 에이전트가 두 개, 다섯 개로 늘어나고 MCP 서버가 여러 개가 될 때 발생합니다. 누가 어떤 자격 증명으로 CRM에 접근하는지, 어떤 에이전트가 민감한 도구를 호출할 수 있는지 명확하게 답할 수 없는 혼돈의 카오스에 빠지게 됩니다.

바로 이 지점에서 MCP 게이트웨이가 빛을 발하기 시작합니다.

> **과연 어떤 에이전트가, 어떤 자격 증명으로, 어떤 도구를 호출할 수 있으며, 이 모든 과정을 나중에 누가 증명할 수 있을까요?**

MCP 게이트웨이는 에이전트와 MCP 서버 사이에 위치하는 중재자입니다. 에이전트에게는 단일 연결 지점을 제공하고, 각 호출자가 어떤 도구를 볼 수 있고 실행할 수 있는지 결정합니다. 또한, 업스트림 인증을 처리하고, 발생한 모든 일을 꼼꼼하게 기록하죠.

이런 게이트웨이가 없다면, 모든 클라이언트는 자신만의 서버 목록, 토큰, 그리고 '허용됨'에 대한 각자의 정의를 가지고 움직입니다. 개발자 노트북에서는 통할지 몰라도, 프로덕션 환경에서는 걷잡을 수 없는 복잡성을 초래할 겁니다. 제가 처음 이런 환경을 접했을 때, 단순히 URL 복붙하고 토큰 박는 게 전부인 줄 알았죠. 하지만 두세 번째 에이전트가 늘어나고, CRM 연동 이슈가 터지면서 '이대로는 안 되겠다'는 생각이 절실했습니다.

## MCP 게이트웨이, 대체 뭘 하는 녀석일까?

대부분의 MCP 게이트웨이는 다음과 같은 핵심 기능을 제공합니다.

1.  **집중화 (Aggregation).** 여러 MCP 서버를 단일 엔드포인트 뒤로 묶어줍니다. 덕분에 클라이언트는 10개의 URL 대신 하나의 URL만 설정하면 됩니다.
2.  **인증 (Authentication).** 게이트웨이가 에이전트 측의 로그인과 서버 측에서 사용되는 자격 증명(OAuth 플로우 포함)을 관리합니다.
3.  **도구 필터링 (Tool filtering).** 모든 에이전트가 모든 도구를 필요로 하지는 않습니다. 게이트웨이는 사용자, 팀 또는 키별로 어떤 도구가 보이는지, 그리고 호출 가능한지 결정합니다.
4.  **로깅 및 추적 (Logging and tracing).** 모든 도구 호출은 기록으로 남아 나중에 검색하고 분석할 수 있습니다.
5.  **비용 및 컨텍스트 제어 (Cost and context control).** 대규모 도구 카탈로그는 모델에 설명되는 것만으로도 토큰을 빠르게 소모시킵니다. 일부 게이트웨이는 이 비용 절감에도 도움을 줍니다.

어떤 제품은 MCP 전용으로 설계되었고, 어떤 제품은 LLM 게이트웨이나 API 관리 솔루션에서 MCP 기능을 추가했습니다. 둘 중 어느 쪽이 무조건 더 좋다고 말할 수는 없습니다. 중요한 건 여러분이 현재 어떤 인프라를 사용하고 있느냐에 달려있죠.

## 게이트웨이는 MCP 서버가 아니다! (중요한 오해)

이 부분에서 많은 혼동이 발생합니다.

MCP 서버는 도구를 노출합니다. 에이전트는 언제 이 도구를 호출할지 결정하죠. 게이트웨이는 오직 **해당 호출이 서버에 도달해도 되는지, 그리고 어떤 결과가 다시 돌아와야 하는지**를 결정할 뿐입니다.

마치 방문객 기록이 있는 프런트 데스크를 떠올려 보세요.

-   이 호출자는 누구인가?
-   어떤 서버와 도구를 볼 수 있는가?
-   이 인자들로 이 도구를 호출해도 되는가?
-   업스트림 서버는 어떤 자격 증명을 받아야 하는가?
-   도구가 무엇을 반환했으며, 모델이 그 모든 것을 보아도 되는가?

만약 서비스 앞에 API 게이트웨이를 두어 본 경험이 있다면, 이 개념이 매우 익숙하게 느껴질 겁니다. 유일한 차이점은 호출자가 스스로 얼마나 많은 호출을 할지 결정하는 에이전트라는 점이죠.

## 서버 수준의 접근 권한만으로는 부족한 이유

에이전트가 GitHub MCP 서버에 연결하도록 허용하는 것은 너무나도 '거친' 결정입니다. 진짜 질문은 "해당 서버의 **어떤 도구를** 사용할 수 있는가?"입니다.

```text
지원 에이전트가 티켓을 읽을 수 있는가? 네.
티켓을 닫을 수 있는가? 아마도.
리포지토리를 삭제할 수 있는가? 아니요.
도구의 프로덕션 버전을 호출할 수 있는가? 승인 후에만 가능.
```

이것들은 '도구 수준'의 질문입니다. 전체 서버를 허용하거나 차단하는 게이트웨이는 이런 질문에 답할 수 없습니다.

위험한 부분은 요청에서 끝나지 않습니다. 도구가 실행되도록 허용되었어도, 토큰, 고객 기록 또는 모델이 반응할 수 있는 '오염된' 지침을 반환할 수 있습니다. 좋은 제어는 양방향 모두를 커버해야 합니다.

## 프로덕션 환경의 MCP 게이트웨이는 무엇을 해야 하는가?

다음 여섯 가지는 반드시 평가할 가치가 있습니다. 이들이 명확해지기 전까지 다른 세부 사항들은 중요도가 떨어집니다.

| 제어 항목          | 질문                                         | 왜 중요한가                                             |
| :----------------- | :------------------------------------------- | :------------------------------------------------------ |
| **도구 수준 정책** | 서버만이 아닌 개별 도구를 허용, 거부, 범위 지정할 수 있는가? | 도구는 실제 시스템을 읽고 변경합니다.                   |
| **식별**           | 에이전트와 그 뒤의 사람 또는 서비스를 식별할 수 있는가? | 하나의 공유 토큰은 거버넌스가 아닙니다.                 |
| **업스트림 인증**  | 사용자 및 서버별 OAuth 및 자격 증명을 관리하는가? | 에이전트가 장기 보안 비밀을 가지고 있어서는 안 됩니다. |
| **관측 가능성**    | 도구 호출을 호출자부터 결과까지 추적할 수 있는가? | 사고는 하나의 요청 내에서만 발생하지 않습니다.         |
| **컨텍스트 비용**  | 대규모 도구 카탈로그의 토큰 비용을 줄이는가?    | 도구 정의는 빠르게 누적됩니다.                          |
| **배포**           | 데이터 및 자격 증명이 허용되는 곳에서 실행될 수 있는가? | 보안 규칙이 기능보다 먼저 배포를 결정하는 경우가 많습니다. |

진정한 평가와 단순 기능 체크리스트를 구분하는 두 가지 핵심 질문이 있습니다.

> 위험한 도구 호출을 실행 전에 차단할 수 있는가?

> 아무것도 재배포하지 않고 특정 에이전트의 접근 권한을 즉시 취소할 수 있는가?

만약 답변이 "대시보드에서 나중에 볼 수 있습니다"라면, 그것은 관측 가능성이지 제어가 아닙니다. 실제로 프로덕션 환경에서 장애가 발생했을 때, 에이전트의 어떤 호출이 어떤 서버에 도달했고 어떤 결과를 냈는지 빠르게 추적하는 것이 관건입니다. 제가 예전에 이런 부분을 간과했다가 밤샘 디버깅으로 고생했던 기억이 생생하네요.

## 주목할 만한 8가지 MCP 게이트웨이

이것은 보편적인 순위가 아닙니다. "최고"는 여러분이 어디에서 운영하는지, 이미 무엇을 사용하고 있는지, 관리형 서비스를 원하는지 또는 팀이 직접 소유하길 원하는지에 따라 달라집니다.

이 카테고리의 제품 기능은 빠르게 변화합니다. 이 목록을 POC(개념 증명)를 위한 단기 목록으로 취급하고, 장기적인 결정을 내리기 전에 현재 문서, 라이선스, 티어 제한을 반드시 확인하세요.

### 1. Bifrost

![Bifrost](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/fbhhkygkku15c2618jia.png)

**최적의 사용자:** MCP 도구, 모델 트래픽, 에이전트-간(A2A) 호출을 위한 단일 자체 호스팅 게이트웨이를 원하는 팀, 특히 VPC, 온프레미스 또는 에어갭(air-gapped) 배포가 중요한 경우.

[Bifrost](https://www.getmaxim.ai/)는 MCP 클라이언트 역할(도구 서버에 연결)과 MCP 서버 역할(Claude Desktop 또는 Claude Code와 같은 클라이언트에 하나의 관리되는 엔드포인트 노출)을 동시에 수행합니다. 에이전트는 한 번만 연결하면 게이트웨이 뒤의 새로운 서버가 모든 클라이언트를 건드리지 않고 나타납니다.

접근 제어는 [가상 키(virtual keys)](https://docs.getbifrost.ai/features/governance/virtual-keys)를 통해 이루어집니다. 각 키는 MCP 클라이언트 및 개별 도구의 허용 목록을 가질 수 있으며, 동일한 키가 모델 범위, 예산 및 속도 제한도 담당합니다. 도구 필터링은 [계층화(layered)](https://docs.getbifrost.ai/mcp/filtering)되어 있습니다. 요청 헤더는 호출자가 보는 것을 좁힐 수는 있지만 넓힐 수는 없으며, 게시된 모델은 키가 접근 권한을 부여받기 전까지 기본적으로 도구를 차단합니다. [가상 MCP 서버(Virtual MCP servers)](https://docs.getbifrost.ai/mcp/virtual-mcps)는 여러 서버의 도구를 하나의 큐레이션된 엔드포인트로 묶어 팀에 제공합니다.

과소평가하기 쉬운 기능은 '코드 모드(Code Mode)'입니다. Bifrost는 모든 도구 정의를 컨텍스트에 로드하는 대신, 연결된 서버를 모델이 필요할 때 읽을 수 있는 컴팩트한 스텁으로 제공합니다. 6개 서버에 걸쳐 96개 도구에서 16개 서버에 걸쳐 508개 도구로 늘어나는 [벤치마크](https://github.com/maximhq/bifrost-benchmarking/blob/main/mcp-code-mode-benchmark/benchmark_report.md)에서 코드 모드는 입력 토큰을 58.2%에서 92.8%까지, 예상 비용을 최대 92.2%까지 절감했으며, 통과율은 100%를 유지했습니다. 도구 수가 많아질수록 절감 효과는 커집니다. [코드 모드 문서](https://docs.getbifrost.ai/mcp/code-mode)에서 설정 방법을 확인할 수 있습니다.

또한 사용자별 OAuth 로그인, 도구 호출 실행 전 승인, 도구 비용 및 호출량과 함께 제공되는 MCP 로그, [고객 VPC 내 배포](https://docs.getbifrost.ai/enterprise/invpc-deployments), 그리고 A2A 트래픽을 위한 [에이전트 게이트웨이](https://docs.getbifrost.ai/features/agent-gateway/overview)를 지원합니다. 감사 로그는 엔터프라이즈 티어에서 제공됩니다.

**평가 시 질문:** 하나의 가상 키로 모델 요청, MCP 도구 호출, 예산을 함께 관리할 수 있는가?

### 2. Kong AI Gateway

![Kong AI Gateway](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/qjsop7686up0tve0yby1.png)

**최적의 사용자:** 이미 Kong Gateway 또는 Kong Konnect를 API 관리용으로 사용하고 있는 조직.

[Kong AI Gateway](https://docs.konghq.com/gateway/latest/ai-gateway/)는 인프라 팀이 이미 일반 API 트래픽에 Kong을 신뢰하고 있는 경우에 매우 매력적입니다. 에이전트용으로 별도의 제어 플레인을 추가하는 대신, 기존 인프라를 확장하여 MCP를 커버할 수 있습니다.

Kong은 관리형 API 위에 중앙 인증, 권한 부여, 속도 제한, 감사 추적 및 MCP 서버 생성을 제공합니다. 마지막 기능은 여러분의 도구가 실제 기존 REST API인 경우에 중요합니다. 각 API에 대한 서버를 작성하지 않고도 REST API를 MCP 도구로 노출할 수 있습니다.

물론 단점도 명확합니다. 만약 Kong을 이미 사용하고 있지 않다면, MCP 트래픽만을 위해 광범위한 API 관리 플랫폼을 채택하는 것은 여러분이 필요로 하는 것보다 더 많은 플랫폼을 도입하는 것일 수 있습니다.

**평가 시 질문:** 실행하는 정확한 MCP 플로우에 대해 도구 수준 제어가 모델 측 제어만큼 성숙한가?

### 3. LiteLLM

![LiteLLM](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/ggsunzme2hlx48ynyb64.png)

**최적의 사용자:** 모델 라우팅과 함께 MCP를 커버하는 오픈 소스, 자체 호스팅 Python 프록시를 원하는 팀.

[LiteLLM](https://docs.litellm.ai/)은 하나의 인터페이스를 통해 여러 모델 제공자를 호출하는 방법으로 시작했습니다. 이제 이 프록시에는 [MCP 게이트웨이](https://docs.litellm.ai/docs/mcp)가 포함되어 있어, MCP 서버가 모델 트래픽 옆에 위치하며 가상 키 및 팀별로 접근 권한을 확인합니다. MIT 라이선스이며 여러분의 환경에서 실행됩니다.

직접 운영해야 하는 Python 서비스이므로 데이터베이스, 업그레이드 및 스케일링을 고려해야 합니다. SSO 및 감사 로그와 같은 일부 거버넌스 기능은 엔터프라이즈 제품으로 분류되어 있으므로, 오픈 소스 티어가 여러분의 요구 사항을 얼마나 커버하는지 확인해야 합니다.

**평가 시 질문:** 팀이 프록시, 데이터베이스 및 업그레이드 경로를 소유할 수 있는가, 그리고 여러분의 티어에 어떤 거버넌스 기능이 포함되는가?

### 4. Amazon Bedrock AgentCore Gateway

![Amazon Bedrock AgentCore Gateway](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/joaalrmx1jfcbaxuze7n.png)

**최적의 사용자:** 완전 관리형 게이트웨이를 원하고 제어 플레인을 AWS 내부에 유지하는 데 익숙한 AWS 네이티브 팀.

[Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/)는 API, 람다 함수 및 기존 서비스를 MCP 호환 도구로 변환할 수 있습니다. 이는 인바운드 ID 확인, 아웃바운드 자격 증명 주입, OAuth 플로우, 그리고 에이전트가 매우 큰 카탈로그에 직면했을 때 도움이 되는 도구 검색을 지원합니다.

Bedrock 및 AWS ID를 기반으로 이미 구축 중인 팀에게 가장 빠른 경로입니다. 운영해야 할 게이트웨이 인프라가 적고 조립해야 할 구성 요소도 적습니다.

제한 사항도 명확합니다. 이는 관리형 AWS 서비스입니다. 온프레미스 배포, 멀티클라우드 제어 플레인 또는 에어갭 환경이 필요한 경우, 이는 적절한 기준선이 아닐 가능성이 높습니다.

**평가 시 질문:** 어떤 자격 증명이 AWS에서 관리되며, 어떤 ID를 다운스트림 도구로 전달할 수 있는가?

### 5. IBM ContextForge

![IBM ContextForge](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/qhg5seqwv6oq6otifhbq.png)

**최적의 사용자:** MCP 서버, REST API, gRPC 서비스 및 에이전트의 복잡한 실제 컬렉션을 통합해야 하는 팀.

[IBM ContextForge](https://github.com/IBM/mcp-context-forge)는 MCP 프록시 역할보다는 검색 및 통합에 더 중점을 둡니다. 여러 내부 서비스를 하나의 엔드포인트 뒤에 두고 REST 또는 gRPC 서비스를 도구 친화적인 형태로 변환할 수 있습니다.

이것은 "에이전트에게 20년간 축적된 내부 API의 안전한 카탈로그를 어떻게 제공할까?"라는 실제 문제가 있을 때 흥미로운 솔루션이 됩니다.

공개된 기능에는 사용자 범위 OAuth, 재시도, 속도 제한, OpenTelemetry, 관리 UI 및 에어갭 배포 지원이 포함됩니다.

**평가 시 질문:** 에이전트별 엄격한 예산 집행이 필요한가, 아니면 도구 및 서비스 통합이 주된 문제인가?

### 6. Azure API Management

![Azure API Management](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/a7nazj2xy06m3996h1qg.png)

**최적의 사용자:** 이미 Azure API Management를 사용하고 있고, 다른 API와 동일한 정책으로 MCP 트래픽을 관리하려는 팀.

Microsoft의 AI 게이트웨이는 별도의 제품이 아닙니다. Azure API Management의 기능 세트이므로, API 팀이 이미 사용하는 정책, 모니터링 및 개발자 포털이 MCP로 확장됩니다. APIM은 REST API 또는 기존 서버를 [MCP 서버](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview)로 노출할 수 있으며, 속도 제한, JWT 유효성 검사 및 IP 필터링 정책을 적용합니다. 모니터링은 Azure Monitor 및 Application Insights를 통해 이루어집니다.

계획에 따라 세부 사항을 확인하세요. 제가 검토한 문서에는 제한 사항이 명시되어 있습니다. MCP 지원은 도구를 커버하지만 리소스나 프롬프트는 제외하며, MCP 정책은 현재 서버의 모든 도구에 적용되어 도구별 규칙을 설정하기가 더 어렵습니다. 일부 새로운 기능은 클래식 티어의 조기 릴리스 채널을 통해 먼저 제공됩니다.

**평가 시 질문:** 도구별 정책이 필요한가, 아니면 서버 수준 제어가 사용 사례에 충분한가?

### 7. Docker MCP Gateway

![Docker MCP Gateway](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/40lhx8n3y7uhvrtwbly.png)

**최적의 사용자:** 격리된 컨테이너에서 MCP 서버를 실행하고, Docker 워크플로우에 맞는 게이트웨이를 원하는 개발 팀.

[Docker MCP Gateway](https://github.com/docker/mcp-gateway)는 오픈 소스이며 클라이언트와 MCP 서버 사이의 프록시 역할을 합니다. 각 서버를 제한된 권한, 네트워크 접근 및 리소스를 가진 격리된 컨테이너에서 실행하며, 도구가 요청될 때 온디맨드로 서버를 시작합니다.

보안 플래그가 실용적입니다. 이 게이트웨이는 이미지 서명 확인, 호출 로깅, 비밀 차단을 지원하며, 각 서버에서 도구의 일부만 노출할 수 있습니다. 프로필은 사용 사례별로 서버를 그룹화하고 OCI 레지스트리를 통해 공유할 수 있습니다. OpenTelemetry를 통한 분산 추적은 게이트웨이부터 서버 작업까지의 경로를 보여줍니다.

범위는 완전한 엔터프라이즈 게이트웨이보다 좁습니다. Docker 문서에 따르면 Docker AI Governance의 일부인 MCP Gateway는 초대 전용 기능이므로, 중앙 집중식 거버넌스는 Docker 영업을 통해 이루어집니다. 오픈 소스 게이트웨이는 중앙 ID 및 예산 계층이라기보다는 MCP 서버를 위한 안전한 런타임으로서 가장 강력합니다.

**평가 시 질문:** 컨테이너 격리가 주된 관심사인가, 아니면 중앙의 사용자별 ID 및 정책도 필요한가?

### 8. Cloudflare MCP Server Portals

![Cloudflare MCP Server Portals](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/p65swnkjd8wu6pb0bkzf.png)

**최적의 사용자:** Cloudflare One 및 Access를 이미 사용하고 있으며, 다른 기업 애플리케이션과 마찬가지로 MCP를 관리하려는 조직.

[Cloudflare MCP Server Portals](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals)는 여러 MCP 서버를 단일 포털 URL 뒤에 배치합니다. 사용자는 기업 ID 공급자를 통해 Cloudflare Access로 인증하며, Cloudflare는 업스트림 서버의 자체 권한 부여 방식과 상관없이 어떤 서버를 볼 수 있는지 결정합니다. 관리자는 포털별로 도구 및 정책을 사용자 지정할 수 있으며, 모든 서버의 요청 로그가 한곳에 모입니다.

또한 개인 네트워크에만 존재하는 MCP 서버에도 연결할 수 있으며, 선택적인 게이트웨이 경로를 통해 트래픽에 DLP 검사를 추가할 수 있습니다. Cloudflare는 이 기능을 제로 트러스트 모델의 일부로 발표했으므로, 장치 상태 및 유사한 Access 제어가 자연스럽게 통합됩니다.

단점은 명확합니다. 이미 Cloudflare 생태계에 속해 있다면 가장 의미가 있습니다. Cloudflare는 이를 오픈 베타로 출시했으므로, 계획을 세우기 전에 현재 상태와 계획 제한을 확인하세요.

**평가 시 질문:** 포털 내에서 도구 수준 정책이 얼마나 세분화될 수 있는가, 그리고 어떤 제어가 유료 Cloudflare One 플랜을 필요로 하는가?

## '도구 경계'가 진짜 시험대다

모든 벤더는 에이전트가 도구를 호출하는 깔끔한 데모를 보여줄 수 있습니다.

하지만 더 나은 테스트는 **거부되어야 할 도구 호출**입니다.

```text
에이전트: "비활성 고객 기록을 삭제해줘."
도구 요청: DELETE /customers?status=inactive
정책: 이 에이전트는 고객 데이터를 읽을 수 있지만, 삭제할 수는 없다.
예상 결과: 도구 실행은 절대 일어나지 않는다.
```

이제 좀 더 어렵게 만들어 봅시다.

```text
에이전트: "50달러 미만의 환불을 처리해줘."
도구 요청: refund(customer_id, amount)
정책: 에이전트는 현재 사용자의 계정에 대해서만 최대 50달러까지 환불할 수 있다.
예상 결과: 실행 전에 신원, 금액, 소유권, 도구 인자 규칙이 모두 통과되어야 한다.
```

그리고 반환 경로를 테스트해 보세요.

```text
도구 결과: 액세스 토큰 또는 다른 고객의 데이터를 포함한다.
예상 결과: 모델이 보기 전에 결과가 차단되거나 수정된다.
```

마지막 시나리오는 종종 놓치기 쉽습니다. 도구가 실행되도록 허용되었어도, 모델이 받아서는 안 될 정보를 반환할 수 있기 때문이죠.

여러분은 실행 **이전**의 제어와 실행 **이후**의 제어 모두를 원합니다. 제가 실무에서 새로운 게이트웨이를 도입할 때 가장 먼저 테스트하는 부분도 바로 '거부되어야 할 호출이 제대로 차단되는가'입니다. 안전한 길만 테스트하는 건 의미가 없죠.

## 3주를 낭비하지 않는 MCP 게이트웨이 평가 방법

벤더 데모부터 시작하지 마세요. 여러분 환경에서 실제 에이전트의 여정 세 가지부터 시작하세요.

### 여정 1: 정상적이고 안전한 경로

에이전트가 MCP 도구를 통해 내부 문서를 읽고, 요약한 다음, 임시 티켓을 엽니다. 이는 일반적인 라우팅, ID 및 로깅이 작동하는지 증명합니다.

### 여정 2: 반드시 중단되어야 할 요청

에이전트가 자신의 범위를 벗어난 도구를 시도합니다. 이는 게이트웨이가 단순히 보고만 하는 것이 아니라, 실행 자체를 방지하는지 증명합니다.

### 여정 3: 거대한 도구 카탈로그

5개 이상의 MCP 서버를 연결하고, 에이전트가 어떤 작업도 하기 전에 도구 정의에 얼마나 많은 토큰이 사용되는지 측정합니다. 이는 게이트웨이가 컨텍스트 비용을 절감하는 데 도움이 되는지, 아니면 모든 것을 그대로 전달하는지 보여줍니다.

각 여정마다 다음 네 가지 증거를 요청하세요.

1.  호출자 ID
2.  정책 결정
3.  민감한 데이터가 수정된 업스트림 요청 및 결과
4.  에이전트 요청, 도구 호출 및 최종 출력을 연결하는 추적(trace)

만약 어떤 제품이 이 증거들을 쉽게 수집하기 어렵게 만든다면, 나중에 사고 대응이 매우 불쾌해질 겁니다.

## 사람들이 잊어버리는 질문들

### 최종 사용자의 ID를 사용할 수 있는가?

사용자를 대신하여 행동하는 에이전트가 더 넓은 접근 권한을 가진 서비스 계정으로 조용히 변해서는 안 됩니다. 게이트웨이가 사용자 및 도구별로 ID를 교환, 전달 또는 범위 지정할 수 있는지 확인하세요.

### 즉시 접근을 차단할 수 있는가?

MCP 서버가 침해되거나 에이전트가 오작동하기 시작할 경우, 모든 클라이언트를 재배포하지 않고도 하나의 키 또는 도구 번들에 대한 접근을 즉시 비활성화할 수 있는가?

### 도구 설명은 어떻게 되는가?

악의적이거나 오염된 도구 설명은 에이전트를 잘못된 방향으로 유도할 수 있습니다. 게이트웨이가 도구 정의를 고정하거나 검토하는지, 그리고 서버가 이를 변경할 때 어떤 일이 발생하는지 질문하세요.

### 모든 전송 방식을 커버하는가?

MCP는 stdio, SSE, 스트리밍 가능한 HTTP를 포함한 여러 전송 방식을 통해 실행됩니다. 어떤 경로가 동일한 ID, 정책 및 감사 적용 범위를 갖는지 질문하세요.

### 업스트림 서버는 누가 운영하는가?

타사 서버를 프록시하는 게이트웨이는 해당 서버의 위험을 상속받습니다. 서버가 어디에서 실행되는지, 어떻게 격리되는지, 업데이트가 어떻게 검증되는지 질문하세요.

## 솔직한 결론

MCP 게이트웨이는 에이전트를 안전하게 만들어주는 마법의 레이어가 아닙니다.

그것은 여러분이 마침내 규칙을 가시화하고 시행할 수 있는 지점입니다.

올바른 게이트웨이는 대개 기능 목록이 가장 긴 제품이 아닙니다. 여러분이 이미 운영하는 환경에 잘 맞고, 실제로 사용하는 전송 방식을 커버하며, 두려워하는 도구 호출을 중단시키고, 다른 사람이 결정을 이해할 수 있는 충분한 증거를 남기는 게이트웨이입니다.

가장 위험한 도구 호출부터 시작하세요. 그 후에는 모든 것이 명확해질 겁니다.
